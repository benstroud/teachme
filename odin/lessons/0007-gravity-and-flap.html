Lesson 07 · Joust — Physics

Gravity & Flap

Delta time, Euler integration, and the mechanic that makes Joust feel like Joust

← Lesson 06: Platforms

Mission context

The white rectangle falls. Press Space and it climbs. This is the core loop that defines Joust — everything else is layered on top of it. After this lesson the game is playable in the sense that matters: it feels right.

Screen space: Y points down

Before touching code, one conceptual shift. In screen coordinates, (0, 0) is the top-left corner and Y increases downward. This inverts your physical intuition:

vy and what it means
vy < 0 → moving UP ↑
vy = 0 → stationary —
vy > 0 → moving DOWN ↓
consequence for forces
GRAVITY adds to vy (+)
FLAP subtracts from vy (−)
terminal velocity caps vy

Gravity is a positive constant because it accelerates things downward — toward larger Y. A flap impulse subtracts from vy, making it more negative — toward smaller Y, which is up the screen. This will feel backwards once and then become permanent intuition.

Delta time — frame-rate independence

rl.GetFrameTime() returns the time in seconds since the last frame completed. At a steady 60 fps this is about 0.016 s. At 30 fps it is 0.033 s.

If you write vy += GRAVITY without dt, the player falls twice as fast on a 120 fps machine as on a 60 fps one. Multiplying by dt converts units to pixels per second, independent of frame rate:

odin// Without dt — frame-rate dependent (wrong)
player_vy += GRAVITY          // adds some arbitrary amount per frame

// With dt — frame-rate independent (correct)
player_vy += GRAVITY * dt     // adds (pixels/s²) × s = pixels/s per frame

Define physics constants in real-world units — pixels per second or pixels per second squared — and the multiplication makes the units work out.

odinGRAVITY    :: f32(800)   // pixels per second²
FLAP_FORCE :: f32(420)   // pixels per second (subtracted from vy per flap)
MAX_FALL   :: f32(600)   // terminal velocity cap, pixels per second

The physics update

Four lines handle all of Joust's vertical physics. Order matters:

odindt := rl.GetFrameTime()

// 1. Gravity accelerates the player downward each frame
player_vy += GRAVITY * dt

// 2. Cap falling speed — without this, long falls become uncontrollable
player_vy  = min(player_vy, MAX_FALL)

// 3. Flap: each Space press subtracts a fixed upward impulse
if rl.IsKeyPressed(.Space) {
    player_vy -= FLAP_FORCE
}

// 4. Integrate: move position by velocity × time elapsed
player_y += player_vy * dt

Step 4 is Euler integration — the simplest way to advance a physics simulation. Each frame, position moves by velocity multiplied by elapsed time. It is not perfectly accurate for all physics problems, but it is more than sufficient for a 2D arcade game.

min() is a built-in Odin procedure — no import needed. min(vy, MAX_FALL) returns MAX_FALL when vy exceeds it, clamping terminal velocity.

IsKeyPressed vs IsKeyDown

This distinction shapes the entire feel of the flap mechanic:

FunctionReturns true…Use for
IsKeyPressed(.Space) on the single frame the key transitions from up to down Flap — one impulse per press, regardless of how long you hold
IsKeyDown(.Space) every frame the key is held Thrust rockets, held-fire weapons — continuous force while held

Using IsKeyDown for flap would make the player accelerate infinitely upward while the key is held — nothing like Joust. IsKeyPressed gives one impulse per tap, which rewards rapid flapping to climb and punishes holding still.

Vertical wrap

In the original arcade game, flying off the top or bottom of the screen wraps you to the other side. Add this after the position update:

odinif player_y > SCREEN_H            { player_y = -PLAYER_H  }   // fell off bottom → appear at top
if player_y < -PLAYER_H          { player_y = f32(SCREEN_H) }  // flew off top → appear at bottom

The player will still pass through platforms — collision detection comes in Lesson 09. For now, the arena is decoration. That is fine: the physics already feel correct and the platforms give visual context.

The complete main.odin

odinpackage main

import rl "vendor:raylib"

SCREEN_W   :: 800
SCREEN_H   :: 600
GRAVITY    :: f32(800)
FLAP_FORCE :: f32(420)
MAX_FALL   :: f32(600)
PLAYER_W   :: f32(40)
PLAYER_H   :: f32(60)

PLATFORMS :: [?]rl.Rectangle{
    {  0, 554, 280, 46},
    {520, 554, 280, 46},
    { 48, 426, 176, 18},
    {576, 426, 176, 18},
    {288, 316, 224, 18},
    {336, 186, 128, 18},
}

LAVA :: rl.Rectangle{280, 574, 240, 26}

main :: proc() {
    rl.InitWindow(SCREEN_W, SCREEN_H, "Joust")
    defer rl.CloseWindow()
    rl.SetTargetFPS(60)

    player_x:  f32 = 380
    player_y:  f32 = 256
    player_vy: f32 = 0

    for !rl.WindowShouldClose() {
        dt := rl.GetFrameTime()

        // physics
        player_vy += GRAVITY * dt
        player_vy  = min(player_vy, MAX_FALL)

        // input
        if rl.IsKeyPressed(.Space) {
            player_vy -= FLAP_FORCE
        }

        // integrate
        player_y += player_vy * dt

        // vertical wrap
        if player_y  > f32(SCREEN_H) { player_y = -PLAYER_H          }
        if player_y  < -PLAYER_H    { player_y = f32(SCREEN_H)        }

        // draw
        rl.BeginDrawing()

            rl.ClearBackground(rl.BLACK)

            rl.DrawRectangleGradientV(
                i32(LAVA.x), i32(LAVA.y),
                i32(LAVA.width), i32(LAVA.height),
                rl.RED, rl.ORANGE,
            )

            for plat in PLATFORMS {
                rl.DrawRectangleRec(plat, rl.DARKGRAY)
            }

            rl.DrawRectangle(
                i32(player_x), i32(player_y),
                i32(PLAYER_W),  i32(PLAYER_H), rl.WHITE,
            )

            rl.DrawText("JOUST", 10, 10, 20, rl.YELLOW)
            rl.DrawText("SPACE to flap", 10, 34, 14, rl.GRAY)

        rl.EndDrawing()
    }
}

Run it with odin run .. The player falls immediately and Space sends it upward. Spam Space quickly to climb; hold back and it falls. That rhythm is Joust.

Platforms are not solid yet The player passes through every platform. This is expected — collision detection is Lesson 09. Tune the feel now: try adjusting GRAVITY, FLAP_FORCE, and MAX_FALL until it matches the weight you want.

Check your understanding

1. player_vy += GRAVITY * dt each frame updates the player's:

Velocity — vy is velocity, not position. Gravity is an acceleration (pixels per second²), so multiplying by dt gives a velocity change (pixels per second). Position only moves on the separate line player_y += player_vy * dt. Conflating velocity and position is the most common physics beginner mistake.

2. A flap impulse pushes the player upward. In screen space (Y increases downward), that is applied as:

vy -= FLAP_FORCE — subtracting makes vy more negative, which means moving upward (smaller Y). += would add downward force. vy = -FLAP_FORCE also moves up but discards any existing velocity — it feels snappy rather than additive. *= multiplies, which makes no physical sense as an impulse.

3. Euler integration: position is advanced each frame by:

y += vy * dt — position changes by velocity (pixels/s) multiplied by elapsed time (s), yielding pixels. Dividing would give pixels/s², which has the wrong units. Adding or subtracting dt mixes units incompatibly (pixels/s ± seconds = nonsense).

4. To cap the player's maximum fall speed to MAX_FALL, write:

min(vy, MAX_FALL) — when vy exceeds MAX_FALL (e.g. 700 > 600), min returns the smaller value (600), capping the speed. max would do the opposite: enforce a minimum fall speed, which is wrong. abs takes one argument. cap is not an Odin built-in.
