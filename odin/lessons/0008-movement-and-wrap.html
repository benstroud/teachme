Arrow keys, held-key input, and flying off one edge to appear on the other

Mission context

After this lesson the player is fully airborne — gravity, flap, left, right, wrap. The arena is complete except for collision. Next lesson makes the platforms solid; this one makes the rider feel like a rider.

Held-key input: IsKeyDown

Lesson 07 used IsKeyPressed for flap — it fires once on the frame a key transitions from up to down. Horizontal movement needs the opposite: fire every frame while the key is held. That is IsKeyDown.

FunctionReturns true on…Use for
IsKeyPressed(key) the single frame the key first goes down Flap, jump, fire — one-shot impulse
IsKeyDown(key) every frame while the key is held Movement, scroll, charge — continuous action
IsKeyReleased(key) the single frame the key comes back up Release-triggered events

If you used IsKeyPressed(.Left) for movement, the player would nudge one pixel per tap and stop. IsKeyDown gives smooth continuous flight.

Horizontal velocity and facing direction

Add two new variables alongside the existing ones:

odinplayer_vx:     f32 = 0   // horizontal velocity, pixels/s
player_facing: f32 = 1   // 1 = right, -1 = left

player_facing is not used for drawing yet — the player is still a white rectangle. It will control sprite flipping in Lesson 10 when you load the actual bird texture. Store it now so the variable exists when you need it, and updating it costs nothing.

And one new constant:

odinMOVE_SPEED :: f32(200)   // pixels per second horizontal

The input block

odinif rl.IsKeyDown(.Left) {
    player_vx     = -MOVE_SPEED
    player_facing = -1
} else if rl.IsKeyDown(.Right) {
    player_vx     = MOVE_SPEED
    player_facing = 1
} else {
    player_vx = 0            // no key held: stop instantly
}

The else branch stops the player the moment no key is held. The original arcade Joust did have some air resistance, but instant stop is simpler and still feels crisp — tune it later if you want. Negative vx is left; positive vx is right. Same sign convention as vertical: positive = larger X = rightward.

Screen wrap — horizontal

Exact same pattern as vertical wrap from Lesson 07. The only choice is the destination: when the player exits one edge, it appears just off-screen on the opposite side so it slides in smoothly rather than popping into view already on-screen.

exit right → appear left
if x > SCREEN_W {
  x = -PLAYER_W
}
 
// just off the left edge
// slides in as player moves right
exit left → appear right
if x < -PLAYER_W {
  x = f32(SCREEN_W)
}
 
// just at the right edge
// slides in as player moves left

The vertical wrap from Lesson 07 stays unchanged — all four wrap conditions sit together after the position integration.

Integrate horizontal position

Exactly the same Euler step as vertical — this should feel familiar now:

odinplayer_x += player_vx * dt   // same as: player_y += player_vy * dt

Both axes integrate independently. X has no gravity (there is no horizontal gravity in Joust), so the velocity is set directly from input rather than accumulated.

Complete main.odin

odinpackage main

import rl "vendor:raylib"

SCREEN_W   :: 800
SCREEN_H   :: 600
GRAVITY    :: f32(800)
FLAP_FORCE :: f32(420)
MAX_FALL   :: f32(600)
MOVE_SPEED :: f32(200)
PLAYER_W   :: f32(40)
PLAYER_H   :: f32(60)

PLATFORMS :: [?]rl.Rectangle{
    {  0, 554, 280, 46},
    {520, 554, 280, 46},
    { 48, 426, 176, 18},
    {576, 426, 176, 18},
    {288, 316, 224, 18},
    {336, 186, 128, 18},
}

LAVA :: rl.Rectangle{280, 574, 240, 26}

main :: proc() {
    rl.InitWindow(SCREEN_W, SCREEN_H, "Joust")
    defer rl.CloseWindow()
    rl.SetTargetFPS(60)

    player_x:      f32 = 380
    player_y:      f32 = 256
    player_vx:     f32 = 0
    player_vy:     f32 = 0
    player_facing: f32 = 1

    for !rl.WindowShouldClose() {
        dt := rl.GetFrameTime()

        // horizontal input
        if rl.IsKeyDown(.Left) {
            player_vx     = -MOVE_SPEED
            player_facing = -1
        } else if rl.IsKeyDown(.Right) {
            player_vx     = MOVE_SPEED
            player_facing = 1
        } else {
            player_vx = 0
        }

        // vertical physics
        player_vy += GRAVITY * dt
        player_vy  = min(player_vy, MAX_FALL)
        if rl.IsKeyPressed(.Space) {
            player_vy -= FLAP_FORCE
        }

        // integrate
        player_x += player_vx * dt
        player_y += player_vy * dt

        // wrap all four edges
        if player_x > f32(SCREEN_W) { player_x = -PLAYER_W          }
        if player_x < -PLAYER_W    { player_x = f32(SCREEN_W)        }
        if player_y > f32(SCREEN_H) { player_y = -PLAYER_H           }
        if player_y < -PLAYER_H    { player_y = f32(SCREEN_H)        }

        // draw
        rl.BeginDrawing()

            rl.ClearBackground(rl.BLACK)

            rl.DrawRectangleGradientV(
                i32(LAVA.x), i32(LAVA.y),
                i32(LAVA.width), i32(LAVA.height),
                rl.RED, rl.ORANGE,
            )

            for plat in PLATFORMS {
                rl.DrawRectangleRec(plat, rl.DARKGRAY)
            }

            rl.DrawRectangle(
                i32(player_x), i32(player_y),
                i32(PLAYER_W), i32(PLAYER_H), rl.WHITE,
            )

            rl.DrawText("JOUST", 10, 10, 20, rl.YELLOW)
            rl.DrawText("SPACE flap  \xE2\x86\x90\xE2\x86\x92 move", 10, 34, 14, rl.GRAY)

        rl.EndDrawing()
    }
}

Check your understanding

1. Which raylib function returns true every frame a key is held down?

IsKeyDown — IsKeyHeld, KeyIsDown, and IsKeyFire are not raylib functions. Only IsKeyDown exists. The others sound plausible, which is exactly why they are worth ruling out: when you are reading unfamiliar API docs, recognising what is real versus what merely sounds familiar is a core skill.

2. Horizontal position integration each frame (same pattern as vertical):

x += vx * dt — same Euler step as y += vy * dt from Lesson 07. Velocity (pixels/s) times elapsed time (s) equals displacement (pixels). Division, addition, and subtraction all produce the wrong units.

3. When the player presses the left arrow, player_facing is set to:

-1 — the convention of ±1 for direction matches screen-space sign: positive X is rightward, negative X is leftward. Using ±1 means you can later multiply the sprite's draw width by player_facing to flip it — no special case needed. ±2 carries no useful meaning here.

4. When player_x < -PLAYER_W (flew off the left edge), set player_x to:

f32(SCREEN_W) — two things to get right: the dimension (W not H, because this is a horizontal wrap) and the type (f32 not i32, because player_x is f32 and Odin won't silently convert). The i32 variants would be compiler errors; the SCREEN_H variants would teleport the player to Y-coordinate 600 — completely wrong axis.
