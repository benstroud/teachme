Mission context

The Joust game loop is a for. The enemy AI is a switch. The lava check is an if. By the end of this lesson you can sketch the skeleton of the entire game.

if / else if / else

No parentheses around the condition — that is the only Odin-specific rule. Everything else is familiar:

odinif player.health <= 0 {
    player.alive = false
} else if player.health == 1 {
    flash_warning()
} else {
    // still fighting
}

An init statement can run before the condition. Variables declared there are scoped to the entire if/else chain — useful for avoiding a name that leaks into the surrounding scope:

odinif egg := find_nearest_egg(); egg != nil {
    collect(egg)
}

for — Odin's only loop

Odin has one loop keyword: for. It covers every loop pattern you know from other languages. No while, no do, no loop.

Infinite loop — the game loop

A bare for with no condition runs forever. This is how every game loop is structured:

odinmain :: proc() {
    // setup ...

    for {                          // runs until an explicit break
        update()
        draw()

        if should_quit() { break }
    }
}

Condition loop — the while form

Add a condition and you have a while loop:

odinfor game_running {
    update()
    draw()
}

C-style loop — counted iterations

Three-part form for when you need a counter. Note: Odin has no ++ operator — increment with i += 1:

odinfor i := 0; i < enemy_count; i += 1 {
    spawn_enemy(i)
}
Gotcha for C / Go / JS programmers Odin has no ++ or -- operators. Always write i += 1 and i -= 1.

Range over a slice

Iterate every element of an array or slice. Value comes first, index second — the opposite of Go:

odinfor enemy in enemies {
    update_enemy(enemy)
}

// With index — value first, index second
for enemy, i in enemies {
    fmt.println(i, enemy.x)
}

Integer range

Two range operators: ..< (exclusive upper bound) and ..= (inclusive). You will use ..< almost always:

odinfor i in 0..<5 {  // 0 1 2 3 4
    fmt.println(i)
}

for i in 0..=4 {  // 0 1 2 3 4 — same result, inclusive
    fmt.println(i)
}

break exits the loop. continue skips to the next iteration — use it to skip dead enemies without nesting:

odinfor enemy in enemies {
    if !enemy.alive { continue }  // skip dead ones
    update_enemy(enemy)
}

switch — the enemy state machine

Unlike C, switch in Odin does not fall through. Each case is independent — no break required. An empty case: is the default branch.

Here is the Joust enemy state machine. The .Flying shorthand works because the type can be inferred from the switch expression:

odinEnemyState :: enum { Flying, Egg, Hatching }

Enemy :: struct {
    x, y:  f32,
    state: EnemyState,
}

update_enemy :: proc(e: Enemy) {
    switch e.state {
    case .Flying:
        // patrol back and forth across platform
    case .Egg:
        // sit still; hatch timer ticking
    case .Hatching:
        // emerge animation; become a harder enemy
    case:
        // default — should never happen
    }
}

You can match multiple values in one case with a comma:

odinswitch e.state {
case .Egg, .Hatching:
    draw_egg(e)
case .Flying:
    draw_enemy(e)
}

A switch without an expression works as an if/else if chain — useful when conditions don't share a single value to switch on:

odinswitch {
case player.y > LAVA_Y:
    player_dies()
case player.y > SCREEN_H:
    player.y = 0
case:
    // normal flight
}

If you genuinely need a case to fall through, use the explicit fallthrough keyword at the end of the case body.

Check your understanding

1. How many distinct loop keywords does Odin have?

Just one: for. It covers every pattern — infinite, condition-only, C-style counted, range over slice, range over integers. There is no while, do, loop, or repeat in Odin.

2. Iterating a slice s binding each element to v and its index to i:

for v, i in s — value comes first, index second. This is the opposite of Go and a common gotcha. for i, v in s compiles but silently swaps what you think v and i are.

3. After a switch case body completes in Odin (no fallthrough):

Execution jumps to after the closing brace of the entire switch — no fallthrough, no break needed. This is the opposite of C. If you need the next case to also run, put fallthrough at the end of the case body explicitly.

4. In a switch e.state on an EnemyState enum, matching the .Egg value is written:

case .Egg: — the dot prefix is shorthand for the enum type name when it can be inferred from context (EnemyState.Egg also works but is verbose). "Egg" would be a string literal, when and type are not case keywords.
