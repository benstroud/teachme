Mission context

Every frame of Joust calls update_player, update_enemy, check_joust. These are the procedures you will write. This lesson covers the mechanics behind them — and by the end you will see the skeleton of the entire game loop.

Parameters and return types

You have seen the basic form. A quick recap with the full syntax, since the details matter:

odin// Single return type after ->
is_grounded :: proc(p: Player, ground_y: f32) -> bool {
    return p.y >= ground_y
}

// Consecutive params sharing a type — x, y: f32 instead of x: f32, y: f32
distance :: proc(x1, y1, x2, y2: f32) -> f32 {
    dx := x2 - x1
    dy := y2 - y1
    return math.sqrt(dx*dx + dy*dy)
}

Pointer parameters — how to mutate a struct

This is the most important concept in this lesson. Odin passes values by copy. If you pass a Player to a procedure and modify its fields, the original is unchanged. To mutate, pass a pointer.

Odin's pointer syntax uses ^ for the type and & for address-of — distinct symbols, distinct jobs:

SyntaxPositionMeaning
^Playertype"a pointer to a Player value"
&pexpression"take the address of p" — produces a ^Player
p^expression"dereference p" — produces the Player value

In practice you rarely need the explicit dereference p^. Field access auto-dereferences — p.x works whether p is a Player or a ^Player:

odin// Takes a pointer — can modify the original Player
update_player :: proc(p: ^Player, dt: f32) {
    p.vy  += GRAVITY * dt     // auto-deref: no p^.vy needed
    p.y   += p.vy * dt
    p.x   += p.vx * dt
}

// Caller takes address with &
player: Player
update_player(&player, dt)
Value vs pointer — the rule of thumb If the procedure reads but does not modify: pass by value (Player).
If the procedure modifies: pass by pointer (^Player).
In game code, update procedures almost always take pointers.

Multiple return values

Odin procedures can return any number of values. Wrap them in parentheses in the return type. The canonical Joust example — check_joust needs to return a result and whether a collision even happened:

odin// Returns: did they collide, and if so who won
check_joust :: proc(a, b: ^Enemy) -> (bool, bool) {
    colliding := rects_overlap(a.rect, b.rect)
    a_wins    := a.y < b.y                  // higher lance wins
    return colliding, a_wins
}

// Caller unpacks with multiple assignment
hit, a_wins := check_joust(&enemy_a, &enemy_b)
if hit {
    // resolve combat
}

Named return values

Name the returns to make intent clear. The names become local variables; a bare return sends them back:

odinspawn_position :: proc(wave: int) -> (x, y: f32) {
    x = f32(wave % 3) * 200 + 100
    y = 50
    return                          // returns x and y
}

sx, sy := spawn_position(2)

Use named returns when the meaning of each return value isn't obvious from the types alone — (x, y: f32) is far clearer than (f32, f32) for a position.

defer — the cleanup guarantee

defer schedules a statement to run when the enclosing scope exits — regardless of how it exits (normal return, early return, or error). It is the Odin idiom for pairing setup with teardown.

Multiple defers in the same scope run in reverse order — last declared, first executed.

Preview: the raylib game loop scaffold

This is the exact pattern you will write in Lesson 05. defer guarantees CloseWindow runs even if the game crashes during setup:

odinimport rl "vendor:raylib"

main :: proc() {
    rl.InitWindow(800, 600, "Joust")
    defer rl.CloseWindow()          // always runs when main returns

    rl.SetTargetFPS(60)

    for !rl.WindowShouldClose() {    // loop until × or Escape
        update()
        draw()
    }
}                                    // ← CloseWindow() fires here

The import alias rl shortens every raylib call. This is the pattern the Odin community uses — you will see it everywhere.

The Joust skeleton

With four lessons of Odin behind you, here is what the skeleton of the game looks like. Nothing in here is new — it is just the pieces assembled:

odinpackage main

import rl "vendor:raylib"

EnemyState :: enum { Flying, Egg, Hatching }

Entity :: struct {
    x, y:   f32,
    vx, vy: f32,
    alive:  bool,
}

Enemy :: struct {
    using entity: Entity,    // inherit Entity fields directly
    state: EnemyState,
}

update_player :: proc(p: ^Entity, dt: f32) { /* gravity, input */ }
update_enemy  :: proc(e: ^Enemy,  dt: f32) { /* state machine */ }

main :: proc() {
    rl.InitWindow(800, 600, "Joust")
    defer rl.CloseWindow()

    player: Entity
    enemies: [8]Enemy

    for !rl.WindowShouldClose() {
        dt := rl.GetFrameTime()

        update_player(&player, dt)
        for &e in enemies { update_enemy(&e, dt) }
    }
}

One new thing here: for &e in enemies — the & in a range loop gives you a pointer to each element rather than a copy, so modifications stick. And using embeds one struct's fields into another — Enemy gets x, y, alive directly. You do not need to memorise these now; they will appear naturally in Lesson 05.

Check your understanding

1. Which is the correct Odin type for "a pointer to a Player"?

^Player — Odin uses ^ for pointer types (borrowed from Pascal). *Player is C/Go syntax and won't compile. &Player looks like a C++ reference; in Odin, & is the address-of operator used in expressions, not a type sigil. @Player is not valid Odin.

2. To pass a Player variable p as a ^Player parameter, you write:

&p takes the address of p, yielding a ^Player. In Odin, ^ used as a prefix in expressions is not the address-of operator — it is the postfix dereference: p^ reads the value a pointer points to. *p is C syntax and won't compile.

3. A procedure returning two f32 values (x and y) declares its return type as:

Multiple return values are wrapped in parentheses: -> (f32, f32). Square brackets are for arrays, curly braces for struct literals, and angle brackets are not valid return-type syntax in Odin.

4. When multiple defer statements exist in one scope, they execute in:

Reverse order — LIFO (last declared, first executed). If you defer CloseWindow() then defer UnloadTexture(t), the texture is unloaded first and the window is closed second. This matches the natural "undo in reverse" teardown pattern.
