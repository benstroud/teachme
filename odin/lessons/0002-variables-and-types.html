Variables & Types

Declaration syntax, the numeric tower, and structs as game entities

← Lesson 01: Hello, Odin

Mission context

Every game object — player position, velocity, health, alive state — is a struct. Every smooth movement calculation uses f32. This lesson is the vocabulary you will reach for every time you write game logic.

Three ways to declare a variable

Odin has distinct syntax for each combination of "do I know the type?" and "do I have an initial value?"

odin// 1. Inferred type — most common in practice
score  := 0
speed  := 2.5
alive  := true

// 2. Explicit type with initial value — when inference picks the wrong type
x: f32 = 0       // without the f32, Odin infers f64 for 0.0 and int for 0
health: i32 = 100

// 3. Type only — zero-initialised, no explicit value required
frame_count: int   // guaranteed to be 0
is_paused:   bool  // guaranteed to be false

Unlike C, Odin zero-initialises everything by default. A declared variable with no value is always safe to read — it will be 0, false, or "" depending on its type. This eliminates an entire class of bugs.

Footnote: uninitialized memory Odin does provide --- to opt into uninitialized memory (x: int = ---), which skips the zero-write for performance. You will not need it until you are optimizing hot paths. Ignore it for now.

And a reminder from Lesson 01 — the fourth form is a constant, not a variable. It cannot be reassigned:

odinGRAVITY :: 9.8        // compile-time constant — immutable forever
TILE_SIZE :: 32       // cannot be changed at runtime

Numeric types — what you will actually use

Odin's numeric tower is large, but in practice four types cover nearly all game programming:

TypeSizeUse for
f32 32-bit float Position, velocity, angle, lerp — anything that needs decimals. raylib's API is built around f32.
int pointer-width (64-bit on modern machines) Loop counters, array indices, counts. The default integer.
i32 32-bit signed When you need to match a C API or cap memory use. Common in file formats.
bool 8-bit Flags — is_alive, is_grounded, game_over.

Important: int is pointer-sized, not always 32-bit. On a 64-bit machine it is 64 bits. This matters if you are reading binary formats or passing sizes to C APIs — use i32 explicitly in those cases.

No implicit conversions — ever

This will bite you. Odin never silently converts between numeric types. Mixing f32 and int in an expression is a compile error:

odinframe: int = 60
delta: f32 = 1.0 / frame   // ✗ compile error: cannot mix f32 and int

Convert explicitly using TargetType(value):

odinframe: int = 60
delta: f32 = 1.0 / f32(frame)  // ✓ explicit cast

speed: f32 = 3.7
tiles: int = int(speed)         // ✓ truncates — 3

The conversion syntax is Type(value), just like a procedure call. There is no cast keyword required for basic numeric conversions.

Structs — modelling game entities

Structs are declared as constants with :: (they are compile-time type definitions). Fields can share a type by listing names with a comma:

odinPlayer :: struct {
    x, y:   f32,    // position
    vx, vy: f32,    // velocity
    health: int,
    alive:  bool,
}

To create a value, use a struct literal with curly braces. You can initialise positionally or by name:

odin// Named fields — preferred: order doesn't matter, omitted fields are zero
p := Player{x = 100, y = 200, health = 3, alive = true}

// Positional — must match field declaration order exactly
p2 := Player{100, 200, 0, 0, 3, true}

// Zero-initialised — all fields are 0 / false
p3: Player
p4 := Player{}   // equivalent

Access fields with .. If you have a pointer to a struct, Odin auto-dereferences — no ->:

odinp := Player{x = 10, health = 3, alive = true}
p.x += 2.5        // direct access

ptr := &p
ptr.health -= 1   // pointer field access — no -> needed

Named init is strongly preferred in practice: it documents intent, survives field reordering, and leaves unspecified fields at their zero value rather than requiring you to fill every position.

Check your understanding

1. Which declares a zero-initialised, mutable int named hp without providing an explicit value?

hp: int declares a mutable variable of type int, zero-initialised by the compiler guarantee (no value needed). hp := 0 is also valid but provides an explicit value. hp :: 0 declares a constant — immutable. hp =: 0 is not valid Odin syntax.

2. Which expression converts an int variable n to the f32 type?

In Odin, Type(value) is the conversion syntax. f32(n) converts n to a 32-bit float. f64(n) converts to a 64-bit float (too wide for most raylib calls). int(n) is a no-op (already int). u32(n) converts to an unsigned 32-bit integer — different type entirely.

3. Given Vec2 :: struct { x, y: f32 }, which initialises a value at point (1, 2)?

Struct literals in Odin use curly braces: Vec2{1, 2}. Parentheses are for procedure calls. Square brackets are for array indexing. Angle brackets are not valid Odin syntax (no generics in the angle-bracket sense).

4. For a game object's x position (sub-pixel movement, used with raylib), the best type is:

f32 is correct for three reasons: positions are fractional (smooth movement requires decimals), f32 has more than enough precision for screen coordinates, and raylib's entire API is built around f32 — using f64 would require constant downcasting. int and i32 can't represent fractions.
