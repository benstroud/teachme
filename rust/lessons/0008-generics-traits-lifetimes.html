Generics, Traits & Lifetimes

Write code that works across types, define shared behavior, and keep references valid.

The mental model in one sentence

Generics abstract over types, traits define shared behavior ("an interface"), and lifetimes tell the compiler how references relate so they stay valid.1

Generics: one function, many types

fn largest<T>(list: &[T]) -> &T {
    let mut max = &list[0];
    for item in list {
        if item > max { max = item; }
    }
    max
}

<T> is a placeholder type. You've already used generics: Vec<T>, Option<T>, Result<T, E>.1 (This example actually needs T: PartialOrd — see traits below.)

Traits: shared behavior

trait Shape {
    fn area(&self) -> f64;
}

struct Circle { r: f64 }
impl Shape for Circle {
    fn area(&self) -> f64 { 3.14159 * self.r * self.r }
}

A trait declares methods a type must implement, letting different types share an interface.1

Combine with bounds to constrain generics:

fn biggest<T: PartialOrd + Copy>(list: &[T]) -> T { ... }

Common std traits: Copy, Clone, Debug (for {:?}), Display (for {}), and PartialOrd/Ord for comparisons.

Lifetimes: keep references valid

fn first_word<'a>(s: &'a str) -> &'a str {
    s.split_whitespace().next().unwrap_or("")
}

The 'a annotation says "the returned reference is valid as long as the input s is" — so the compiler can prove no dangling reference.1

Lifetimes appear when a function returns a reference tied to a parameter. Structs that hold references also need one: struct User<'a> { name: &'a str }.

The three in combination

Generics make code type-flexible; trait bounds constrain which types are allowed (so largest only works on orderable, copyable types); lifetimes ensure any references involved are safe. Together they're how Rust stays safe and reusable.

Key idea If ownership is what makes Rust memory-safe, traits are what make it expressive: they let you say "this generic thing must support these operations," turning compile-time safety into a breadcrumbs of capabilities.
