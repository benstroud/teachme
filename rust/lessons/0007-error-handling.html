Error Handling

No exceptions. Instead: Result for recoverable errors and panic! for the unrecoverable.

The mental model in one sentence

Rust splits errors into recoverable (returned as Result<T, E>) and unrecoverable (signalled by panic!) — and usually requires you to handle the recoverable kind before the code compiles.1

Recoverable errors: Result<T, E>

use std::fs::File;

let f_result = File::open("hello.txt");
// match is exhaustive:
match f_result {
    Ok(file)   => println!("opened {file:?}"),
    Err(error) => println!("failed: {error}"),
}

Ok(T) carries success, Err(E) the error.1

Propagating with ?

use std::fs::File;
use std::io::{self, Read};

fn read_username() -> Result<String, io::Error> {
    let mut f = File::open("user.txt")?;   // Err is returned early
    let mut s = String::new();
    f.read_to_string(&mut s)?;
    Ok(s)
}

? unwraps Ok or returns the Err from the enclosing Result function — the clean way to bubble errors up.2

unwrap and expect

let f = File::open("x.txt").expect("missing x.txt"); // panic w/ message
let g = File::open("y.txt").unwrap();                 // panic, no message

Both extract the value or panic. Fine for prototypes and cases where failure truly means a bug; in library code, prefer propagating with ?.

Unrecoverable: panic!

panic!("this is unrecoverable");   // stops the program

panic! halts execution — appropriate for bugs like indexing out of range, not for expected outcomes like "file not found" that callers should handle.

Deciding recoverable vs unrecoverable

  • Expected, retryable, or user-facing problems → Result.
  • Invariants broken / code that can't continue correctly → panic!.1
Key idea The absence of exceptions means error handling is explicit. A function that might fail says so in its return type, and callers must acknowledge it — no silent, catch-less failures.
