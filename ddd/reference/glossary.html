Glossary

Terms as this set uses them. Each entry names the lessons where it appears. Definitions are the author's summaries of the book, to be checked against the chapters.

Strategy and language

Ubiquitous language
The shared vocabulary of a team, used in conversation, documents, diagrams, and code. Where words disagree, the model is wrong. Lessons 1, 2.
Bounded context
The boundary within which one model applies and the ubiquitous language has one meaning. Usually drawn where the language changes. Lesson 9.
Context map
A picture of the bounded contexts and the relationships between them, such as shared kernel, customer/supplier, conformist, or anticorruption layer. Lesson 9.
Core domain
The part of the domain that makes the business distinctive. It gets the best modelling. Lesson 10.
Generic subdomain
A problem many businesses share. Adopt an existing solution rather than modelling it in depth. Lesson 10.
Supporting subdomain
Necessary for the business and specific to it, but not a differentiator. Keep it simple and replaceable. Lesson 10.

Building blocks

Entity
An object defined by an identity that persists through change of its attributes. Lesson 5.
Value object
An object defined only by its attributes, with no identity of its own. Should be immutable. Lesson 5.
Domain service
An operation that is part of the model but belongs to no single entity or value. Named in the domain's terms. Lesson 5.
Module
A group of related concepts under a name the business would recognise. Generic names such as utils are a warning. Lesson 5.
Aggregate
A cluster of domain objects treated as one unit, with a root that outside code references. Holds the invariants. Transactions do not cross aggregate boundaries. Lesson 6.
Factory
Creates an aggregate or entity in a valid state, when creation is more complicated than a constructor call. Lesson 6.
Repository
Gives the application access to aggregates as if they were in a collection, hiding how they are stored. Lesson 6.
Specification
A named predicate that states whether an object satisfies a condition. The value is the name. Lesson 7.

Design quality and refactoring

Anemic domain model
Objects that hold data while their rules sit in services. An anti-pattern, because it loses the benefits of a domain model. Lesson 4.
Layered architecture
The domain layer depends on nothing outside itself. Interface, application, and infrastructure layers sit around it. Lesson 4.
Breakthrough
A sudden, deeper insight into the domain that lets the model and code be reshaped into something simpler and more accurate. Lesson 7.
Implicit concept
A concept the code uses, often as a repeated condition or a pair of values that travel together, without naming it. Lesson 7.
Intention-revealing interface
A name that says what an operation means for the business, not how it changes the data. Lesson 8.
Side-effect-free function
A query that returns a value and changes no state, so it can be called freely. Lesson 8.
Supple design
A design developers can combine and change without fear. Built from intention-revealing interfaces, side-effect-free functions, assertions, and closed operations. Lesson 8.
