Making Concepts Explicit

Some of the most important ideas in a domain are never named. They hide in conditions, in comments, and in arguments passed around. Part III starts by finding them, naming them, and giving them a place in the model.

Refactoring toward deeper insight

Part III of the book, Refactoring Toward Deeper Insight, begins with the idea of a breakthrough: a moment when the team sees a simpler, more accurate model, and the code can be reshaped around it.1 The later chapter on making implicit concepts explicit describes how such breakthroughs are prepared: the team looks for concepts the code is already using without naming.

Signs of an implicit concept

  • A condition repeats in several places, such as if (order.total > 1000 && order.customer.isNew).
  • A comment explains a rule that the code does not enforce.
  • A pair of values always travels together, such as an amount and a currency, or a start and an end.
  • A method is hard to name, because the concept it implements has no name yet.

Worked example: the implicit rule

Suppose a condition appears in three places:

if (order.total > 1000 && order.customer.isNew) { requireApproval(order); }

The rule is "a large first order needs approval". It has a business name, and the code does not use it. Making it explicit means giving the concept a home:

class Order {
  requiresApproval(): boolean {
    return this.total() > 1000 && this.customer.isNew();
  }
}
// The three call sites now read: if (order.requiresApproval()) { ... }

The condition is now in one place, has a name the business recognises, and can be tested. The model is the same, but it is more honest about what it knows.

Specifications When a rule must be checked on its own, or combined with others, Evans describes a specification: a named predicate that says whether an object satisfies a condition. The useful part is the name, not the mechanism.

Your task (one attempt)

  1. Find a repeated condition in code you know. Write down the business rule it encodes, in one sentence.
  2. Name the concept. Say whether it belongs on an existing object, a value object, or a new service, and why.
  3. Rewrite the call sites to use the new name. Say which test you would write first, and what would fail if someone changed the rule.

Check yourself

Which sign most clearly points to an implicit concept?

A repeated business condition is the clearest sign of a concept the code uses but never names.

What is the benefit of naming the "large first order" rule as a method?

A named concept gives the rule one home and a name the team shares. It does not change performance, and it still needs tests.

What does "breakthrough" describe in Part III?

In the book, a breakthrough is a deeper understanding of the domain that makes the design simpler and more accurate, and the code follows it.1
