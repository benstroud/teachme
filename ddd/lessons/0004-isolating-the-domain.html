Isolating the Domain

The business rules should not depend on the screen, the database, or the framework. Keeping them apart is what lets the model stay readable, and it is also where anemic models come from when the separation is done badly.

Why separate the domain

Evans's chapter Isolating the Domain begins Part II, which covers the building blocks of a model-driven design. Its concern is that domain logic gets tangled with everything around it: request handling, SQL, serialisation, and UI state. Once that happens, the model cannot be read on its own, and changing the database can silently change a business rule.1

The usual remedy is layering. The domain layer holds the model. Layers above it handle the user interface and the application's workflow. Layers below it handle storage and external services. The domain layer depends on nothing outside itself.

A layered view

LayerHoldsMust not hold
User interfaceScreens, request parsing, view modelsBusiness rules such as "a claim can only be paid once"
ApplicationUse cases that coordinate steps, such as "approve and pay"The rules themselves
DomainEntities, value objects, rules, domain servicesSQL, HTTP, framework decorators, logging calls
InfrastructureDatabase adapters, message clients, file accessDecisions about what the business allows

The anemic model warning

Isolation done badly produces an anemic model. The objects become bags of data with getters and setters, and every rule moves into services that operate on them. Fowler describes this as an anti-pattern. The objects look like a domain model, but they carry none of its benefits, and the mapping to the database often becomes the main cost.2

Fowler's concern is about where the behaviour sits. A thin service layer that coordinates work is fine. A service that holds most of the rules has pulled them away from the objects that should own them, and he warns that this drifts toward transaction scripts.2

// Anemic: data on the object, rules in a service
class Invoice { total = 0; paid = false; }
class InvoiceService {
  pay(invoice: Invoice) { invoice.paid = true; }
}

// Richer: the object owns the rule it enforces
class Invoice {
  private paid = false;
  constructor(private readonly total: number) {}
  pay(): void {
    if (this.paid) throw new Error("Invoice already paid");
    this.paid = true;
  }
}
Thin services are fine The problem is not that services exist. Application services that orchestrate a use case belong in the application layer. The warning is about domain rules that live in services instead of in the objects that the rules are about.

Your task (one attempt)

  1. Take a feature in code you know. Mark each line as UI, application, domain, or infrastructure.
  2. Find one domain rule that sits in the wrong layer. Move it, in your head or in a sketch, to the object it belongs to.
  3. Say what you would have to change to test that rule without a database. Write the test's first line.

Check yourself

Which of these belongs in the domain layer, according to this lesson?

The business rule belongs in the domain. SQL, HTTP parsing, and logging belong to infrastructure or the interface layers.

What is the main warning about an anemic domain model?

Fowler's point is that behaviour pulled out of the objects into services costs the model its benefits, and tends toward transaction scripts.2

Why does isolating the domain help testing?

When the domain depends on nothing outside itself, its rules can be exercised directly, which is the practical gain of the separation.
