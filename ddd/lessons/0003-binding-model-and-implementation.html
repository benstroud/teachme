Binding Model and Implementation

A model that lives only on a whiteboard drifts from the code within weeks. Evans's point in Part I is that the model and the implementation must be bound together, so each change to one shows up in the other.

The drift problem

Teams often build a model, write code, and then forget the model. The code grows its own structure, the diagrams go out of date, and the words in the meetings stop matching the words in the code. Evans's third chapter in Part I, Binding Model and Implementation, argues against that split: the code should be a faithful expression of the model, and the model should be refined by what the code reveals.1

The loop

The practice the book describes is a cycle. A developer and an expert explore a concept together. They express it in code. Writing the code exposes a contradiction or a gap. The team goes back to the model, refines it, and the code changes to match. Each pass makes the model more accurate, and the code more honest about the domain.

StepWhat happensSmell when it fails
ExploreDevelopers and experts talk through a ruleDevelopers guess the rule and never check it
ExpressThe rule becomes a class, method, or testThe rule lives in a comment, not in code
ExposeWriting the code finds a contradictionContradictions are patched with flags and exceptions
RefineThe model changes, and the code followsThe model changes, but the code is left as it was
Why the code must be the model A model that is not in the code cannot be tested, checked, or enforced. The code is the only part of the model that runs every day, so it is where the model earns its keep.

A small example of binding

Suppose the expert says: "A claim can only be paid once, and only after a surveyor approves it." A drifted implementation stores a status string and lets any function change it. A bound implementation has a method that refuses the second payment, and a test that states the surveyor rule. The difference shows up the first time a new developer changes the flow.

class Claim {
  private paid = false;
  private surveyorApproved = false;

  approveBySurveyor(): void {
    this.surveyorApproved = true;
  }

  pay(): void {
    if (!this.surveyorApproved) {
      throw new Error("A claim needs surveyor approval before payment");
    }
    if (this.paid) {
      throw new Error("A claim can only be paid once");
    }
    this.paid = true;
  }
}

The rule is now in one place, named after the domain, and it fails loudly. That is the binding Evans means.

Your task (one attempt)

  1. Find one rule in a system you know that lives in a comment, a spreadsheet, or someone's memory. Write it as one sentence in the domain's words.
  2. Predict where in the code the rule would best live, and which class or function should own it.
  3. Write a short test, in any language, that would fail if someone broke the rule. Say which part of the loop the test helps with.

Check yourself

What does the binding loop describe?

The loop runs in both directions. The code tests the model, and the model improves the code. Neither is finished first.1

In the claim example, why is the "paid once" rule better as a method than a status string?

The rule is in one place, named after the domain, and it refuses the invalid action. A status string lets any caller set the state without checking the rule.

Which sign means the model and the implementation have drifted apart?

Rules living in comments and out-of-date diagrams are the sign of drift. The other three are the binding working as intended.
