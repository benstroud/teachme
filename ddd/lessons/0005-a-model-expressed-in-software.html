Lesson 5 of 10Domain-Driven Design

A Model Expressed in Software

Entities, value objects, services, and modules are the building blocks Evans uses to put a model into code. Each one answers a question about identity, equality, or responsibility.

The building blocks

Part II of the book turns from the principle to the parts. The chapter A Model Expressed in Software describes the main patterns a team uses to write a model in code: entities, value objects, services, and modules.1 The choice between them is a question about what the object is.

Building blockAsk yourselfExample
EntityIs it the same thing over time, even as its attributes change?A customer who changes address is still the same customer
Value objectIs it defined only by its attributes, and can it be replaced freely?A money amount of 10 GBP, or an address
ServiceIs it an operation that belongs to no single object?Transferring money between two accounts
ModuleDoes this group of concepts make sense together and carry a domain name?A "billing" module, not a "utils" module

Entities: identity matters

An entity has an identity that persists through change. Two claim records with the same fields but different identifiers are two different claims. Make the identity explicit in code, and compare entities by it.

Value objects: the attributes are the thing

A value object has no identity of its own. Two money values of the same amount and currency are equal, and you can replace one with another. Value objects should be immutable, so any operation returns a new value rather than changing the old one. This also removes a whole class of bugs where a shared object changes under someone else.

class Money {
  constructor(readonly amount: number, readonly currency: string) {
    if (amount < 0) throw new Error("Money cannot be negative");
  }
  add(other: Money): Money {
    if (other.currency !== this.currency) throw new Error("Currency mismatch");
    return new Money(this.amount + other.amount, this.currency);
  }
  equals(other: Money): boolean {
    return this.amount === other.amount && this.currency === other.currency;
  }
}

Services and modules

A domain service is an operation that is part of the model but does not naturally belong to one entity or value. Keep it named in the domain's terms. A module groups related concepts under a name the business would recognise. Module names such as utils or helpers are a warning that no concept lives there.

Entity or value object? When in doubt, ask whether two instances with identical attributes should be treated as the same. If yes, a value object. If the business tracks each one separately, an entity.

Your task (one attempt)

  1. From the Money example, add a subtract method. Decide what it should do if the result is negative, and say which rule it enforces.
  2. Take three objects from a system you know. Label each as entity, value object, service, or module, and give one reason for each label.
  3. Find one object you labelled as an entity that you could make a value object. Say what the business would lose if you did.

Check yourself

Two address records have identical fields. Which building block fits an address that needs no identity of its own?

A value object is defined by its attributes. Two equal addresses are interchangeable, so no identity is needed.

Why should a value object such as Money return a new value instead of changing itself?

Immutability stops a shared value from changing unexpectedly. Operations return a new value, so each holder keeps the value it was given.

Which module name best follows this lesson's advice?

A module should carry a name the business would recognise. Generic names such as utils, helpers, or common suggest that no concept lives there.
