Lesson 6 of 10Domain-Driven Design

Aggregates, Factories, Repositories

Objects change over time, and their rules must hold at every step. Aggregates draw the boundary for consistency, factories create valid objects, and repositories give them back without leaking storage into the model.

The life cycle

Part II's chapter The Life Cycle of a Domain Object covers how objects are created, changed, stored, and removed while keeping the model's rules intact.1 Three patterns carry most of that work: aggregates, factories, and repositories.

Aggregates

An aggregate is a cluster of domain objects that can be treated as a single unit. It has one root, and references from outside the aggregate go only to that root. Fowler's summary makes two points that matter in practice: outside code should hold only the root, and transactions should not cross aggregate boundaries.2

The aggregate is where the invariants live. An order and its line items form one aggregate if the rule "the total equals the sum of the lines" must always hold. Outside code cannot add a line that bypasses the total, because the only way in is through the root.

class Order {
  private lines: { sku: string; amount: number }[] = [];

  addLine(sku: string, amount: number): void {
    if (amount <= 0) throw new Error("A line needs a positive amount");
    this.lines.push({ sku, amount });
  }

  total(): number {
    return this.lines.reduce((sum, line) => sum + line.amount, 0);
  }
}
// Outside code holds an Order, never a bare line. The total cannot drift.
Not a collection class Fowler warns that an aggregate is sometimes confused with a generic collection. An aggregate is a domain concept, such as an order or a clinic visit. A collection is a generic container, and it has no rules of its own.2

Factories

A factory creates an aggregate or an entity in a valid state. When creation is complicated, the factory holds the rules for it, so callers cannot build a half-formed object. A factory is worth its cost when creating the object takes more than a constructor call can express.

Repositories

A repository gives the application access to aggregates as if they were in a collection. Callers ask for an order by its identifier and save it back. The storage details, such as SQL or a document store, sit behind the repository's interface, so the model does not depend on them.

interface OrderRepository {
  findById(id: string): Promise<Order | undefined>;
  save(order: Order): Promise<void>;
}

Check yourself

What does Fowler say about transactions and aggregates?

Fowler's summary says transactions should not cross aggregate boundaries. The aggregate is the unit of consistency.2

Outside code only holds the order root, never a line item. Why?

Routing all changes through the root is how the aggregate enforces its rules. A bypassed line could break the total.2

What is the job of a repository in this lesson?

A repository provides access to aggregates as a collection-like interface, so storage stays outside the model.1
