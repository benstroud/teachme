The Schema Design Process

A repeatable method: identify the workload, map relationships, apply patterns, create indexes.

The mental model in one sentence

MongoDB's schema design is a four-step process — identify the workload, map relationships, apply patterns, create indexes — so you design for the app's actual operations, not from intuition.1

Step 1 — Identify the workload

List the operations your app runs most, their frequency, and what they touch. MongoDB recommends a workload table:2

ActionTypeInformationFrequencyPriority
View an articleReadid, text, comments1,000,000/dayHigh
Submit a commentWriteuser, text1,000/dayMedium
View analyticsReadid, clicks10/hourLow

Frequently-run operations deserve the optimized shape and an index; the frequent read is what tells you what to embed.2

Step 2 — Map relationships

For each relationship decide embed or reference (Lesson 2), yielding document shapes that serve the reads (Lesson 3).1

Step 3 — Apply design patterns

Reach for established patterns to optimize specific reads/writes:3

  • Computed values — precompute totals so results are ready at read time.
  • Group / bucket — group data into series and account for outliers.
  • Polymorphic — variable fields/types in one collection.
  • Schema versioning — coexist old/new shapes during rollout.
  • Archive — move old data out of the hot working set.
  • Single collection — reference to group related doc types.

Step 4 — Create indexes

Support the frequent query patterns from step 1 with indexes (e.g. an index on the field used by the high-frequency read). Indexes are a deliverable of the design, not an afterthought.1

Design, don't drift

The flexible model lets you change the schema later — but change at production scale is costly. Plan early, keep a simple schema to start, and optimize deliberately.4

Key idea The workload table is the anchor. Every later choice — embed or reference, which index, which pattern — should trace back to a row in that table.
