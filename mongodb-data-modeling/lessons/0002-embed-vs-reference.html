Embed vs Reference

The decision that decides everything else. Learn the triggers that push you one way or the other.

The mental model in one sentence

Embed related data when you read it together and keep it together; use references when the related data is large, unbounded, independently queried, or written at different times.12

Embed: denormalized, fast, atomic

An embedded model copies related data into one document. It's denormalized — the same value may appear in several documents — and in return you get:

  • Reads served in a single database operation.1
  • Related data updated in a single atomic write.1
  • Simpler code: no join, no second query.
// embed a "contains" relationship
{ _id: 1, customerId: 55, items: [ { sku: "pen", qty: 3 }, ... ] }

Reference: normalized, no duplication

A reference model splits related data into separate collections and links them (often by storing the other document's _id). It's normalized — the source of truth lives once — and you resolve it with an application join or a query.

// reference the "many" that can exist on its own
order:  { _id: 10, customerId: 55, total: 40 }
customer: { _id: 55, email: "ada@x.dev" }   // referenced, not duplicated

The decision table (memorize this)

MongoDB's own guidance:3

ScenarioLinking method
Keeping related data together simplifies model and codeEmbed
"Has-a" / "contains" relationshipEmbed
Application reads the pieces togetherEmbed
Data is updated togetherEmbed
Data is archived togetherEmbed
Child side has high cardinality / unboundedReference
Duplication is too costly to manageReference
Combined size is too large / too much bandwidthReference
Embedded data grows without boundReference
Write-heavy, data written at different timesReference
Child can exist without its parentReference

The hidden tension

Embedding "rolls up" the many into the one. That's great for one big read and atomic updates, but every change to the many (say, editing a shared author's name) means updating every document that embeds it. When related data changes often and is shared, references keep the duplication manageable.23

Key idea Ask two questions per relationship: do I read the child with the parent? (embed) and does the child grow without bound or stand alone / mutate often? (reference). The answers are usually one-sided.
