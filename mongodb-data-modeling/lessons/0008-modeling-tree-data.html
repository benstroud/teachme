Modeling Tree Data

Hierarchies have five documented shapes in MongoDB — pick the one that matches the queries.

The mental model in one sentence

MongoDB documents five tree models — parent references, child references, ancestors array, materialized paths, and nested sets — each trading read simplicity against write cost.1

The five patterns

// 1. Parent references — each node stores its parent _id
{ _id: "Electronics", parent: null }
{ _id: "Computers",   parent: "Electronics" }

// 2. Child references — each node stores its children _id array
{ _id: "Catalog", children: ["Electronics", "Books"] }

// 3. Ancestors array — each node stores all ancestors
{ _id: "Laptops", parent: "Computers",
  ancestors: ["Electronics", "Computers"] }

// 4. Materialized paths — each node stores the path string
{ _id: "Laptops", path: "Electronics,Computers,Laptops" }

// 5. Nested sets — left/right numbers enclose a subtree
{ _id: "Electronics", left: 1, right: 8 }

Which query shapes each serves

PatternBest when you…Weakness
Parent references…query immediate parent / childrenWhole-subtree reads need many steps
Child references…get a node's direct children fastDeep/subtree walks are multiple queries
Ancestors array…need all ancestors or descendants of a nodeMaintain the array on each insert
Materialized paths…want subtrees by a path-prefix regexRegex query, path must be maintained
Nested sets…read subtrees extremely fastReordering moves many nodes (low mutability)

Reading a subtree, pattern by pattern

  • Ancestors array: find all descendants of "Electronics" with { ancestors: "Electronics" } — one query, an entry-class use of an array of references.
  • Materialized paths: find a subtree with a prefix regex on the path field.
  • Nested sets: every node with left/right inside the parent's range — a single range query.1

Choose based on the dominant operation: frequent "give me this whole subtree" leans to ancestors array or nested sets; light parent-child browsing favors the simple reference patterns. Nested sets famously "optimize discovering subtrees at the expense of tree mutability."1

Key idea Trees are the one case where a pure "embed vs reference" instinct is too blunt. Name the real query ("parent-child?" "whole subtree?") and pick the pattern that answers it in one cheap read without making writes painful.
