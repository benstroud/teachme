Lesson 1 of 9MongoDB Data Modeling

Why Data Modeling

The document model rewards a different instinct than a relational one: design for how your app reads and writes.

The mental model in one sentence

MongoDB has a flexible document model: documents in a collection don't have to share fields, and a field's type can differ between documents. So a data model isn't "normalize the tables" — it's "arrange data so one document holds everything the app needs in one trip."1

Document vs relational: what changes

Relational behaviorDocument behavior
Schema fixed before you insert; planning-heavy.Schema evolves as the app evolves.
You often join tables to reassemble related data.You store related data together so reads need no join.1
Universal normal forms guide the design.Your application's read/write patterns guide the design.

This is the single idea that undoes SQL habits: data accessed together should be stored together.1

A concrete shift: embedding instead of a join

Say an app shows a patron and both their addresses on one page. A relational model puts addresses in a separate table and joins. A document model puts them inside the patron, so one query returns the whole page:

// relational habit: patrons table + addresses table, JOIN
// document habit:  one document, addresses embedded
{
  _id: "joe",
  name: "Joe Bookreader",
  addresses: [
    { street: "123 Fake Street", city: "Faketon", state: "MA" },
    { street: "1 Some Other Street", city: "Boston", state: "MA" }
  ]
}

The same document, read once, gives the app everything for that page.2

Why this earns senior attention

  • Fewer round trips. A well-modeled document serves a page in one read instead of a query plus joins (or a second query for the array-of-ids).
  • Atomic updates. Because related data is in one document, an update to it is a single atomic write.2
  • Fewer indexes/loads. Rolling related small documents up means fewer documents and fewer index entries (Lesson 2 discusses the flip side).
Key idea Before writing a single document, answer two questions about the app: what does it read together? and what does it write together? Those two answers drive the whole model.
