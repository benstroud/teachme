Schema Versioning & Evolution

The flexible model lets you change shape over time — do it without breaking the running app.

The mental model in one sentence

MongoDB's flexible schema means you can evolve a model in production; the safe way is an additive, backward-compatible change that you roll out across old and new documents with a version marker.1

Prefer additive, backward-compatible changes

The least risky evolution is one that old documents and old code still understand:

  • Add a new field with a default — old reads ignore it, new reads use it.
  • Don't rename or retype a field that's in production unless you migrate readers too.
  • Keep the old shape readable while the app rolls forward.
// additive: new field with a default for existing docs
db.orders.updateMany({}, { $set: { discount: 0 } })

The schema-versioning pattern

Store a version marker so both old and new documents can coexist and code can route by shape:1

// v1 document
{ _id: 1, schema_version: 1, title: "A", author: "ada" }

// v2 document (additive: releaseDate added, defaulted on old)
{ _id: 2, schema_version: 2, title: "B", author: "ada",
  releaseDate: ISODate("2026-09-01") }
// read-time: route by version
if (doc.schema_version <= 1) { /* old behavior */ }
else { /* new behavior */ }

The version field is itself a schema-design pattern; it makes the rollout of a new shape explicit and testable.2

Rolling forward: reads before writes

  1. Deploy code that reads both shapes.
  2. Write new documents in the new shape; add the version marker.
  3. Backfill existing documents (a script or aggregation) with defaults.
  4. Once no old documents remain, the old shape can be retired.

Know when to reference instead

If the "evolution" is really unbounded growth (an array that keeps expanding) or data being split into a separate entity, that's a modeling change — the schema versioning pattern handles shape evolution, while the 16 MiB/atomicity rules (Lesson 4) tell you when to split into a reference.

Key idea A schema migration in MongoDB is mostly additive and cheap. Keep the version marker and the read-both pattern so you can change shape on a live system without a coordinated multi-service outage.
