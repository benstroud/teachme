Putting It Together

A full modeled app, an explicit anti-pattern pass, and the senior design reflex.

The mental model in one sentence

Model a real feature end-to-end: start from its workload, choose embed-or-reference per relationship, honor the 16 MiB and atomicity rules, lock it with validation, and sweep for anti-patterns.

Example: an e-commerce checkout

Workload: place an order (write total + line items together, high); view an order (read everything, high); manage inventory per SKU (many admins, independently).

// order: line items embedded (bounded, co-read, atomic update)
{ _id: ObjectId(), schema_version: 1,
  customerId: 55,
  items: [ { sku: "pen", qty: 3, price: 2.00 },
           { sku: "pad", qty: 1, price: 5.00 } ],
  total: 11.00, status: "placed", placedAt: ISODate(...) }

// inventory: referenced, because it mutates often and is read alone
// sku "pen": { _id: "pen", stock: 97, updatedAt: ISODate(...) }

// customer: referenced, independent, changes separately
// { _id: 55, email: "ada@x.dev" }

Why: line items are bounded and always shown with the order (embed, atomic); inventory and customer change independently and are queried alone (reference).12

Lock it down with validation

db.createCollection("orders", {
  validator: { $jsonSchema: {
      bsonType: "object",
      required: [ "schema_version", "customerId", "items", "total", "status" ],
      properties: {
        total: { bsonType: "double", minimum: 0 },
        status: { enum: [ "placed", "fulfilled", "cancelled" ] },
        items: { bsonType: "array", minItems: 1 }
      }
  } }
})

The anti-pattern sweep

  • Massive unbounded document? No — items is bounded; history is not embedded forever.
  • Embedding what should stand alone? No — inventory and customer are referenced.
  • Over-fragmenting? Reasonable — order, inventory, customer are genuinely separate.3

The senior reflex

Before finalizing any model, verbally test it against the rules you've learned:

  1. Does the shape serve the highest-frequency read in one operation?
  2. Is every embedded thing bounded and co-updated (16 MiB, atomicity)?
  3. Is anything queried alone trapped inside another document (should reference)?
  4. Is the schema pinned where drift would hurt, and versioned so it can evolve?
Key idea Data modeling is a reflex, not a recall task. Run the four checks on every schema and you'll make the embedded/atomic/shaped choice that interviewers and production both reward.
