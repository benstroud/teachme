Data Modeling Cheat Sheet

The compressed essence of the course. Skim before a lesson, study it fully before an interview.

1. The one principle

Data that's accessed together should be stored together. Shape documents around the application's read/write patterns, not relational normal forms.1 The model is: documents are flexible and polymorphic; there is no mandatory fixed schema.

2. Embed vs reference (the core decision)

ScenarioChoose
"Contains"/has-a, one-to-oneEmbed
Data read together, updated togetherEmbed
Data archived togetherEmbed
Simpler model / fewer operationsEmbed
High-cardinality or unbounded childReference
Child queried/used independentlyReference
Write-heavy, written at different timesReference
Duplication too costly to manageReference
Complex many-to-many / large hierarchyReference

Source table: the MongoDB "link related data" decision table.23

3. Relationship shapes

// one-to-one: embed the "one" inside the owner
{ _id, email, profile: { name, avatar } }

// one-to-many (embed the many, bounded, always shown with parent)
{ _id, author, addresses: [ { street, city }, { street, city } ] }

// one-to-many (reference the many, large/independent) — reverse ref
// post:      { _id, author, title }
// user:      { _id, name, postIds: [...] }        // array of ids

// many-to-many: references on both sides
// student: { _id, name, courseIds: [...] }
// course:  { _id, title, studentIds: [...] }

Embeds the many when it is bounded and co-displayed; falls back to references when the child side grows without bound or stands alone.4

4. The two hard rules

  • 16 MiB per document — an unbounded embedded array will break this.2
  • Single-document atomicity — writes to one document are atomic; cross-document needs transactions. Model so the hot path touches one document.5
  • Avoid lost updates: filter on the expected current value, or use $inc.5

5. The schema design process

  1. Identify workload — fill a table: Action | Query Type | Info | Frequency | Priority (reads and writes).6
  2. Map relationships — embed or reference per relationship.
  3. Apply patterns — computed values, bucketing, polymorphism, versioning, etc.
  4. Create indexes — support the frequent query patterns.

6. Lock it down: $jsonSchema

db.createCollection("students", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: [ "name", "year", "major" ],
      properties: {
        name: { bsonType: "string" },
        year: { bsonType: "int", minimum: 2017, maximum: 3017 },
        gpa:  { bsonType: "double" }
      }
    }
  }
})
  • Validation runs on insert and update; invalid docs are rejected by default.7
  • Combine with $expr rules (e.g. discounted price < price) via an $and validator.

7. Evolve safely

// additive + back-compatible, with a version marker
db.orders.updateMany({}, { $set: { schema_version: 2, discount: 0 } })

// read-time: route by version
if (doc.schema_version <= 1) { ... } else { ... }
  • Prefer additive, backward-compatible field additions; keep a schema-version field; migrate reads before dropping old fields.8

8. Trees (pick by query)

PatternBest when you query…
Parent references…immediate parent/children.
Child references…children of a node directly.
Ancestors array…all ancestors/descendants.
Materialized paths…subtrees via a path string prefix.
Nested sets…subtrees fast, mutate rarely.

9. Anti-patterns to avoid

  • Massive unbounded document — an embedded array that never stops growing (16 MiB + hot-write rewriting the whole doc).
  • Massive array field — the same idea; cap or reference it.
  • Embedding what should stand alone — data that changes often and is read separately belongs in its own collection.
  • Over-fragmenting into needless collections (e.g. one-per-type logs) without a payoff.
