Rebase onto

With --onto you can replay a specific range of commits onto a new base — the tool for moving a topic branch or dropping a middle commit.

The mental model in one sentence

git rebase --onto newbase upstream [branch] replays the commits that are unique to upstream..branch onto newbase — letting you choose a different place to rest them than the branch they currently follow.1

The 3-argument form

git rebase --onto newbase upstream [branch]
#   upstream..branch  = the commits to move
#   newbase           = where to replay them

Compare with the plain 1-arg git rebase upstream: there, the commits upstream..branch are replayed onto upstream itself. The 3-arg --onto form decouples "what to move" from "where to put it".1

Use case: drop the middle commit

# topic is o1-o2-o3-o4-o5 on master; you want to keep o4,o5 but drop o3
#   newbase = o2 (that is topic~3)
#   upstream = o3 (that is topic~2)   → range o3..topic = o4, o5
git rebase --onto topic~3 topic~2 topic
# result: o1---o2---o4'---o5'   (o3 dropped, o4/o5 replayed)

By giving a newbase earlier than the range start, you effectively drop a commit in the middle while keeping every commit after it.1

Key idea Master the two names: upstream marks the start of what to move (exclusive lower bound), newbase marks the new resting place. Move them independently and rebase becomes precise surgery instead of a blunt "onto the tip".

Also used for recovery

The same --onto is how you recover when an upstream was itself rebased: git rebase --onto subsystem subsystem@{1} replays your work onto the new tip while excluding the old, already-reapplied commits.1
