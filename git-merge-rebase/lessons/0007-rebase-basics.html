Rebase Basics

Instead of a merge commit, rebase replays your commits onto the other branch — producing new commits and a linear story.

The mental model in one sentence

Rebase means "reapply commits on top of another base tip": take the commits unique to your branch, replay them onto the target branch, and get new commits — so the result looks like one straight line.1

Flipping the base

# before: main and feature diverged
git switch feature
git rebase main
# after: feature's unique commits sit on top of main's tip

      o---o---o  main
              \
               f1--f2  feature          (f1', f2' are new commits)

Your branch's unique commits are replayed one-by-one onto main. Because their history changed, Git writes new commits with new hashes — even if the content is the same.1

Key idea Merge leaves a fork in the road; rebase erases it. That's what makes history linear — and why rebasing local work is fine, but rebasing already-published commits is the famous hazard (covered in a later lesson).

Rebase vs merge, the two views

  • Merge — preserve "what actually happened" (a faithful history with merge commits).1
  • Rebase — tell a cleaner "story" of how you got from A to B.1

Neither is objectively better; teams pick one and document the policy.1

Interactive rebase

git rebase -i opens a plan you can edit — reorder, reword, squash (merge several commits), or drop commits — before they are replayed.1

Check yourself

1. Rebasing your branch onto main results in…

2. The replayed commits are new commits because…

3. The merge-versus-rebase choice is about…
