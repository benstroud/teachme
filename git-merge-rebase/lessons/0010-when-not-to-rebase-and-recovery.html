When Not to Rebase & Recovery

Rebase freely only on work nobody else depends on; if you ever rewrite shared history, the reflog and --onto are your way back.

The mental model in one sentence

Only rebase commits that you own — never commits others may have based work on — because rewriting changes the hashes everyone else anchors to; when that happens anyway, recover with reflogs and --onto.1

The golden rule

If you only ever rebase commits that have never left your own computer, you'll be just fine... If you rebase commits that have already been pushed and people may have based work on, you may be in for trouble.Pro Git — Rebasing

Rewriting a shared branch changes commit hashes, so anyone who already based work on the old ones now sits on a fork that no longer exists at that tip.1

Key idea The safe combination: rebase your local work to clean it up, then merge it into the shared branch. "Rebase local before pushing; never rebase what you've pushed."1

Recovery after an upstream rebase

# upstream (subsystem) was rebased; old tip is still in your reflog
git fetch
git rebase --onto subsystem subsystem@{1}
# replays your work onto the new tip, skipping the already-applied commits

The reflog (git reflog) records where refs used to point; subsystem@{1} names the old tip so --onto can exclude it and stop Git re-applying the same patches.1

If you or teammates must rebase a shared branch

Tell everyone, and standardize on git pull --rebase (or set pull.rebase true) so re-integrating the rewritten branch is as painless as possible.1
