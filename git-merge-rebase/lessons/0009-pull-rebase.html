Pull with --rebase

A normal pull merges upstream in; pull --rebase instead replays your local commits on top of it — keeping a linear branch.

The mental model in one sentence

By default git pull fetches and then merges; with --rebase it fetches and then rebases your local commits onto the fetched upstream, so you never make an integration merge commit for upstream drift.1

What each mode gives you

git pull              # fetch + merge  → possibly a merge commit
git pull --rebase     # fetch + rebase your work onto origin/main

If there is nothing new locally, a plain pull fast-forwards. If both sides gained commits, a default pull creates an integration merge; --rebase instead re-bases your local commits to sit cleanly on the new upstream tip.1

Key idea Rebase-on-pull keeps your branch's commits attributed to you and placed after the latest upstream — the branch reads as a straight line. It is the recommended flow on branches you are integrating, not for rewriting shared history others depend on.

Make it the default

git config --global pull.rebase true

Setting pull.rebase makes every git pull rebase by default — a popular choice on feature branches, and the same setting teammates should use if they work atop a rebased branch.1

If a conflict appears

A rebase pull can hit the same conflict markers as a merge; resolve each file, git add, then git rebase --continue (rather than git commit) to keep replaying. You can abort with git rebase --abort.1
