The Fast-Forward

When one branch is simply ahead of the other, a merge just moves the pointer — no new commit, nothing to resolve.

The mental model in one sentence

A fast-forward is a merge that can just move the current branch pointer up to the merged commit, because that commit is already a descendant of where you are — so no merge commit is created.1

When it happens

main: o---o---A
feat:            B---C     (feature descends from A)

git switch main
git merge feature
# main simply fast-forwards to C  — nothing new, "Updating A..C"

Because everything in feature already contains main's history, there is nothing to combine; the pointer just advances. No commit, no conflict.1

But not when you have diverged

If main also gained commits after A, the two branches moved apart. Then a fast-forward is impossible: Git must do a true three-way merge and create a merge commit (next lesson).1

Key idea A fast-forward is the cleanest possible integration — but it only exists when there was no real divergence. Tools often hide this (auto-ff or auto-merge), which is why --ff-only exists: it fails loudly rather than silently creating a merge commit.

Two flags that control it

  • git merge --ff-only — refuse the merge if it cannot fast-forward (good in automation).
  • git merge --no-ff — always create a merge commit, even when a fast-forward would work (used to record "a feature was merged here").1
