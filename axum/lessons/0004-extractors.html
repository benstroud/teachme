Extractors

A handler declares the request data it needs as typed arguments. Axum fills them in, or returns an error response before your code runs.

The idea

An extractor is a type that pulls a value out of an incoming request. You write it as a handler argument, and Axum runs the extraction. The docs say extractors always run in the order of the function parameters, from left to right.1 If an extractor fails, the handler never runs, and the client receives the error response.1

Path, Query, and Json

The lab's l04_extractors.rs uses the three most common extractors:

#[derive(Deserialize)]
struct Pagination {
    page: Option<u32>,
    per_page: Option<u32>,
}

#[derive(Deserialize)]
struct CreateUser {
    name: String,
    age: u8,
}

async fn list_things(Query(p): Query<Pagination>) -> String {
    format!("page {} of {}", p.page.unwrap_or(1), p.per_page.unwrap_or(20))
}

async fn show_team(Path((user_id, team_id)): Path<(u32, u32)>) -> String {
    format!("user {user_id} team {team_id}")
}

async fn create_user(Json(payload): Json<CreateUser>) -> String {
    format!("created {} aged {}", payload.name, payload.age)
}
  • Path reads route parameters. A tuple matches several parameters in order: /users/{user_id}/team/{team_id} fills (user_id, team_id).2
  • Query reads the query string into a struct. Fields typed Option may be absent. The lab test query_defaults_when_absent checks that /things still works.
  • Json reads a JSON body into a struct that derives Deserialize.3

The body must come last

The request body is a stream that can be read only once. Axum enforces this by requiring the body-consuming extractor to be the last argument. The other extractors read the parts of the request and leave the body alone.1

// Compiles: parts first, body last.
async fn echo(method: Method, headers: HeaderMap, body: String) -> String {
    format!("{method} sent {} header(s), body of {} bytes", headers.len(), body.len())
}

// Does not compile: the body extractor is not last.
// async fn bad(body: String, method: Method) -> String { ... }
What the compiler says The probe for the broken version fails with E0277: the trait bound ... Handler<_, _> is not satisfied. The message names the handler, not the argument, so when you see it, check the order of the arguments first.1

When a request is rejected

Each extractor returns a status code when its input is wrong. The lab's tests record what the real server returns:

InputExtractorStatusTest
/users/abc/team/9Path<(u32, u32)>400bad_path_value_is_400
/double with no n fieldQuery, required field400missing_query_field_is_axum_rejection_not_ours (lesson 7)
POST /users, body {"name": (broken syntax)Json400json_with_broken_syntax_is_400
POST /users, valid JSON missing ageJson422json_with_wrong_shape_is_422
POST /users, no Content-Type: application/jsonJson415json_without_content_type_is_415

The split matters. Broken syntax is a 400. Well-formed JSON with the wrong shape is a 422. A missing content type is a 415. Your code does not choose these codes: the extractor does.3

Check yourself

A handler takes (Json<Body>, Path<u32>) in that order. What happens?

The body can be read only once, so Axum requires the body-consuming extractor as the final argument. The probe fails with E0277.1

A JSON body is valid JSON, but it is missing a required field. Which status does the lab return?

Well-formed JSON that does not fit the target type is a 422. Test json_with_wrong_shape_is_422 checks it.3

A POST request has a JSON body but no Content-Type: application/json header. Which status does the lab return?

Without the JSON content type, the Json extractor refuses the body with 415. Test json_without_content_type_is_415 checks it.3
