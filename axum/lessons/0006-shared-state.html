Shared State

Every request is a separate call. State that must outlive one request is bound to the router once, then handed to each handler that asks for it.

Bind state to the router

A router can be built with a state type S. Handlers that take State<T> need S to provide a T. Calling with_state supplies a value of S, and the result is a Router with no unbound state. That is the only kind axum::serve accepts.1

#[derive(Clone, Default)]
pub struct AppState {
    pub notes: Arc<Mutex<Vec<String>>>,
}

pub fn app(state: AppState) -> Router {
    Router::new()
        .route("/notes", post(add_note))
        .route("/notes/count", get(count_notes))
        .with_state(state)
}

// State first, body last.
async fn add_note(State(state): State<AppState>, body: String) -> StatusCode {
    state.notes.lock().unwrap().push(body);
    StatusCode::CREATED
}

The lab's l06_state.rs runs this exactly. add_note follows the rule from lesson 4: the state extractor is a parts extractor, so it comes first, and the body comes last.

Why Arc

Axum clones the state for each handler call. AppState derives Clone, and cloning it clones the Arc, not the notes. Every clone points at the same Mutex. The lab test state_is_shared_across_requests keeps a clone outside the router and checks that it sees both notes.1

Substates with FromRef

A handler that needs only one part of the state can ask for that part. Implement FromRef to say how to get it from the whole state:2

impl FromRef<AppState> for Arc<Mutex<Vec<String>>> {
    fn from_ref(app: &AppState) -> Self {
        app.notes.clone()
    }
}

async fn count_notes(State(notes): State<Arc<Mutex<Vec<String>>>>) -> String {
    notes.lock().unwrap().len().to_string()
}
Choosing a mutex The lab uses std::sync::Mutex, and no handler holds the guard across an .await. The docs say a Tokio mutex is needed only when the guard must cross an await point.2 A std guard held across an .await is the mistake to avoid.

Compared with Tauri

If you did the Tauri set, the shape is familiar. Tauri's app.manage and State<T> play the same role as Axum's with_state and State<T>.3 The difference is where the state is bound: Tauri binds it to the app at setup, while Axum binds it to the router, and the router's type parameter records whether state is still missing.

Check yourself

Why must the router have no unbound state before axum::serve takes it?

with_state binds the state. The result is a Router with no unbound state, which is what serve needs. The probe in the lab confirmed the compile failure.1

You clone an AppState that holds Arc<Mutex<Vec<String>>>. What do you get?

Cloning an Arc produces another pointer to the same allocation. The test state_is_shared_across_requests depends on this.1

The state holds a lock that a handler must keep across an .await. What do the docs recommend?

The state docs say a Tokio mutex is needed when the guard must be held across an .await. Otherwise the std mutex is often preferred.2
