Middleware

Code that runs around many handlers: adding headers, refusing unauthenticated requests, logging. Axum builds it from Tower layers, and from_fn lets you write one as a function.

A middleware is a function that calls next

middleware::from_fn turns an async function into a layer. The function receives the request and a Next, and calls next.run(request) to pass the request on. The docs say the function takes zero or more parts extractors, then one body extractor, and Next must be last.1

// Runs after the handler: change the response.
async fn add_app_header(request: Request, next: Next) -> Response {
    let mut response = next.run(request).await;
    response
        .headers_mut()
        .insert("x-app", HeaderValue::from_static("axum-lesson"));
    response
}

// Runs before the handler: refuse the request, or let it through.
async fn require_token(request: Request, next: Next) -> Result<Response, StatusCode> {
    if request.headers().contains_key("x-token") {
        Ok(next.run(request).await)
    } else {
        Err(StatusCode::UNAUTHORIZED)
    }
}

The first function acts after the handler, by editing the response. The second acts before it, and returns an error status when the check fails. In the second case the handler is never called.

layer versus route_layer

Both attach middleware, and the difference is which routes they cover:2

CallApplies toIn the lab
.layer(m) on a RouterEvery route added before the calladd_app_header: every response has x-app
.route_layer(m) on a method routerOnly that route, and only when it matchesrequire_token: only /secret needs a token
pub fn app() -> Router {
    Router::new()
        // route_layer: only applies to /secret, and only when that route matches.
        .route(
            "/secret",
            get(secret).route_layer(middleware::from_fn(require_token)),
        )
        .route("/hello", get(hello))
        // layer: applies to every route added before it.
        .layer(middleware::from_fn(add_app_header))
        .layer(TraceLayer::new_for_http())
        .layer(CorsLayer::permissive())
}
Order of layers The docs note that with repeated .layer() calls the last one is the outermost, so a request reaches it first.2 The docs recommend ServiceBuilder when you want layers to run top to bottom, which reads more like the order of execution.

Tower-HTTP layers

The tower-http crate provides ready-made layers. The lab uses two:3

  • TraceLayer::new_for_http() logs each request and response. Lesson 10 shows the subscriber that prints them.
  • CorsLayer::permissive() allows every origin. It is convenient for a lab, and it is not a production setting. Lesson 10 covers what to change.

Check yourself

Which call attaches middleware to one route, and only when that route matches?

route_layer applies to a single method router and runs only when its route matches. layer covers every route added before it.2

A from_fn middleware returns Err(StatusCode::UNAUTHORIZED) before calling next. What does the client see?

The middleware decides whether to call next.run. If it returns an error response instead, the handler is not called. The lab test route_layer_rejects_without_token checks the 401.

Which tower-http layer logs each request and response?

TraceLayer::new_for_http() logs requests and responses through tracing. Lesson 10 shows the subscriber.3
