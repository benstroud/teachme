Responses

A handler returns a value. If that value implements IntoResponse, Axum makes the HTTP response from it: the body, the status, and the headers.

IntoResponse is the contract

The handler docs say a handler is an async function that returns something that can be converted into a response.1 The trait that does the conversion is IntoResponse. Strings, status codes, Json, tuples, and Result all implement it, so you rarely write the conversion yourself.

Json as a response

Json<T> serializes T with serde and sets the content type. The lab's one_user handler returns it directly:2

#[derive(Serialize)]
struct User {
    id: u32,
    name: String,
}

async fn one_user() -> Json<User> {
    Json(User { id: 1, name: "Ada".into() })
}

The lab test json_sets_content_type_and_body checks that the response is application/json and that the body parses with name equal to Ada.

Tuples set the status and headers

A tuple puts a status code and extra parts in front of the body. The first element can be a StatusCode, and the docs describe the other elements as header or extension parts.1

async fn created() -> (StatusCode, Json<User>) {
    (StatusCode::CREATED, Json(User { id: 2, name: "Ben".into() }))
}

async fn plain() -> impl IntoResponse {
    ([(header::CONTENT_TYPE, "text/plain; charset=utf-8")], "hello")
}

The first handler returns 201 Created with a JSON body. The second is a header array in front of a string: the array sets content-type, and the string becomes the body. The lab tests tuple_overrides_status and header_array_sets_content_type check both.

Result sends errors as status codes

Result<T, E> works as a response when both T and E implement IntoResponse. A StatusCode is a valid error type, so an Err becomes a status-only response:1

async fn find(Path(id): Path<u32>) -> Result<Json<User>, StatusCode> {
    if id == 1 {
        Ok(Json(User { id, name: "Ada".into() }))
    } else {
        Err(StatusCode::NOT_FOUND)
    }
}
Prefer a concrete error type The response docs advise against Result<impl IntoResponse, impl IntoResponse>, because it does not always work with ?. A concrete error type, such as StatusCode here or your own AppError in lesson 7, avoids the problem.1

Check yourself

A handler returns Json<User>. What does the client get, by default?

A bare Json response has status 200 and sets application/json. The test json_sets_content_type_and_body checks it.2

A handler returns (StatusCode::CREATED, Json(user)). What does the client get?

A tuple with a status code first sets that status. The rest of the tuple is the body and parts.1

A handler returns Err(StatusCode::NOT_FOUND) from a Result<Json<User>, StatusCode>. What does the client get?

StatusCode implements IntoResponse, so the Err arm becomes a 404 response. Axum does not drop the connection.1
