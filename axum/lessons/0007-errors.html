Errors

Every failure must become a response. Define one error type, decide its shape once in IntoResponse, and let ? convert into it.

Why errors become responses

Axum services are built on Tower's Service, and Axum requires them to use Infallible as the error type. An error that escaped the service would reach the HTTP server, which closes the connection without sending a response.1 So a handler that fails must return a value that is already a response.

That is why a handler may return Result<T, E> where E implements IntoResponse. The Err arm becomes a response, and the client sees a status code and a body.

One error type, one shape

The lab's l07_errors.rs defines one enum and decides its wire format in one place:

#[derive(Debug)]
pub enum AppError {
    BadInput(String),
    NotFound,
}

impl IntoResponse for AppError {
    fn into_response(self) -> Response {
        let (status, message) = match self {
            AppError::BadInput(msg) => (StatusCode::BAD_REQUEST, msg),
            AppError::NotFound => (StatusCode::NOT_FOUND, "not found".to_string()),
        };
        (status, Json(json!({ "error": message }))).into_response()
    }
}

Every error now has the same JSON shape, {"error": "..."}, and the status is chosen in one match. A handler never builds an error response by hand.

Let ? convert the error

The ? operator calls From to turn one error type into another. Implement From<ParseIntError> for AppError, and a parse failure in a handler becomes a 400:

impl From<std::num::ParseIntError> for AppError {
    fn from(err: std::num::ParseIntError) -> Self {
        AppError::BadInput(err.to_string())
    }
}

async fn double(Query(q): Query<DoubleQuery>) -> Result<Json<serde_json::Value>, AppError> {
    let n: i64 = q.n.parse()?; // ParseIntError -> AppError::BadInput
    if n < 0 {
        return Err(AppError::BadInput("n must not be negative".into()));
    }
    Ok(Json(json!({ "double": n * 2 })))
}

The lab test parse_error_becomes_400_json sends ?n=abc and checks that the body's error field contains invalid digit, the text from the standard library's parse error.

Two kinds of 400 A parse error inside your handler is your AppError, with your JSON body. A missing required Query field is an extractor rejection, and Axum writes that response. The lab test missing_query_field_is_axum_rejection_not_ours checks that the body is not your JSON at all. Both are 400, but they come from different code.

Beyond the basics

The docs describe HandleError and HandleErrorLayer for services and middleware that can fail with an error type you do not control.1 You will need them when a third-party layer returns an error. They are not covered by a lab test here.

Check yourself

Why must a failing handler return a value that is already a response, instead of letting the error propagate?

Axum services must be infallible at the Tower level. An error reaching the server closes the connection, so errors become responses inside the handler's return type.1

Which trait does ? use to convert a ParseIntError into AppError?

The ? operator calls From::from on the error. That is why the lab implements From<ParseIntError> for AppError.1

A required Query field is missing. Who writes the 400 response?

An extractor that fails returns its own response, and your handler is never called. The lab test checks that the body is not your error JSON.1
