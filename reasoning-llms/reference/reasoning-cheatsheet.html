ReferenceReasoning vs Non-Reasoning LLMs

Reasoning LLM Cheat Sheet

The compressed essence of the course. Skim before a lesson, study it fully before an interview.

1. The two model classes

Standard LLM  = next-token generator, fluent + fast, low cost
Reasoning model = trained (RL) to "think" before the answer, high accuracy on hard steps
  • Standard models recall and write fast; reasoning models deliberate first.1
  • Same engine underneath: the difference is training and inference behavior.

2. Standard generation

context = "The capital of France is "
-> "Paris"  -> "."  -> " "  ...   # token by token, never backtracks
  • Autoregressive: each token depends on all prior context, no search or backtrack.7
  • Great at fluency/recall; fragile on long dependent-step chains.

3. What reasoning adds

Standard:  immediate continuation
Reasoning:  [chain of thought] -> final answer
Trained by: RL on verifiable rewards (e.g. correct math)
  • RL rewards behavior that yields right answers, so long CoT emerges.3
  • R1-Zero proved pure RL (no SFT) can incentivize reasoning.3

4. Chain of thought

Shown (open, e.g. DeepSeek):   full reasoning tokens printed
Hidden (e.g. OpenAI):           only a short reasoning summary
At runtime:                     reasoning content can be streamed
  • CoT began as a prompting trick; reasoning models internalize it.4
  • Hidden means withheld, not absent — the model still thinks.1

5. Effort & compute

reasoning_effort: low | medium | high      # thinking budget per request
Train-time compute  -> capability baked in
Test-time compute   -> per-query accuracy (more thinking tokens)
  • Raise effort for hard math/code; lower it to cut latency and tokens.1
  • More test-time compute can beat a larger model on reasoning.5

6. When reasoning wins

AIME 2024 math:  standard ~12%  ->  o1 74% (pass@1) / 93% (reranked)
Codeforces:       ~89th percentile
GPQA (PhD sci):   exceeds human PhD-level accuracy
  • Wins on long, checkable, multi-step tasks: math, code, logic, deep analysis.2
  • Verifiable rewards are exactly why RL works on these.3

7. When reasoning does not help

Trivia / recall:     answer in weights, no steps
Classification / extraction:  short + direct
Latency-sensitive UI: thinking tokens delay each reply
High-volume / budget:  reasoning costs many tokens
  • Extra thinking returns nothing on easy tasks; it is pure overhead.1
  • It does not fix hallucination: a wrong premise stays wrong after thinking.

8. Evaluating reasoning

pass@1      : one generation (realistic for API calls)
consensus   : majority vote over many samples (costly)
reranked    : upper bound with a verifier
test-time scaling: more thinking/search/verifiers lift accuracy
  • Read any score with effort + sampling setting + benchmark in mind.2
  • Verify with a verifier or re-rank to squeeze accuracy from compute.5

9. Routing & deployment

request -> classify -> easy: standard model (fast, cheap)
                       -> hard: reasoning model (effort by task)
always: stream output, cache repeats, log quality/latency/cost
  • Route the easy majority to standard, the hard minority to reasoning.1
  • Per-request compute allocation is the product lever you own.

10. Checklist

  • Know which class each task needs: recall/flavor (standard) vs proof/code (reasoning).
  • Set reasoning effort per request class; measure quality, latency, and token cost.
  • Expect hidden CoT in some providers; build around the public answer or summary.
  • Quote benchmarks with pass@1, effort, and sampling context.
  • Route, stream, cache — then watch cost and latency per route.
