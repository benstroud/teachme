Microservices Glossary

Every term in this course, in one place. Return here when a lesson uses a word you do not fully own.

The style

microservice
Part of a style that builds one application as a suite of small services, each in its own process, communicating via lightweight mechanisms, built around a business capability, and independently deployable.1
independent deployment
The ability to deploy, release, and evolve a service on its own — a defining trait; coordinated deployments mean the style has broken down.2
monolith
An application built as a single deployable unit. Well-structured monoliths exist; "monolith" does not automatically mean bad code.2
distributed monolith
A set of services that must be changed and deployed in lockstep — microservices in name, a monolith in behavior; a warning sign.2
microservice premium
The productivity cost the style imposes; it is only repaid once system complexity or team size makes it worthwhile.2

Boundaries & teams

business capability / subdomain
A slice of business functionality that becomes a natural service boundary — "an implementable model of a slice of business functionality."3
bounded context
A DDD boundary within which a domain model is consistent; a service typically owns one.3
Conway's Law
The observation that a system's structure tends to mirror the communication structure of the team that built it.2
smart endpoints, dumb pipes
Put logic in the services (the endpoints) and keep the communication pipe as simple as possible.1
shared kernel / database-per-service
Each service owns its data; a shared database couples services and undermines the style.3

Consistency & data

ACID
Atomic, consistent, isolated, durable — the transactional guarantees of a single database.
eventual consistency
The state of data distributed across services converges over time, rather than being strongly consistent at every instant.2
saga
A way to manage a transaction that spans services: a sequence of local transactions, with compensation steps to undo on failure — no distributed transaction.4
transactional outbox
A pattern that publishes an event reliably alongside the data change (an outbox table written in the same transaction).5
API composition
Combining responses from several services to answer one client query.
CQRS
Command-query responsibility segregation: separate the write model from the read model, useful when queries need their own data shape.3

The edge, resilience & operations

API gateway
A single entry point that routes and composes calls to services, keeping clients away from the service mesh.6
backend-for-frontend
A gateway owned per client type, shaped to that client's needs.
circuit breaker
A resiliency pattern that stops calling a failing service after repeated failures, letting it recover.7
idempotency / retry
Retries are safe only when a repeated call has no duplicate side effect — handlers should be idempotent.
distributed tracing
Carrying a trace id across service calls so one user request can be followed end to end.1
service discovery
How services find each other's addresses at runtime instead of hardcoded URLs.1
strangler fig
A migration approach that incrementally replaces a monolith with services, piece by piece.1
