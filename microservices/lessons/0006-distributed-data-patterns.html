Distributed Data Patterns

With no distributed transaction, patterns handle the span: saga coordinates work, outbox publishes reliably, and composition builds queries.

The mental model in one sentence

When an operation spans services, you cannot use one ACID transaction — so saga sequences local transactions with compensations, transactional outbox publishes events reliably, and API composition (with the gateway) assemblies read results.12

Saga

A saga manages a multi-service operation as a sequence of local transactions: each service commits its own step, and if a later step fails, previously applied steps are undone by compensating transactions. This is the alternative to a distributed transaction that doesn't exist.2

Transactional outbox

To publish an event reliably alongside a data change, write the event to an outbox table in the same local transaction as the business change; a relay later publishes it. This closes the "the DB saved but the event was lost" gap.3

API composition & CQRS

  • API composition — combine several services' responses to answer one client query (often at a gateway).
  • CQRS — separate the write model from the read model; your queries can use a denormalized read store that events keep up to date.1
Key idea The common theme: accept eventual consistency and model it explicitly — sagas and outboxes make partial failure and retries handled instead of silent.
