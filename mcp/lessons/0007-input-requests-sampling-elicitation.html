Input Requests, Sampling, and Elicitation

Sometimes a server needs something from the human or the model mid-task. The 2026-07-28 revision changes how it asks, and sampling is on its way out. Learn the rules for asking safely.

A note on evidence

This lesson is cited, not yet exercised by the lab. The SDK exports the types and builders, and the changelog and specification describe the flow. The lab's tests do not yet run a multi-round-trip exchange. Treat the code in this lesson as the documented shape, and verify it before you ship.

Input requests replace server-initiated requests

In the 2025 revision, a server could send its own requests to the client, such as elicitation/create. The 2026-07-28 revision replaces these with a multi-round-trip pattern. The handler returns an InputRequiredResult (resultType: "input_required") that lists what it needs. The client answers and retries the same operation with inputResponses.1

// Handler shape from the SDK's documentation: ask for confirmation before deleting.
server.registerTool("deploy", { inputSchema: z.object({ env: z.string() }) }, async ({ env }, ctx) => {
  const confirmationSchema = z.object({ confirm: z.boolean() });
  const confirmed = acceptedContent(ctx.mcpReq.inputResponses, "confirm", confirmationSchema);
  if (confirmed?.confirm !== true) {
    return inputRequired({
      inputRequests: {
        confirm: inputRequired.elicit({
          message: `Deploy to ${env}?`,
          requestedSchema: confirmationSchema,
        }),
      },
    });
  }
  return { content: [{ type: "text", text: `Deployed to ${env}` }] };
});

Read it as a loop. The first call has no answer, so the tool asks. The client shows the question, collects the answer, and retries with it. The second call finds the answer and completes.2

Elicitation: two modes

An elicitation asks the user for input. The spec defines two modes, and the choice matters for security:3

ModeWhat it collectsRule
formStructured values, against a flat JSON Schema of strings, numbers, booleans, and enumsMUST NOT be used for passwords, API keys, or access tokens
urlThe user is sent to an out-of-band URL to complete the stepRequired for sensitive data. The client MUST NOT open the URL without the user's consent

Clients SHOULD let users decline an elicitation at any time, and a response is one of accept, decline, or cancel.3

The rule for secrets If the server needs a credential, it must send the user to a URL where the credential is entered out of band. A form field that asks for a password is the wrong design, even if the field is hidden.3

Sampling is deprecated

Sampling lets a server ask the client's model for a completion, with no server-side API key. Under the 2026-07-28 revision it is deprecated, and new implementations SHOULD NOT adopt it. The deprecation registry gives an earliest-removal rule, not a date.4 The spec still says that a human SHOULD always be able to deny a sampling request, and that a client MUST respect maxTokens.4

Think it through (no code)

Your server needs an OAuth token for a third-party service on first use. Decide: form elicitation, URL elicitation, or a token in an environment variable set before launch. Justify the choice with the rule for sensitive data, and say what the user sees in each case.

Check yourself

Which elicitation mode must a server use to collect a password or API key?

Form mode must not carry sensitive data. Sensitive input goes through URL mode.3

What is the status of sampling under the 2026-07-28 revision?
