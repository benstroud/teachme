Deploying a Server

A server runs in one of two places: as a process on the user's machine, or as a network service many clients share. Each has different trust and different rules. Learn both, and the one checklist they share.

Two transports, two trust models

The architecture overview gives the practical difference: a local stdio server typically serves a single client, while a remote Streamable HTTP server typically serves many. Stdio has no network overhead, and it is the natural choice for a tool the user installs.1

stdio (local)Streamable HTTP (remote)
Who starts itThe client, as a child processAn operator, as a long-running service
ClientsUsually oneMany
AuthenticationCredentials from the environment, per the specOAuth for HTTP servers, per the spec
Main riskLocal compromise and one-click installsAnyone who can reach the port

Serve over HTTP

The lab's src/http.ts wraps the same server in createMcpHandler. That returns a web-standard fetch function, which a Node HTTP server calls with each request:2

const handler = createMcpHandler(() => buildServer(store), { legacy: "reject" });

const http = createServer(async (req, res) => {
  // ...convert req to a web Request, then:
  const rejected =
    originValidationResponse(request, localhostAllowedOrigins()) ??
    hostHeaderValidationResponse(request, localhostAllowedHostnames());
  const response = rejected ?? (await handler.fetch(request));
  res.writeHead(response.status, Object.fromEntries(response.headers));
  res.end(Buffer.from(await response.arrayBuffer()));
});
http.listen(port, "127.0.0.1");

Two decisions in that code are security decisions. The server listens on 127.0.0.1, not on every interface. And the Origin and Host checks run before any MCP logic. The spec says servers MUST validate the Origin header against DNS rebinding, and SHOULD bind only to localhost when running locally.3

What the lab recorded

The HTTP test calls the server through the v2 client, pinned to 2026-07-28. It lists tools, and it calls add_numbers and gets { sum: 9 }. A second request carries a foreign Origin and is refused:

foreign origin status: 403 {"jsonrpc":"2.0","error":{"code":-32000,"message":"Invalid Origin: evil.example"},"id":null}
no origin status: 400

The 403 is the Origin check at work. The bare 400 appeared for a request with no Origin header and none of the MCP headers. The lab did not investigate that 400 further, so read only its status code, not a cause.

What a remote server must add

Binding to localhost is not enough for a server other people reach. The authorization spec says the authorization is OPTIONAL for MCP, but for HTTP it is the mechanism that identifies the caller. An HTTP server MUST implement OAuth 2.0 Protected Resource Metadata, and MUST accept only tokens issued for its own resource. Access tokens must never go in the query string.4

Stdio servers should not follow the HTTP flow. They should read their credentials from the environment, which the spec states directly.4

The lab's limits The lab's HTTP server has no OAuth. It is correct for a process bound to localhost, and it is not correct for a server on the internet. Lesson 9 lists what production needs.

Configuration from the environment

The lab reads PORT and HOST from the environment, with defaults of 3000 and 127.0.0.1. A container image should take the same approach, with the host set explicitly, rather than edits to the source.
