The Event Loop, Callbacks & Promises

Microtasks vs. macrotasks — how Node.js stays single-threaded yet concurrent.

A single thread that never blocks

Node.js runs your code on one thread and uses an event loop to dispatch asynchronous work. As I/O operations complete, their callbacks queue up in order. TypeScript can't fix timing bugs — only understanding the loop can. The two queue kinds behave very differently:1

  • Microtasks (Promise callbacks, process.nextTick) — run immediately after the current stack empties, before the timers/I-O phases.
  • Macrotasks (setTimeout, I/O callbacks, setInterval) — run in a later phase of the same pass.
console.log("1: Synchronous start");

setTimeout(() => {
  console.log("4: Macrotask (setTimeout)");
}, 0);

Promise.resolve().then(() => {
  console.log("3: Microtask (Promise)");
});

console.log("2: Synchronous end");

// Output order: 1, 2, 3, 4

Even with a 0-ms timer, the Promise microtask runs first. The timer is queued to the macro phase; the promise lands in the micro phase, which the loop drains before moving on.

Async/await with type safety

TypeScript requires that async functions return Promise<T> wrapped types, keeping the asynchronous contract explicit:

async function fetchUserStatus(userId: number): Promise<{ id: number; active: boolean }> {
  return { id: userId, active: true };  // promised shape, checked by TS
}

async function main(): Promise<void> {
  const status = await fetchUserStatus(42);
  console.log(`User ${status.id} active: ${status.active}`);
}

main();
Key idea Microtasks beat macrotasks. When you see code "run out of order," the reason is almost always that a Promise resolution was reordered past a timer you assumed would fire first.
