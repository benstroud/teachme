Indexes & Query Performance Cheat Sheet

The compressed essence of the course. Skim before a lesson, study it fully before an interview.

1. The core idea

An index is a B-tree over a field's values. It lets MongoDB answer a query by scanning the relevant index keys instead of every document. The trade-off: indexes speed reads but add cost to every write.1

// no index → collection scan (COLLSCAN)
// with index → index scan (IXSCAN) + FETCH

db.orders.createIndex({ customerId: 1 })   // single-field
  • _id is implicitly indexed (unique); you can't drop it.1
  • Default index name = keys + directions, e.g. customerId_1.
  • An embedded-field index serves only whole-document equality on that sub-doc, not sub-field queries.1

2. Compound indexes & prefixes

db.orders.createIndex({ region: 1, placed: 1, total: 1 })

The compound index serves queries on any prefix: {region}, {region, placed}, {region, placed, total}. It does NOT serve {placed} or {total}.2

  • {a,c} can use the prefix {a} but is less efficient than a true {a,c} index.
  • If you have {a:1,b:1}, a separate {a:1} is redundant (unless sparse/unique) — drop it.2
  • Max 32 fields in a compound index.2

3. ESR — the field-order recipe

// query: equality on region, sort by placed, range on total
db.orders.createIndex({ region: 1, placed: 1, total: 1 })  // E S R
  • Equality (exact match) fields first.
  • Then Sort (to avoid an in-memory sort), then Range ($gt/$lt).3
  • Equality fields can be any order among themselves, but all precede sort/range.
  • $ne, $nin, $regex are range; $in alone is equality (with sort caveats).3

4. Sorting with an index

db.orders.createIndex({ placed: 1 })         // asc
// serves sort { placed: 1 } AND { placed: -1 } (walk in reverse)

db.orders.createIndex({ a: 1, b: -1 })       // must match pattern or inverse
// serves sort {a:1,b:-1} and {a:-1,b:1} only
  • If an index includes the sort fields (in the same order), MongoDB sorts from the index — no in-memory SORT stage.4
  • Otherwise a SORT stage appears in explain (in-memory sort; spills to disk if >100 MB).4

5. Multikey (array) indexes

db.movies.createIndex({ genres: 1 })         // genres is an array → multikey
  • One index entry per distinct array element, all pointing to the same document.5
  • Automatically multikey — no flag needed.
  • To cover a query, the multikey array must be out of the projection and no $elemMatch.5

6. Properties: unique, TTL, partial, sparse

db.users.createIndex({ email: 1 }, { unique: true })
db.eventlog.createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 })
db.orders.createIndex(
  { status: 1 },
  { partialFilterExpression: { status: { $exists: true } } })
  • Unique — rejects duplicate values / combinations.6
  • TTL — single-field, on a date; auto-deletes after expireAfterSeconds (primary only on replica sets).7
  • Partial / sparse / hidden — restrict coverage for space & write savings, or test a drop.

7. Reading explain

db.orders.find({ customerId: 7 }).explain("executionStats")
  • winningPlan.stage: IXSCAN (using an index), COLLSCAN (full scan), FETCH, SORT.
  • A SORT stage means an in-memory sort; a covered query has query+projection all in the index (no FETCH).8
  • executionStats: nReturned, executionTimeMillis, scan counts — compare before/after an index.

8. Strategy checklist

  • Index the workload, not everything — cover the frequent queries from the app.
  • Order compound fields ESR; remember the prefix rule.
  • Use the index to satisfy sorts (avoid SORT).
  • Balance read wins against write overhead.1
  • Prune redundant prefix indexes (covered by a compound).
  • Prove it with explain (IXSCAN, no SORT).
