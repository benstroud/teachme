Compound Indexes & Prefixes

The single most important index rule: order matters, and a compound index serves queries on its leading prefixes.

The mental model in one sentence

A compound index orders by several fields at once, and MongoDB can use it for any query that filters on a leading prefix of those fields — but only the prefix, in the index's order.1

The prefix rule

db.orders.createIndex({ region: 1, placed: 1, total: 1 })

This index serves queries on:

  • { region } (prefix of 1)
  • { region, placed } (prefix of 2)
  • { region, placed, total }

It does not serve queries on { placed }, { total }, or { placed, total } — those skip the leading field.1

Partial prefixes still help, thinly

A query on { region, total } can use the region prefix but then filters total in the scan rather than via the index — correct, but less efficient than a true { region, total } index.

Field order decides everything

The index is physically sorted by its first field, then its second, and so on. Reordering the fields changes which queries it serves — which is exactly what the ESR guideline (Lesson 4) exploits.

The "drop the redundant prefix index" rule

If you already have { a: 1, b: 1 }, an index on just { a: 1 } is redundant — the compound covers every query the prefix index would, so the standalone index is pure write overhead (unless it carries a unique/sparse constraint).2

// redundant: keep only the compound one
db.c.createIndex({ a: 1 })
db.c.createIndex({ a: 1, b: 1 })
Key idea Think of a compound index as a phone book sorted by (region, then placed, then total). You can look things up only if you know the region first. Field order = which lookups are possible.
