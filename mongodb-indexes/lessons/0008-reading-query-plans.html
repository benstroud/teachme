Reading Query Plans with explain

Stop guessing whether an index is used. Ask the database and read its answer.

The mental model in one sentence

explain shows the winning query plan as a stage tree, so you can see at a glance whether MongoDB did a collection scan, used an index, or had to sort in memory.1

Running explain

db.orders.find({ customerId: 7 }).explain("executionStats")

Useful verbs: queryPlanner (the plan) and executionStats (what actually ran, including counts and time). Default is allPlansExecution. Note it ignores the plan cache, so it exercises the planner fresh.12

The stage vocabulary

StageMeaning
COLLSCANCollection scan — no index used.
IXSCANIndex scan — reading keys from an index.
FETCHRetrieving the actual documents after the index narrows matches.
SORTIn-memory sort — no index supplied the order.

The stages nest: a plan like FETCH → IXSCAN means it found matching keys in the index, then fetched those documents.

Spotting the two things you care about

  • Is an index used? Look for IXSCAN instead of COLLSCAN.2
  • Is the sort free? If there's no SORT stage, the index supplied the order.2

Covered queries

When the projection is also in the index, MongoDB can answer from the index alone — no FETCH at all. That's a covered query, the ideal end state.3

// index { customerId: 1, region: 1 } covers this:
db.orders.find({ customerId: 7 }, { _id: 0, region: 1 })

The before-after loop

  1. explain the slow query → note stage and execution time.
  2. Create/adjust the index (ESR, Lesson 4).
  3. explain again → confirm COLLSCAN → IXSCAN, no SORT, time down.
Key idea The plan is the ground truth your design is measured against — COLLSCAN, SORT, and FETCH in the wrong places are the evidence that an index is missing or mis-ordered.
