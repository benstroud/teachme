Index Strategy & Putting It Together

The end-to-end method: analyze the workload, design the minimal index set, prove it, and reap the write-cost savings.

The mental model in one sentence

Index to serve the app's frequent query patterns — a small, well-ordered set — then verify each with explain and prune anything redundant.

Step 1 — Index the workload, not everything

List the queries your app runs most (the same workload table that drives schema design: action, fields, frequency, priority). The frequent reads that filter on specific fields are the ones that earn an index — and the read-vs-write ratio decides whether each is worth it.1

Step 2 — Design the smallest efficient set

// queries shown by the workload
db.orders.find({ region: "EU", total: { $gt: 100 } }).sort({ placed: -1 })

// ESR-ordered compound index that serves it
db.orders.createIndex({ region: 1, placed: -1, total: 1 })
  • Order fields by ESR (Lesson 4).
  • Let one compound index cover several queries via its prefixes (Lesson 3).

Step 3 — Prove it and prune

  1. explain each hot query → want IXSCAN, no SORT, ideally covered.
  2. Drop redundant prefix indexes (a compound supersedes its own prefix).2
  3. Use hidden indexes to test a drop before committing (Lesson 7).

Real costs to watch

  • Write overhead: every index updates on every insert — a wide write collector shouldn't carry many.1
  • Index builds: creating an index on a large live collection is itself an operation; run it in off-hours or on a rolling schedule.
  • Unused indexes waste disk and slow writes for nothing — audit and drop them.

The check you can run today

For every slow query: is there an index (IXSCAN)? is the order free (no SORT)? is the compound prefix-served? is it selective? Answering these four turns query tuning from art into a routine.3

Key idea Great indexing is minimalism: the fewest, best-ordered indexes that serve the workload — each proven in explain and each pulling its weight against its own write cost.
