Lesson 1 of 9MongoDB Indexes

Why Indexes & How They Work

An index is a book's table of contents — a small, ordered structure that turns every-document scanning into a quick lookup.

The mental model in one sentence

MongoDB stores a small, ordered copy of a field's values in a B-tree index; with one, a query reads just the relevant keys instead of scanning every document.1

The relentless collection scan

Without a usable index, MongoDB must examine every document to answer a query — a full collection scan. That's fast on toy data and catastrophic at scale:

db.orders.find({ customerId: 7 })
// no index on customerId → MongoDB inspects every order document

What an index changes

Create an index on the queried field:

db.orders.createIndex({ customerId: 1 })

Now MongoDB can find customerId: 7 directly in the B-tree and jump to just those documents. The read becomes an index scan (IXSCAN) rather than a collection scan (COLLSCAN).1

The trade-off that defines your job

Indexes speed reads but slow writes: every insert must also update each index on the collection.1 So you don't index everything — you index the queries that matter:

  • Repeatedly queried fields: index them.
  • A field on a high-write collection that's rarely read: think before indexing.

What's always there: the _id index

MongoDB automatically creates a unique index on every collection's _id and you can't drop it — which is why lookups by _id are always fast.1

Key idea Before optimizing a slow query, ask: is there an index it can use, and does the read's value justify that index's write cost? Those two questions are the whole discipline.
