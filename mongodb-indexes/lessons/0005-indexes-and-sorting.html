Indexes & Sorting

Let the index return sorted results for free — or watch MongoDB fall into an in-memory sort.

The mental model in one sentence

If an index is ordered by the fields you sort on (in the same order), MongoDB returns results already sorted with no separate SORT stage; otherwise it sorts in memory.1

Single-field sorts

An ascending index on a serves both sort({a:1}) and, by walking it in reverse, sort({a:-1}).1

db.records.createIndex({ a: 1 })
db.records.find().sort({ a: 1 })    // index-served
db.records.find().sort({ a: -1 })    // index-served (reverse)

Compound sorts follow the prefix, and the direction

Get this one exactly:

// index { a: 1, b: -1 } serves sorts that MATCH the pattern or its exact inverse
//   { a: 1, b: -1 }  ✓   { a: -1, b: 1 }  ✓
//   { a: -1, b: -1 } ✗   { a: 1, b: 1 }   ✗

The sort keys must be a prefix of the index, in the same order.1

What an in-memory sort costs

When no index supplies the order, MongoDB adds a SORT stage — the query plan's fingerprint of an in-memory sort. Since MongoDB 6.0, sorts that exceed 100 MB spill to disk (unless allowDiskUse:false), but a large in-memory sort is still expensive and a red flag for latency.2

Why this interacts with ESR

This is exactly why ESR puts the sort field in the index: doing so removes the SORT stage. A sort({ place: 1 }) on a query filtered by { region: 1 } wants an index like { region: 1, place: 1 } — equality, then sort.3

Key idea When you read a plan and see a SORT stage for a hot query, the fix is almost always an index whose field order puts the sort field after your equality fields.
