Single-Field Indexes

The simplest index — one field, ordered — and the two caveats that surprise people.

The mental model in one sentence

A single-field index orders a collection by one field, so MongoDB can locate values and support sorts on it directly.

Creating one

db.collection.createIndex({ field: 1 })    // 1 = ascending, -1 = descending
db.orders.createIndex({ customerId: 1 })   // serve finds by customerId
db.orders.createIndex({ placed: -1 })      // serve "newest first" sorts
  • The key pattern is { field: direction }.1
  • Direction matters for sorts (Lesson 5); for a plain equality lookup either works.

Index names

The default name is the keys and directions joined by underscores — customerId_1, placed_-1. You can give it an explicit name, but you can't rename one after creation (drop and recreate instead).2

Caveat 1: embedded-object indexes are coarse

Indexing an embedded document (e.g. location) is used only by queries that specify the entire document. A query on a sub-field inside it (location.city) won't benefit — index the sub-field directly instead.2

db.sales.createIndex({ location: 1 })        // only full {state,city,zip} matches
db.sales.createIndex({ "location.city": 1 }) // what you usually want instead

Caveat 2: selectivity

An index is most useful when it's selective — an equality on it narrows the result a lot. An index on a field with one dominant value (e.g. status: "active" for 99% of docs) still lets Mongo scan the index, but returns most documents anyway; weigh whether it's worth the write cost.1

Key idea For a field you filter on, the single-field index is the starting point. Remember it orders the data, and its usefulness is bounded by how selective the values are.
