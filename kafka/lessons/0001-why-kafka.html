Lesson 1 of 9Apache Kafka

Why Kafka

A queue gives a job to one consumer once. Kafka keeps a durable, replayable, ordered log of events that many consumers can read.

The mental model in one sentence

Kafka is a distributed, append-only commit log — a durable, time-ordered history of events — rather than a queue that moves a message from producer to consumer and deletes it.1

What an event is

An event is an action, incident, or change recorded by software — a payment, a click, a temperature reading. It's a notification (the "when-ness" that can trigger activity) plus small state, usually JSON, Avro, or Protobuf.2

Queue vs log: the key difference

Queue (e.g. SQS)Kafka log
LifetimeMessage deleted after consumedEvents kept (retention / compaction)
OrderingBest-effort / noneStrict per partition
Re-readNoYes — replayable from an offset
ConsumersOne consumer group drainsMany groups read independently

Because events persist and are replayable, Kafka is how systems build event history, event sourcing, and stream processing — things a queue isn't built for.

The storage + compute layering

Kafka has a distributed storage layer (stores events efficiently, scales by adding brokers) and a compute layer of APIs on top — the producer, consumer, Kafka Streams, and Connect APIs.1

Key idea Ask: does this job need one consumer to process it once (queue), or do multiple consumers each need the same ordered, replayable events (log)? That single question usually picks the tool.
