Producers

The client that writes events — choosing the partition, the key, and how hard it insists on durability.

The mental model in one sentence

A producer writes events to a topic, chooses a partition (usually by key for ordering), and picks an acks level that trades latency against durability.1

Choosing the partition

  • Let the client hash a key: same key → same partition → per-key ordering (Lesson 2).
  • No key → round-robin across partitions (greater parallelism, no ordering).
  • Explicit partition id — rare, for advanced control.

acks: the durability dial

acksGuaranteeCost
0None — fire and forget; may lose writes.Fastest
1Leader has appended the write.Leader failure can lose it
allAll in-sync replicas appended.Slowest, most durable

acks=all is the durable default; pair it with min.insync.replicas so "all" means "enough copies" (Lesson 3).1

Retries & idempotence

Producers retry transient failures. Without care, a retry after a timeout can deliver the same event twice (duplicate). Making the producer idempotent (adding per-record identifying metadata) lets Kafka deduplicate retries — a step toward exactly-once (Lesson 6).1

// producer sketch (conceptual)
producer = {
  bootstrapServers: "broker:9092",
  acks: "all",                     // durability
  retries: 5,
  enableIdempotence: true,          // dedupe retries
}
producer.send(topic, key = orderId, value = orderEvent)
Key idea The producer is where you decide both where an event lands (key → partition) and how certain the write is (acks). Choose the key by ordering needs, and set acks to the durability your data deserves.
