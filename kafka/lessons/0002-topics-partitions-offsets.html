Topics, Partitions & Offsets

The shape of the log: a topic is sharded into ordered partitions, and every event in a partition has an offset.

The mental model in one sentence

A topic is a named channel of events, split into partitions (ordered, append-only logs), and each event in a partition carries a unique offset.1

Topic → partitions

topic "orders"
  partition 0: [o1, o4, o7]     offset 0,1,2
  partition 1: [o2, o5]         offset 0,1
  partition 2: [o3, o6, o8, o9] offset 0,1,2,3

Producers append events to partitions; consumers read from partitions. The topic is the subscription unit; partitions are the unit of parallelism and of ordering.

Offsets

Within a partition, each event has a unique, monotonically increasing offset that is never reused — events are stored and delivered in offset order.2 The offset is what lets a consumer remember where it stopped and resume (or replay) later.

consume() -> read at offset N -> process -> commit(N+1)

Ordering is per-partition

Ordering is guaranteed within a partition, not across a topic. To keep related events in order, route them to the same partition — usually by a key:

// route by key: all events for the same user land in one partition
producer.send(key = userId, value = event)

If you need per-entity ordering (all of one user's events in sequence), the partition key is your entity id.

Partition count = parallelism

More partitions mean more parallel producers/consumers — but ordering is then only within each partition, and too many partitions add overhead (more files, more leadership, more rebalances). Pick the count for the parallelism you need, not "bigger."

Key idea Everything in Kafka maps to the partition: ordering lives there, offsets live there, parallelism lives there. Decide who shares a partition by asking what must be ordered together.
