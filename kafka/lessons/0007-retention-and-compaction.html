Retention & Log Compaction

Events don't vanish after being read — how long they stay, and two very different cleanup policies.

The mental model in one sentence

Kafka keeps events in the log until a cleanup policy removes them: either deletion by time/size for event streams, or compaction that keeps only the latest value per key for state.1

Retention: delete by time or size

  • By time (retention.ms): events older than N are removed.
  • By size (retention.bytes): drop the oldest once the partition exceeds N.
  • Delete-based retention is the default — good for streams of events you replay only short-term.

Retention is when data disappears; the more history you keep, the longer consumers can re-read it.

Compaction: keep the latest per key

With log compaction, Kafka keeps, for each key, the latest value, dropping older versions. The log "compacts" to the current state of every key — like a changelog that only preserves the newest row.1

compacted topic:
  key=user:1 value={name: "Ada"}
  key=user:2 value={name: "Bob"}
  key=user:1 value={name: "Ada Lovelace"}   // newer; old user:1 value dropped

Choosing delete vs compact

  • Delete for event streams you want to replay for a window, then discard (click streams, logs).
  • Compact for state-like topics where each key's current value is what matters (a service's current config, a user's latest profile) — even if consumers are far behind.1

Why this powers event sourcing

Kafka can hold the full event history (delete, long retention) and separately a compacted projection — the classic event-sourcing pair. The durable, replayable log from Lesson 1 is exactly what retention gives you.

Key idea Pick cleanup by what the topic is: a stream of events → delete after a window; a set of current values → compact by key. Getting this wrong is a classic cause of "why did my history vanish" or "why does the log never shrink."
