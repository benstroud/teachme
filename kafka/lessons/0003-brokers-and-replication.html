Brokers & Replication

A cluster of brokers stores each partition on multiple nodes, so a broker failure doesn't lose data.

The mental model in one sentence

Kafka runs as a cluster of brokers; each partition is replicated across brokers with one leader and follower copies, so the data survives node failures.1

Brokers and clusters

  • A broker is a Kafka server that stores partitions and serves producers/consumers.
  • A cluster is a group of brokers; Kafka scales out by adding brokers, with partitions spread across them.1

Replication: leader and followers

Each partition is stored on several brokers (the replication factor). One copy is the leader — it serves reads and writes. The others are followers that stay in sync and can take over if the leader fails.1

topic "orders" partition 0, replication factor 3:
  broker1: partition 0 (LEADER)
  broker2: partition 0 (follower)
  broker3: partition 0 (follower)

ISR: the in-sync replicas

Only replicas that are fully caught up with the leader count as in-sync (the ISR). Leadership can only move to an in-sync replica — so a stale or dead follower can't lose acknowledged data.1

Making writes durable: min.insync.replicas + acks

  • A producer with acks=all waits until all in-sync replicas have appended the write.
  • min.insync.replicas sets how many ISR copies must acknowledge a write for it to be accepted — combine it with acks=all and a replication factor ≥ 2 so a broker loss still leaves a current copy.1

The durability trade-off

More replicas = better durability but higher write cost and latency. Choose the replication factor for the availability you need; acks and min.insync.replicas then decide exactly how hard a client insists before believing a write succeeded.

Key idea Durability is a combination: the partition (how many copies) times the write policy (which copies must ack). "Replication factor ≥ 2 + acks=all + min.insync ≥ 2" is the standard safety floor.
