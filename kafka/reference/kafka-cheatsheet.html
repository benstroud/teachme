Kafka Cheat Sheet

The compressed essence of the course. Skim before a lesson, study it fully before an interview.

1. The mental model

Kafka is a distributed, append-only commit log of events. Events are durable, replayable, ordered per partition, and readable by many consumers — more than a queue, less than a database.1

producer --> topic:partitions (append-only log) --> consumers (by offset)

2. Core pieces

TermWhat it is
EventAn action recorded as notification + small state (JSON/Avro/Protobuf).1
TopicA named channel events are written to and subscribed from.
PartitionAn ordered, append-only shard of a topic; unit of parallelism.
OffsetMonotonic id per event in a partition, never reused.2
BrokerA server in the cluster storing partitions.
Producer / ConsumerClients that write / read events.
Consumer groupConsumers splitting a topic: each partition to one member.2

3. Ordering & keys

// ordering is PER-PARTITION, not per-topic
// a key routes an event to the same partition = per-key ordering
producer.send(record(key = userId, value))  // same user, same partition, ordered

More partitions = more parallelism, but ordering is only within a partition. Pick partition count for scale, not "more is better."

4. Replication & durability

SettingMeaning
replication.factorCopies of each partition across brokers.
leader / followersOne leader serves reads/writes; followers stay in sync.
ISRIn-sync replicas; only these can be leader.3
min.insync.replicasHow many ISR must ack a write to accept it.
acksProducer durability: 0 / 1 / all.4

5. Delivery semantics

  • At-most-once — possible loss, no duplicates (acks=0).
  • At-least-once — no loss, possible duplicates (default).
  • Exactly-once — idempotent producer + transactions.4

6. Consumers & offsets

// consumer commits its position so it resumes after a restart
consume() -> process() -> commit(offset)
// commit AFTER processing = at-least-once (reprocess on crash);
// commit BEFORE = at-most-once

Rebalancing reassigns partitions when group membership changes.

7. Retention & compaction

  • Delete — drop events after retention.ms / bytes (default).
  • Compact — keep only the latest value per key (state-like topics).5

8. Ecosystem & choosing

  • Kafka Streams — stateful processing in Java; Connect — integrations; Schema Registry — schema governance.
  • Use Kafka when you need replayable, ordered, multi-consumer history; a managed option on AWS is MSK.6
  • Prefer a queue (SQS) when one consumer does each job once; prefer Kafka when many consumers each need the same ordered events.

9. Design checklist

  • Keys determine ordering — choose your partition key so related events land together.
  • Set acks + min.insync together — acks=all is only meaningful with a replication factor ≥ 2.
  • Consumers: commit after processing for at-least-once; make the work idempotent.
  • Right retention per topic — delete for raw streams, compact for state.
  • Reach for Kafka for history, not for jobs a single consumer should do once.
