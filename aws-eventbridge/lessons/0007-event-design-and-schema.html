Event design and schema

Naming events well and giving them a contract, so producers and consumers evolve safely.

An event is a public API

Once a service publishes Order Placed, other teams write consumers against it. That makes an event every bit as much a contract as a REST endpoint. Naming and shape deserve real care, because changing them later means breaking everyone who subscribed.1

Naming conventions that hold up

  • source is a reverse domain you own: com.acme.orders. It names who.
  • detail-type is a past-tense, business-langued phrase naming what happened: Order Placed, Order Shipped, not placeOrder or do_stuff.
  • The pair must be unambiguous. OrderPlaced as a single concatenated string robs you of the two-axis routing that patterns expect.
  • Keep detail payload facts, not presentation. It should say what the consumer can rely on, not how to render it.
Why past tense An event records that something already happened. Consumers react to facts — "Order Placed" — not to commands. This stays true even when a Lambda reacts with further actions.

The Schema Registry as your contract store

EventBridge ships a Schema Registry: a central store of event schemas, written in OpenAPI 3 or JSON Schema Draft4. Built-in pieces:2

  • aws.events — schemas for all AWS-service events.
  • discovered-schemas — populated automatically by schema discovery, which infers a schema from the events flowing through a bus.
  • Custom registries you create for your own domains.

Schemas are versioned, and every version is a snapshot of the event shape at a point in time. Consumers can pull code bindings (generated TypeScript classes/interfaces) directly from the registry, so a consumer's code reflects the producer's real contract instead of a hand-maintained guess.2

Evolving a contract without breaking consumers

Events change. Scheme the way you'd version an API:

  • Additive changes are safe — adding an optional field to detail won't break consumers that read specific keys.
  • Removing or renaming is a new event — bump the detail-type (e.g. Order Placed → Order Placed v2) or publish a new event name; keep the old one working while consumers migrate.
  • Register the schema early and let discovery version it, so there is a record of how it evolved.1

Treat "the event is the API" as load-bearing in every design you draw.1

Check yourself

1. Which is the better detail-type for an event announcing an order moved to shipped?

2. What does source primarily name in an event?

3. Suppose the detail of Order Placed must gain an optional couponCode field. Best move?

4. Which format does the EventBridge Schema Registry use for schemas?

Hands-on step (attempt one at a time)

  1. Write, by hand, a versioned contract for one event in a domain you know well: source, detail-type, and the full detail shape with types (its "schema").
  2. Turn it into an OpenAPI 3 schema and register it in the Schema Registry (or write the JSON schema by hand and compare).
Ask the agent Paste the event contract you designed and ask: could a new team consume this without asking the producer? Is anything too coupled to a specific UI? Then get feedback.
