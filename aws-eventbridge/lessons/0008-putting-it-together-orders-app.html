Putting it together: an orders system

The capstone — one architecture that uses everything you have learned.

The system

We are coordinating four Lambda services with an EventBridge bus: an orders API, an inventory service, a payment service, and a notifications service. Nothing calls anything directly.1

PlaceOrder (API Lambda)
   │ PutEvents "Order Placed" → com.acme.order-bus
   ▼
com.acme.order-bus  (custom event bus)
   │
   ├─ rule: InventoryOrders  detail.orderId   → Inventory Lambda
   ├─ rule: ChargeCard       detail.total >= 1 → Payment Lambda
   ├─ rule: Notifications    source/detail     → Notifications Lambda
   └─ rule: ShipUpdates      detail.status      → SQS FIFO → Shipper Lambda (ordered per order)

Decisions and the reasoning behind each

PieceChoiceWhy
Integration styleCustom event busOrders domain gets its own bus — clean rules, isolated permissions.
ProducerAPI Lambda calls PutEventsIt records that an order happened; it never calls consumers.
RoutingEvent patterns + content filteringPayment only gets orders with a chargeable total; others are omitted at the bus.
Easy consumersDirect Lambda targetsInventory and notifications react now, fire and forget.
Ordered workSQS FIFO target for shippingShipment updates for one order must process in sequence → FIFO MessageGroupId = $.detail.orderId.2
ReliabilityDLQ + retry ceiling on every targetA failed consumer never silently loses an event.
Consumer contractsIdempotent on orderId + registered schemaAt-least-once duplicates and future evolution are both handled.3

What decoupling is buying you here

  • Add a consumer (e.g. an analytics Lambda) tomorrow by creating one rule — no change to PlaceOrder.
  • Take a consumer down (payment outage) and orders still get accepted and broadcast; payment catches up later.
  • Scale independently — a burst of orders fans out; each target scales on its own Lambda concurrency.
  • Pay only for matches — content filtering keeps irrelevant events from ever invoking a Lambda.
The whole course in one sentence With an event bus, services announce what happened and the bus routes each announcement to exactly the services that care — producers stop knowing consumers, consumers stop blocking producers, and reliability is handled with idempotency, retries, and dead-letter queues rather than hope.
