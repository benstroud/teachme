Delivery guarantees and failures

At-least-once, retries, dead-letter queues, idempotency, and the ordering question.

What EventBridge guarantees (and what it won't)

Two guarantees dominate every design decision here:1

GuaranteeMeaning for you
At-least-once deliveryA target receives the event at least once — but may receive it more than once. Duplicates are possible.
No ordering guaranteeEvents are delivered in arbitrary order, even from the same source in the same region.

These are not bugs — they are the price of a fully managed, massively parallel bus. Your job is to design so the system behaves correctly despite them. That means idempotent consumers and a deliberate choice about ordering.1

Retries and dead-letter queues

When a target fails to accept an event, EventBridge retries per target. The default policy keeps trying for up to 24 hours and as many as 185 attempts, using exponential backoff with jitter. You tune the ceiling with MaximumRetryAttempts and MaximumEventAgeInSeconds.2

After retries are exhausted, the event is dropped — unless you attach a dead-letter queue (DLQ). A DLQ is a standard SQS queue that receives the events that could not be delivered, so you can inspect and reprocess them later.3

Three DLQ facts that bite people:

  • DLQ and retry config are per target, not per rule or per bus. Adding a second target means configuring it again.
  • A DLQ must be a standard SQS queue — FIFO queues are not supported.
  • The queue needs a resource policy granting events.amazonaws.com permission to write. The console adds it automatically; if you configure via API or across accounts, you must add it by hand.3
Senior habit Treat "no DLQ" as a code smell. Every production target should have a DLQ and a retry ceiling that makes business sense, and you should monitor InvocationsSentToDlq.

Idempotency: the non-negotiable

Because delivery is at-least-once, a consumer must be able to process the same event twice with no harmful effect. The classic approach: dedupe on a stable key. The event envelope has a unique id, but the business key (like orderId) is usually the right dedupe key — because the same order event might legitimately arrive via more than one path. Store the processed key (in a DB or DDB) and skip work if it's already done.5

When order genuinely matters

If events must be processed in order (e.g. user updates that build on each other), EventBridge alone can't deliver that. The standard fix: point the rule at an SQS FIFO queue and key each message by a group:4

{
  "Targets": [{
    "Id": "UserEventsFifo",
    "Arn": "arn:aws:sqs:us-east-1:123456789012:UserEvents.fifo",
    "SqsParameters": {
      "MessageGroupId": "$.detail.userId",
      "MessageDeduplicationId": "$.detail.eventId"
    }
  }]
}

FIFO delivers messages within the same MessageGroupId in order and once-only per dedup id. Using the event's business key as the group id routes all of one customer's events into a single ordered lane. This is how you get order out of an unordered bus — by delegating ordering to the service that guarantees it.4

Hands-on step (attempt one at a time)

  1. Give one of your target rules a dead-letter queue and a retry policy with a low cap (e.g. 3 attempts / 60 seconds), then trigger a deliberate failure and watch the event land in the DLQ with its error metadata.
  2. Make your consumer idempotent: track processed order ids in a DynamoDB table and skip repeat work.
