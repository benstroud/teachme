EventBridge Cheat Sheet

The compressed essence of the course. Skim before a lesson, study it fully before an interview.

1. The event envelope

A standard EventBridge event looks like this:

{
  "version": "0",
  "id": "a1b2c3d4-0000-0000-0000-000000000000",
  "detail-type": "Order Placed",
  "source": "com.acme.orders",
  "account": "123456789012",
  "time": "2026-09-06T10:30:00Z",
  "region": "us-east-1",
  "resources": [],
  "detail": {
    "orderId": "ord_1001",
    "customerId": "cust_42",
    "total": 129.99
  }
}
FieldMeaning
sourceProducer namespace, dotted, e.g. com.acme.orders
detail-typeName of the event kind, e.g. Order Placed
detailBusiness payload (this is what patterns filter)
id / versionUnique event id / envelope version
account / region / timeWhere and when the event happened
resourcesARNs of related resources (often empty)

2. Publishing (producer Lambda)

Every PutEvents entry needs at least:

{
  "Source": "com.acme.orders",
  "DetailType": "Order Placed",
  "Detail": "{\"orderId\":\"ord_1001\",\"total\":129.99}",
  "Resources": [],
  "EventBusName": "com.acme.order-bus"
}
  • Detail must be a string containing JSON, not an object.
  • You may publish multiple entries in one call; each is routed independently.
  • Omit EventBusName to hit the default bus.

3. Rules & event patterns

Only specify the fields you match on. Everything else is a wildcard.

{
  "source": ["com.acme.orders"],
  "detail-type": ["Order Placed"],
  "detail": {
    "total": [{ "numeric": [">=", 100] }]
  }
}

Matching rules:

  • Strings match character-for-character — no case folding, no normalization.
  • Numbers compare by string representation: 300, 300.0, 3.0e2 are not equal.
  • values are arrays: {"source": ["a", "b"]} means a or b.
  • All matching rules fire → one event fans out to many targets.
  • Dots in keys are the joining character: state.status ≡ nested state > status.

4. Content-filtering operators

OperatorExampleMatches when…
prefix{"prefix": "ord_"}value starts with the string
suffix{"suffix": "-DRAFT"}value ends with the string
anything-but{"anything-but": ["a","b"]}value is none of the listed
numeric{"numeric": [">=", 100]}number in the declared range
exists{"exists": false}field is (not) present
wildcard{"wildcard": "ord_*"}glob-style match
equals-ignore-case{"equals-ignore-case":"placed"}case-insensitive equality

5. Targets

TargetWhen to reach for it
LambdaFast, push-based compute on the matched event
SQS queueDurable buffer; flow control; ordering via FIFO
SNS topicFurther fan-out to many subscribers
Step FunctionsLong-running workflow from the event
API destinationCall an external HTTP endpoint
Event bus (other account)Cross-account distribution

Use an input transformer to reshape the payload the target receives.

6. Reliability numbers

  • Delivery: at-least-once. Expect duplicates — make consumers idempotent.
  • Ordering: none by default. Route into SQS FIFO (MessageGroupId) when order matters.
  • Retry: per-target; default 24 hours, up to 185 attempts, exponential backoff + jitter. Set MaximumRetryAttempts and MaximumEventAgeInSeconds.
  • DLQ: must be a standard SQS queue (FIFO unsupported). Config is per target. Requires a resource policy granting events.amazonaws.com write — auto-added by the console, manual otherwise.
  • DLQ messages include metadata: ErrorMessage, ErrorCode, RuleArn, TargetArn, RetryAttempts, exhausted-retry reason.

7. Choosing: EventBridge vs SQS vs SNS vs Pipes

Behavior neededReach for
Route one event to the right of several consumers by structureEventBridge bus
Guaranteed order (same entity) + durable bufferEventBridge → SQS FIFO (via MessageGroupId)
High-volume buffering, consumers pull at their own paceSQS
Simple tell-everyone fan-outSNS
Point-to-point, ordered, enrich-in-betweenEventBridge Pipes

8. Design goals

  • source = who; pairing with detail-type = what; detail = business data. Name them consistently and reuse them.
  • One bus (or namespace) per domain; don't throw unrelated events at the same rule set.
  • Make consumers idempotent (dedupe on id or a business key).
  • Version your events and register schemas so producers and consumers evolve safely.
  • Give every target a DLQ + sensible retry policy; monitor FailedInvocations / InvocationsSentToDlq.
