The Resolver Chain

Execution walks parent → child: each resolver hands its returned object to the next field's resolver.

The mental model in one sentence

A resolver's signature is field(obj, args, contextValue, info) — and the first argument (parent) is the object the parent resolver returned, so nested fields can reach out and resolve against it.1

The four arguments

ArgumentWhat it holds
parentThe value the parent resolver returned; undefined for root Query/Mutation fields.
argsThe operation's arguments for this field, validated and coerced against the schema.
contextValueA per-request object (from the context function) shared by every resolver.
infoExecution state: the query AST, path, operation name. Read it rarely.
1

Tracing a nested query

const Books = [
  { id: '1', title: 'The Awakening', authorId: 'a1' },
  { id: '2', title: 'City of Glass', authorId: 'a2' },
];
const Authors = { a1: { id: 'a1', name: 'Kate Chopin' }, a2: { id: 'a2', name: 'Paul Auster' } };

const resolvers = {
  Query: { books: () => Books },
  Book: {
    // parent = one Book from the Query.books return
    author: (book) => Authors[book.authorId],
  },
};
// query: { books { title author { name } } }

Apollo Server calls Query.books → an array of Book. For each book it resolves the requested fields: title via the default resolver (it reads book.title), then author via your field resolver, which returns an Author — whose name is again resolved by default from author.name.1

The default resolver

If no resolver is defined for a field, Apollo Server uses the default: it reads parent[fieldName]. This is why returning a plain object from a parent resolver often "just works" — you only write a field resolver when the field needs computation or a nested fetch that isn't already shaped in the parent.1

Key idea Each level is a function of the level above it. This is why you resolve nested data from the parent (field resolvers), never by fetching the entire graph inside one root resolver.

Reads can go parallel; mutations cannot

Within one operation, sibling query fields may resolve in parallel, but the fields of a mutation run serially, in order, so each sees the effect of the previous one.2
