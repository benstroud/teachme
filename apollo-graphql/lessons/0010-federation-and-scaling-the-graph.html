Federation and Scaling the Graph

When many teams each own part of the data, subgraphs compose into one supergraph — and one client sees a single API.

The mental model in one sentence

Apollo Federation lets several GraphQL services (subgraphs) be composed into one federated schema (the supergraph) that the Apollo Router serves to clients, routing each request to whichever subgraphs can answer it.1

Subgraphs and the supergraph

Each team runs its own GraphQL API as a subgraph, built with buildSubgraphSchema from @apollo/subgraph. A tool (Rover) composes them into the supergraph. Clients query only the Router, and the Router plans how to gather data across subgraphs — clients never know the graph is split.1

       Client / App
            │  one GraphQL query
      ┌─────▼─────┐
      │  Router   │  (serves the supergraph)
      └──┬────┬──┬┘
         │    │  └─────────┐
   ┌─────▼─┐ ┌▼─────┐  ┌──▼────┐
   │orders │ │users │  │catalog│   ← subgraphs
   └───────┘ └──────┘  └───────┘

Entities and the @key directive

For two subgraphs to contribute fields to the same type, that type is an entity: the owning subgraph declares a key, and each contributing subgraph references the same key. The owner provides a __resolveReference resolver that loads the entity from just that key.2

# catalog subgraph — owns the entity
type Product @key(fields: "id") {
  id: ID!
  name: String!
  price: Int
}
# resolver for the type
Product: {
  __resolveReference(ref) { return db.loadProduct(ref.id); }
}

# users subgraph — contributes a field, matches on the same key
extend type Product @key(fields: "id") {
  id: ID! @external
  reviews: [Review!]!
}
  • @key(fields: "id") picks the identity that ties a product across subgraphs.2
  • The non-owning subgraph marks the key field @external and extends the type with only its own fields.
  • __resolveReference turns a key (e.g. just id) into the full entity inside that subgraph.
Key idea The Router can assemble a single query like product { name reviews { body } } by asking the catalog subgraph for name and the users subgraph for reviews — coordinating via the shared id key.

When to federate (and when not to)

  • Federate when multiple teams own disjoint domains and need one client-facing API, or when you must read across boundaries in a single request.1
  • Don't federate a two-team monolith to a split you don't need; a single subgraph (one Apollo Server) is simpler and the Router is only worth its topology when ownership genuinely divides.
  • Team that owns a field is its source of truth; the schema guardrails (via federation composition rules) catch duplicate or conflicting definitions.
