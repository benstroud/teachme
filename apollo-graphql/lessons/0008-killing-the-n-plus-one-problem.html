Killing the N+1 Problem

A list of objects each loads its children per item — N+1 queries for one request. DataLoader coalesces them into one.

The mental model in one sentence

When a resolver loads data per item inside a list, that's N extra queries; a DataLoader collects the requested keys for a tick, runs one batch query, and hands results back per key while caching within the request.1

Seeing the problem

// Given: query books { id title } { author { name } }
const resolvers = {
  Query: { books: () => loadBooks() },       // 1 query
  Book: {
    author: (book) => loadAuthor(book.authorId),  // N queries, one per book
  },
};

A books of 50 items triggers 1 + 50 = 51 queries. This is the N+1 problem and it is the most common GraphQL performance bug.2

Batching with a DataLoader

import DataLoader from 'dataloader';

async function batchAuthors(ids) {
  const rows = await loadAuthorsByIds(ids);   // ONE query with IN (ids)
  const byId = new Map(rows.map(r => [r.id, r]));
  return ids.map(id => byId.get(id) ?? null);
}

function makeLoaders() {
  return { authors: new DataLoader(batchAuthors) };
}

const resolvers = {
  Book: {
    // inside a single tick, all these load() calls share ONE batch
    author: (book, _args, ctx) => ctx.loaders.authors.load(book.authorId),
  },
};
  • load(key) calls made during one microtask drain are grouped into a single batchLoadFn invocation.1
  • The batch function must return results in the same order as the input keys.
  • Results are cached on the loader, so the same key fetched twice in a request hits the DB once.

The cache must be per-request

// in the context function — a FRESH loader for THIS request only
context: async ({ req }) => ({
  user, db, loaders: makeLoaders(),
})

Never store the loader globally. Its cache would serve one user's data to the next user and would go stale across requests. Create loaders in context, per request, so the cache's lifetime equals the request's lifetime.1

Key idea N+1 shows up exactly where you resolved a nested field from the parent (it's a strength — the field is composable) — the cure is to batch, not to give up composition. DataLoader sits at the loader-layer boundary, not in the resolver's business logic.

When batching is unnecessary

  • If the parent already carries the children (e.g. a join fetched everything), a field resolver that re-queries is pure waste — use the default resolver.
  • For genuinely one-off lookups (a single book(id)), a loader adds little; reserve it for list-of-nested lookups.
