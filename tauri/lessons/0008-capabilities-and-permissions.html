Capabilities and Permissions

Decide, in files you can review, which windows may use which powers. This is where a Tauri app's attack surface is shaped.

Two different questions

Tauri separates two things that are easy to confuse:

  • Which of your commands can be called? By default, every registered command is allowed to be used by all the windows and webviews of the app.1 Restricting your own commands is a build-time setting in build.rs (the AppManifest::commands option). It is not a capability file.
  • Which core and plugin powers may a window use? These are granted by permissions, collected into capability files. Core and plugin permissions are granted only when a capability references them.1
Common assumption, corrected Many developers assume that commands are denied until granted. The capabilities docs say otherwise for your own commands. Read the command list you expose as the real boundary, and use capabilities to limit the built-in and plugin APIs.1

A capability file

Capability files live in src-tauri/capabilities/. The docs' example for the main window looks like this:1

{
  "$schema": "../gen/schemas/desktop-schema.json",
  "identifier": "main-capability",
  "description": "Capability for the main window",
  "windows": ["main"],
  "permissions": [
    "core:path:default",
    "core:window:allow-set-title"
  ]
}

Read it as a sentence: the main window may use the path APIs' default set and may set its own title. The windows key names windows by their label, not their title. Lesson 2's label setting is what this key matches. The security boundary depends on labels, so the docs warn not to rely on titles.2

Turn a capability on

Files in the directory are enabled automatically. Once you list capabilities explicitly in tauri.conf.json, only the listed ones are used in the build.1

"app": {
  "security": {
    "capabilities": ["main-capability"]
  }
}

Permission identifiers

A permission identifier has the form <name>:default or <name>:<command-name>. The name is the crate name without the tauri-plugin- prefix. Examples from the docs include core:window:allow-set-title, core:path:default, and, for a plugin, fs:default and fs:allow-mkdir.3

Scopes: where, not just what

A permission says what an API may do. A scope says where or on what it may do it. The docs define a scope as a granular way to define (dis)allowed behavior of a Tauri command, and say that deny always supersedes allow.4 Scopes are written as TOML in permission definitions, for example an allow entry that matches paths under $HOME in the file system plugin.4

Permissions alone grant nothing for files The file system plugin's docs warn that enabling a permission such as fs:allow-exists by itself does not allow access to any path. A scope is also needed.5 The same logic applies to your own commands: a permission is not a check, and your code must enforce the scope, as lesson 5 noted.

Remote content

By default, the API is only accessible to bundled code shipped with the app. A capability can opt in for remote URLs through a remote key, and the docs' example allows https://*.tauri.app.1 Do not add remote access for a site you do not control.

Content Security Policy

Tauri restricts the Content Security Policy of your HTML pages. The protection is only enabled when the policy is set in the Tauri configuration file, and the docs' example starts with default-src 'self' customprotocol: asset:.6 The exact key path under app.security is not confirmed in these notes, so check the CSP page against the file your scaffold generated before you copy it.

What Tauri protects against, and what it does not

The security overview states the scope of the protection plainly.2

Your task (one attempt)

  1. In your tauri-hello project, open src-tauri/capabilities/default.json (or the capability your template created) and note which permissions the main window has.
  2. Pick one permission that a frontend call depends on, for example a window API. Remove it from the list, restart npm run tauri dev, and make the call.
  3. Read the error the call produces. Write down which permission it names or implies.
  4. Restore the permission and confirm the call works again.

Check yourself

Which key in a capability file selects which windows receive its permissions?

The windows key lists window labels. The docs warn that the boundary depends on labels, not titles.2

By default, which windows may call a command you register with generate_handler!?

The capabilities docs state that all registered commands may be used by all windows and webviews by default. Restrict them in build.rs.1

Which statement about scopes is correct?

The scope docs say deny always supersedes allow. Scopes are plugin-specific TOML in permission definitions.4
