Arguments, Return Values, and Errors

A command that can fail needs Result. On the JavaScript side, a failure becomes a rejected promise.

Returning a Result

Commands return Result<T, E>, the same type you met in the Rust set's error handling lesson. The docs describe the consequence on the JavaScript side: if the command returns an error, the promise will reject, otherwise, it resolves.1

#[tauri::command]
fn read_note(path: String) -> Result<String, String> {
    std::fs::read_to_string(&path).map_err(|err| err.to_string())
}
import { invoke } from '@tauri-apps/api/core';

try {
  const text = await invoke('read_note', { path: '/notes/todo.txt' });
  console.log(text);
} catch (err) {
  // The Rust Err arrives here, as the rejection value.
  console.error('could not read note:', err);
}

The error type must serialize

The error type E has to implement serde::Serialize, because the error crosses the IPC boundary as JSON. The simplest route is the one above: map_err(|err| err.to_string()), which turns the error into a string.1

For a structured error, the docs show a hand-written Serialize implementation that produces an object such as { kind: 'io', message: '...' }. That lets the frontend branch on kind instead of parsing text. The docs' full example is the reference for the code; this lesson just asks you to recognise the target shape.1

Your own Rust is not sandboxed The capability system (lesson 8) governs Tauri's core and plugin APIs for the frontend. The std::fs call above runs in your Rust code, and no capability stops it. A command that reads a path from JavaScript must check that the path is allowed. This is the "incorrect scope checks inside a command" risk named in the security overview.2

Arguments

Arguments follow the casing rule from lesson 4 and must be JSON-serializable. Use plain types: String, numbers, booleans, and structs that derive serde traits. Lesson 3 explained why live Rust values cannot cross the boundary.1

Async commands and borrowing

A command can be declared async. The docs describe two threading rules. A non-async command runs on the main thread, unless you mark it #[tauri::command(async)]. An async command runs on a separate async task.1

#[tauri::command]
async fn word_count(text: String) -> usize {
    text.split_whitespace().count()
}

Notice the argument is an owned String, not &str. The docs say borrowed arguments do not work in async functions. Use an owned type, or return Result<T, ()> when a borrowed argument such as State<'_, T> is unavoidable. Lesson 6 shows the State case.1 The reason traces back to borrowing: a reference must stay valid while the task runs, and the Rust set's lessons on borrowing explain why that is hard to guarantee across an await point.

Check yourself

A command returns Err. What does the JavaScript caller see?

The docs say the promise rejects when the command returns an error, and resolves otherwise.1

Which argument type is the safe default for an async command?

Borrowed arguments do not work in async functions. An owned type avoids the lifetime problem.1

What does #[tauri::command(async)] do on a non-async function?

Non-async commands run on the main thread unless marked async this way.1
