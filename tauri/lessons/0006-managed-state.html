Managed State

Commands are separate calls, so anything they must share between calls lives in state the core manages. Learn how to register it, reach it, and avoid the one mistake the compiler will not catch.

The problem

Each invoke is a separate request. A counter, a settings object, or a database handle has to outlive any one call. The core process is the right owner, because it holds global state by design.1 Tauri's answer is managed state: you hand a value to the app once, and every command can ask for it.

Register it in setup

Add the state inside the builder's setup hook with app.manage. The state docs use a Mutex wrapper so the value can be changed safely across calls.1

use std::sync::Mutex;

#[derive(Default)]
struct AppState {
    counter: u32,
}

tauri::Builder::default()
    .setup(|app| {
        app.manage(Mutex::new(AppState::default()));
        Ok(())
    })

Reach it from a command

Declare a State<'_, T> parameter with the exact type you registered. Tauri supplies it:1

use tauri::State;

#[tauri::command]
fn increase_counter(state: State<'_, Mutex<AppState>>) -> u32 {
    let mut app_state = state.lock().unwrap();
    app_state.counter += 1;
    app_state.counter
}

The '_ is a lifetime the compiler infers, which is the borrowing idea from the Rust set. The state is borrowed from the app for the duration of the call. Lesson 5 showed why that borrow makes a command async-unfriendly.

Reach it outside a command

Code that is not a command gets state through the Manager trait. Import it, then ask the app for the state by type:1

use tauri::Manager;

let state = app.state::<Mutex<AppState>>();
The mistake the compiler will not catch If a command asks for State<'_, Mutex<Other>> but you registered Mutex<AppState>, the project still compiles. The invoke is rejected at runtime with a "state not managed" error. Manager::state() panics instead. Keep the type in one type alias and use it everywhere.1

Async commands

An async command that uses state runs into the borrowing rule from lesson 5. The docs' async example returns Result<u32, ()> because State<'_, T> is a borrowed argument.1 The docs also say the standard library's Mutex is often preferred even in async code. A Tokio async mutex is needed only when the lock guard has to be held across an .await.1

You do not need to learn the mutex internals here. Concurrency belongs to a later set. What you need is the rule: hold a lock for the shortest time you can, and do not hold a standard Mutex guard across an .await.

Your task (one attempt)

  1. Add an AppState with a counter field, and register it with app.manage(Mutex::new(...)) in setup.
  2. Add the increase_counter command above and register it.
  3. Add a button in the frontend that calls invoke('increase_counter') and shows the returned number. Click it three times. You should see 1, 2, 3.
  4. Deliberately change the command's parameter to State<'_, Mutex<String>>. Rebuild, click the button, and read the runtime error. Then restore the type.

Check yourself
