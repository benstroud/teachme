The Process Model and the IPC Boundary

Every request from the interface crosses one boundary. Learn what crosses it, what does not, and why that matters for the design of the whole app.

The picture

  ┌──────────────────────────┐          ┌──────────────────────────┐
  │   Core process (Rust)    │  IPC     │  WebView process         │
  │                          │◄────────►│  (your HTML/CSS/TS)      │
  │  windows, tray, OS APIs  │ messages │                          │
  │  global state, commands  │          │  calls invoke(...)       │
  └──────────────────────────┘          │  listens for events      │
                                        └──────────────────────────┘

The core process routes all Inter-Process Communication.1 Nothing reaches the operating system from the webview directly. Every request goes through the core, and the core decides whether to honour it.

Two ways the frontend talks to Rust

  • Commands are requests. The frontend calls invoke, which the docs describe as similar to the browser's fetch API. It returns a promise with the answer.2
  • Events are notifications. They are fire-and-forget, one-way IPC messages, and either the frontend or the core can emit them.2

Lesson 4 builds commands and lesson 7 covers events and channels. For now, notice that both are asynchronous message passing. The frontend never waits on a Rust function the way one JavaScript function waits on another.2

What is allowed to cross

The IPC layer uses a JSON-RPC like protocol, so arguments and return values must be serializable to JSON.2 You cannot pass a live Rust struct, a file handle, or a pointer across the boundary. You pass data, and the core rebuilds what it needs on its side.

Design consequence Think of the boundary as an API you publish to your own frontend. Every command you expose is a door. Lessons 8 and 9 are about deciding which doors exist and which windows may open them.

Where the trust lies

The security overview describes the model plainly. Code running in the webview has only the access to system resources that is exposed through the IPC layer.3 Tauri aims to limit the damage a compromised frontend can do. It does not make your own Rust code safe. The same overview says Tauri does not protect against malicious or insecure Rust code, scopes that are too lax, or incorrect scope checks inside a command.3

So the practical split is this: the frontend is code you wrote, but it is treated as the less privileged side. Put decisions that touch files, the network, or the OS in Rust, validate what the frontend sends, and grant each window only the permissions it needs.

Why a process boundary at all

The process model is the reason a bug in the interface does not automatically become a bug in the OS layer. The core and the webview are separate processes, and the core is the only component with full access to the operating system.1 Rendering can crash, and the core still holds the state and the windows.

Think it through (no code)

Your app needs to save a user's document to disk. Decide, on paper, which side of the boundary does what: who opens the file, who chooses the path, and who checks that the path is allowed. Write one sentence for each. You will compare your answers with the lesson 8 approach later.

Check yourself

From the frontend's point of view, a call to invoke is most like which browser API?

The IPC docs say invoke is similar to fetch: an asynchronous request that returns a promise.2

Which IPC mechanism is described as fire-and-forget, one-way messages?

Events are one-way and fire-and-forget. Commands are request-and-response, and channels are ordered streams.2

What must be true of the arguments and return values that cross the IPC boundary?

The IPC protocol is JSON-RPC-like, so arguments and return values are JSON-serializable.2
