Lesson 05 · Type-level programming

Conditional Types & infer

An if/else for types — and a pattern-matcher that reaches inside a type and pulls a piece back out.

★ Mission link: this is the first genuinely computational type tool. Conditional types are how the standard library's ReturnType, Parameters, and Awaited are built — and how you'll write the reusable utilities others depend on. Builds on Lesson 03 (extends = ⊆) and Lesson 04 (variance is why infer behaves differently in parameter vs. return position — the payoff at the bottom).

The shape: T extends U ? X : Y

A conditional type is a ternary at the type level. The test T extends U is the same extends you met in generic constraints: a subset test, "is T ⊆ U?"1 If yes, the type resolves to X; if no, to Y.

type IsString<T> = T extends string ? "yes" : "no";

type A = IsString<"hello">;  // "yes"  — "hello" ⊆ string
type B = IsString<number>;   // "no"   — number ⊄ string

On its own that's mildly useful. The power shows up when T is a union.

The behavior that trips everyone: distribution

When the checked type is a naked type parameter (just T, not wrapped in anything) and you hand it a union, the conditional distributes — it runs once per union member and unions the results back together.2

type ToArray<T> = T extends any ? T[] : never;

type R = ToArray<string | number>;
// NOT (string | number)[]
// distributes ⟶ ToArray<string> | ToArray<number> ⟶ string[] | number[]

Read it literally: TS splits the union, applies the conditional to each part, then re-unions. Most of the time this is exactly what you want — it's why Exclude and Extract work. But it has two famous edges:

1. never is the empty union — so it distributes to nothing

type R2 = ToArray<never>;  // never, not never[]

Since never is the empty set (Lesson 01), distributing over "zero members" produces zero results — the empty union, which is never. This surprises people constantly: a conditional that looks like it must produce X quietly produces never when fed never.

2. To stop distribution, wrap both sides in a 1-tuple

If you want the union treated as one whole thing, take the parameter out of "naked" position by wrapping it — the idiomatic trick is [T] extends [U]:2

type ToArray<T> = [T] extends [any] ? T[] : never;

type R3 = ToArray<string | number>;  // (string | number)[]
type R4 = ToArray<never>;            // never[]
Senior tell: seeing [T] extends [never] in real code is the signature of someone who knows distribution. A plain T extends never ? … can never reach its true branch when T is never (it distributes to the empty union), so a "T extends never" check that you expect to fire is almost always a bug — the tuple-wrap fixes it.

infer: pattern-match a type apart

Inside the extends clause of a conditional, infer X introduces a fresh type variable that TS solves for by matching the structure. It's destructuring for types: declare a hole, and whatever fills it becomes the captured type, usable in the true branch.3

// the real definition from lib.es5.d.ts
type ReturnType<T> =
  T extends (...args: any[]) => infer R ? R : never;

type P = ReturnType<() => string>;     // string — R matched the return slot

type Parameters<T> =
  T extends (...args: infer P) => any ? P : never;

type Q = Parameters<(a: string, b: number) => void>;  // [a: string, b: number]

You can infer from any structural position — array elements (T extends (infer E)[]), promise contents (T extends Promise<infer U>), tuple heads/tails, object properties. If the pattern doesn't match, you fall to the false branch.

The variance payoff: same infer name, two positions

Here's where Lesson 04 pays off. When the same infer variable appears in more than one spot, TypeScript has to combine the matches — and which way it combines depends on variance:3

// same U in two OUTPUT (covariant) positions ⟶ UNION
type Out<T> = T extends { a: infer U; b: infer U } ? U : never;
type O = Out<{ a: string; b: number }>;        // string | number

// same U in two INPUT (contravariant) positions ⟶ INTERSECTION
type In<T> = T extends {
  a: (x: infer U) => void;
  b: (x: infer U) => void;
} ? U : never;
type I = In<{ a: (x: string) => void; b: (x: number) => void }>;
// string & number  ⟶  never

This is not arbitrary. To produce a U that satisfies both output slots, the widest safe answer is their union (covariance preserves direction). To accept a U that both input slots can stomach, the only safe answer is their intersection — "demand less" from Lesson 04, run to its logical end. The variance of the position literally chooses the set operation.

Why this matters for your mission: when a hand-rolled infer utility mysteriously collapses to never, the cause is almost always an intersection produced from multiple contravariant matches (often method overloads, where TS infers from the last signature). Knowing the union/intersection rule turns that from baffling to obvious.
