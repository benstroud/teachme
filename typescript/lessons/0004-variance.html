Variance

When Cat ⊆ Animal, which compound types keep that relationship — and which flip it?

★ Mission link: variance is the rule behind cryptic "X is not assignable to Y" errors on functions and callbacks — the ones that stop most mid-level devs cold. Get it from first principles and you can both read those errors and design signatures that accept exactly what's safe. Builds on Lesson 01 (subsets) and Lesson 03 (extends = ⊆).

The one question

Start from a fact you already own: Cat ⊆ Animal — every cat is an animal, so Cat is assignable to Animal.1 Variance asks: when you wrap those types in something — an array, a function return, a function parameter — does the ⊆ relationship survive, flip, or vanish?

There are exactly four answers, and they have names:

NameRelationshipLives in
Covariantsurvives — Cat[] ⊆ Animal[]outputs: return types, readonly arrays
Contravariantflips — see belowinputs: function parameters
Invariantneither direction holdsread-write slots (theoretically: mutable arrays)
Bivariantboth directions acceptedTS method params (an unsound convenience)

Outputs are covariant (the intuitive one)

If a function promises to return a Cat, it certainly satisfies a caller expecting an Animal — a cat is an animal. So return position preserves the direction.1

type GetCat    = () => Cat;
type GetAnimal = () => Animal;

const g: GetAnimal = getCat;  // ✅ () => Cat is assignable to () => Animal

Same logic for read-only containers: a readonly Cat[] is safely a readonly Animal[], because all you can do is read cats out, and every cat is an animal.

Inputs are contravariant (the counter-intuitive one)

Now flip to parameters. Which is safe to use where a (c: Cat) => void is expected? The surprise: a handler that accepts the wider type.2

type HandleCat    = (c: Cat)    => void;
type HandleAnimal = (a: Animal) => void;

const h: HandleCat = handleAnimal;  // ✅ accepts any Animal, so it surely accepts a Cat
const b: HandleAnimal = handleCat;  // ❌ would receive a Dog and call cat-only methods

Read it as a contract: the slot promises to hand your function a Cat. A function that can stomach any Animal honors that promise with room to spare. A function demanding something narrower than Cat would be handed values it can't handle. So in parameter position the ⊆ runs backwards — that's contravariance.

The whole rule in one line: a function A is assignable to function B when A's parameters are wider (contravariant) and A's return is narrower (covariant). "Demand less, deliver more." Memorize this and most function assignability errors decode themselves.

The famous unsound hole: mutable arrays

Strictly, a mutable Cat[] should not be an Animal[], because an Animal[] lets you write a Dog into it — corrupting the cats. A read-write slot is logically invariant. But TypeScript deliberately treats arrays as covariant anyway, trading a bit of soundness for everyday ergonomics:3

const cats: Cat[] = [felix];
const animals: Animal[] = cats;  // ✅ allowed — but unsound
animals.push(rex);            // 🔥 a Dog is now in `cats`; no compile error

Knowing this is the difference between trusting the checker blindly and knowing exactly where it has your back versus where it's looking the other way.

Senior gotcha — methods vs. function properties: under strictFunctionTypes, standalone function-typed parameters are checked contravariantly (strict). But parameters of methods (and constructors) stay bivariant — checked in both directions — for backward compatibility with patterns like event handlers and arrays.3 Same shape, different strictness, depending on whether you wrote method(x): T or method: (x) => T.
