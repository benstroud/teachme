Reading & Decoding Any Type Error

Every cryptic not assignable or infinite type message is decodable — read it with the set model, not memorized patterns.

★ Mission link: the MISSION's first item is "read and diagnose any TypeScript error." This lesson is that skill, built entirely from the vocabulary you already own: sets & assignability, variance, conditional / infer, and recursion. You are not learning new TS — you are learning to read it.

The one sentence that defuses every error

Almost every TypeScript error, no matter how long, collapses to one idea: a set that is expected is missing a value that was handed to it. The message is noise around the signal — read from right to left for the actual mismatch.

Type 'string' is not assignable to type 'number'.
       └── what you GAVE       └── what was EXPECTED

Type 'Users[]' is not assignable to type 'User'.
└── GAVE a superset           └── EXPECTED a smaller set

const x: string | number = ... // the DANGER: a value here is one OR the other

The pattern is uniform: assigned (the value's set) vs expected (the location's set). If the right side ⊆ the expected — fine. Otherwise it's an error. That's all a "not assignable" ever means.

Decode: it's usually variance, not a mystery

When a function-type error looks upside down, stop and check variance (Lesson 04). The rule "demand less, deliver more" explains why a function that looks wider is sometimes rejected:

// error: the parameter type flips (contravariance)
type A = (x: string) => void;
type B = (x: string | number) => void;
const a: A = /* a B value */;  // error: B's param is wider, so a B call site needs more than A allows

When the message is counterintuitive — "I gave the caller more capability and it's an error?" — assume contravariance is involved. The note "Type '(x: string | number) => void' is not assignable to '(x: string) => void' because ... some parameters are contravariant" is TS telling you exactly this.

Decode: generic inference failures

Generic errors usually mean the compiler couldn't pick one type parameter that satisfies the whole call. The remedy: check the constraint (extends), then the call site, then widen.

// error: 'T' inferred as number, but the constraint expects a string
function id<T extends string>(x: T): T { return x; }
id(42);  // error: 42 doesn't extend string

Read: "I tried to fold your argument into T, but it violates the extends subset constraint." Fix by making the argument fit the constraint or loosening the constraint — never by a <any> at the call site first.

Decode: "Type instantiation depth exceeded" / "infinite type"

These are the type-level bugs — fetch them like a runtime crash:1

  • "Instantiation depth exceeded": your recursion (Lesson 08) has no effective base case, or isn't in tail position. Find the conditional whose two branches both lead back to itself.
  • "infinite type expanding": a type grows forever (e.g. a conditional whose infer re-binds the same shape). It's recursion without progress — the argument isn't getting smaller.
// the bug: no base case — Rec consumes forever
type Rec<T> = T extends infer U ? Rec<U> : T;  // U === T — no progress

A reading order for any error

  1. Find the rightmost "is not assignable to". That names the two sets.
  2. Read right-to-left: what was actually expected is the whole story.
  3. If it's a function type, check variance. Are parameters swapped wider/narrower than expected?
  4. If it's generic, check the extends constraint. Does the inferred type violate it?
  5. If it mentions "depth"/"infinite", it's a recursion/base-case bug.
  6. Widen with string/number/unknown only as a deliberate step — never any as a reflex.
The senior tell: juniors add as any to silence the message. Seniors read the same message, state the two sets aloud, and name which rule (subset, variance, constraint, recursion) broke. Same 2-minute window; opposite outcome. You now own all four rules.
