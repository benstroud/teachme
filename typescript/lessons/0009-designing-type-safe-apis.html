Lesson 09 · Designing for teams

Designing Type-Safe APIs

Make misuse a compile error, not a runtime surprise — branded types, builders, and overloads.

★ Mission link: this is the senior finish. Everything so far (sets, variance, conditionals, mapped types, recursion) is plumbing; this lesson is product. You'll design signatures where the compiler prevents the mistakes that normally cost a deployment. Grounded purely in the type machinery you've already built — no new syntax, just new judgment.

The goal: "can't be wrong" over "isn't wrong"

A value-level API can be used correctly or incorrectly — only a test catches the latter. A type-safe API makes the incorrect call a compile error, so misuse never ships. The techniques here are the difference between a function that happens to have types and a function that is designed by its types.1

Branded types: make two strings not interchangeable

Structurally, a userId and an email are both string — so a function that expects email will happily take a userId. A branded type (a.k.a. nominal fake) adds a marker that only you can produce, so the two stop being assignable to each other.2

type UserId = string & { readonly brand: "UserId" };
type Email   = string & { readonly brand: "Email" };

// the ONLY way to make one — a narrowing constructor
function userId(s: string): UserId { return s as UserId; }
function email(s: string): Email { return s as Email; }

function prefs(u: UserId) {}
prefs(userId("abc"));  // ok
prefs("abc");           // error — string isn't UserId
prefs(email("a@b.com")); // error — Email isn't UserId

The & intersection + marker makes the set smaller than string — a UserId is a string that additionally claims "I am a UserId," and only userId() can mint that claim. Every other string, including an Email, fails the subset check.

The builder pattern: sequence as a type

State-machine-style: make each method return a type that exposes only the next valid moves. A call in the wrong order becomes a compile error, because the method simply isn't there on the current type.3

// HTTP request builder: method() then path() then send()
class ReqB<S> {
  private _method?: string; private _path?: string;
  method(m: "GET" | "POST"): ReqB<"ready-method"> { return this; }
  path(p: string): ReqB<"ready-path"> { return this; }
  send(): Promise<Response> {
    if (this._method && this._path) { return fetch(this._path, { method: this._method }); }
    throw new Error("must set method + path");
  }
}
// usage:
new ReqB().method("GET").path("/users").send(); // ok
Why this matters: the builder's generic S tracks progression. If shipped naively — returning the same type every step — send() before method() would only fail at runtime. Encoding the state in the type moves that failure to compile time.

Overloads: return a type that depends on the argument

Overloads let one function produce a precisely-typed result per input. TypeScript picks the first matching overload, so order specific overloads before wide ones.4

function parseId(s: "new"): "new";                  // specific first
function parseId(s: string): number;            // wide fallback
function parseId(s: string) { return s === "new" ? "new" : Number(s); }

const a = parseId("new");  // "new" (literal)
const b = parseId("123"); // number

Overloads work because a literal "new" matches the first signature, while a general string falls through to the second. Consumers get a result typed to their exact input — without any or a lost type.

Literal unions over string

The cheapest win: accept a union of allowed literals instead of string. Autocomplete offers the valid values, and a typo is a compile error instead of a silent undefined-shaped bug:

type Size = "small" | "medium" | "large";
function orderCoffee(size: Size) {}

orderCoffee("medium");  // ok — autocomplete offers these
orderCoffee("grande"); // error — "grande" not in Size

The discipline: emit never, not any

Good API types make the compiler do the work. When you design, prefer each of these over its easy alternative:

  • a branded type over a raw string
  • a builder's encoded state over an unchecked send()
  • an overload's precise return over a wide fallback
  • a literal union over string

Each one moves a class of mistakes from "the test suite should have caught this" to "the compiler would not let it exist." That is the senior bar for API design.
