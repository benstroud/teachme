Lesson 08 · Type-level programming

Recursive Type-Level Programming

A type that calls itself — unwrap, walk, and rewrite structures until a base case.

★ Mission link: recursion is where type-level programming stops being a bag of utilities and becomes a language — you can now write Awaited, a path parser, or a type-level toKebabCase. It's the payoff you've been building toward since Lesson 05. Builds on Lesson 05 (conditionals + infer as destructuring) and Lesson 07 (string pattern parsing).

Recursion is two branches, one promise

Read a recursive type as a function with a test, a base case, and a recursive step. The test is a conditional's extends; the base case stops; the step calls the type's own name.1

// Awaited — unwrap Promise<Promise<…>> to the innermost non-promise
type Awaited<T> =
  T extends promise<infer U> ? Awaited<U> : T;
  //   ^ test                ^ recurse            ^ base case

type A = Awaited<Promise<Promise<number>>>;  // number
type B = Awaited<string>;                    // string (base case)

Read it: "if T is a Promise, unwrap it and repeat on the inner type; otherwise stop and return T."That's it. The recursion unfolds Promise after Promise until the base case holds.

Walking a tuple: head + tail

Tuples recurse by infer into a first element plus a rest tuple. This is the pattern for processing a fixed-length collection element by element:

// convert [A, B, C] -> [()>=>A, ()=>B, ()=>C] using recursion
type Lazy<T extends readonly unknown[]> =
  T extends [infer Head, ...infer Rest]
    ? [() => Head, ...Lazy<Rest>]
    : [];

type T = Lazy<[number, string]>;  // [() => number, () => string]

The base case is [] (empty tuple). Each step peels one element into Head and recurses on the Rest. When the tuple is empty, T extends [infer Head, ...] is false — so we return [] and the outer spreads assemble the result.

The tail-call rule: recurse last

TypeScript versions ≥ 4.5 can tail-call optimize a recursive type — reuse the stack instead of growing it — only when the recursive call is in tail position (the last operation). Put the recursion as the final expression, not buried under more work, so you can recurse over arbitrarily long unions and tuples without hitting the depth cap.2

// GOOD: recursion in tail position
type Awaited<T> = T extends promise<infer U> ? Awaited<U> : T;  // tail ✓
The depth limit: without tail-call optimization, deeply recursive types hit a "type instantiation depth exceeded" error — the type-level stack overflow. Keeping the recursion last is the single most important habit; it's also the difference between "works on my sample" and "handles the real union with 10,000 members."

Recursive + template literals: walking a path

Bring Lesson 07's infer-in-a-string pattern into the recursion to walk a dotted path to its final type. This is how LocaleString, event-name types, and lodash-style get signatures are built:

type Obj = { a: { b: { c: number } } };

type Path<T, P extends string> =
  P extends `${infer A}.${infer B}`
    ? A extends keyof T ? Path<T[A], B> : never
    : P extends keyof T ? T[P] : never;

type C = Path<Obj, "a.b.c">;  // number

Read it: "if the path has a dot, take the head A, index into T[A], and recurse on the tail B; when no dot remains, index the whole path and return."The whole dotted route collapses to the value type at the end.

Recursion in one idea

Every recursive type is the same three pieces:

  1. Test — an extends that checks the shape you consume.
  2. Base case — the branch that does not recurse and ends the chain.
  3. Step — a call to its own name with a smaller argument (inner promise, rest tuple, tail path).

If you can identify those three in any recursive type you read, you can read all of them — and write your own.
