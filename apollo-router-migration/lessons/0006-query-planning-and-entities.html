Query Planning & Entities

How the router turns one query into a plan across subgraphs — and the N+1 trap.

The mental model in one sentence

For each incoming query the router builds a query plan: which subgraphs to call, in what order, and how to stitch their results — using entity keys to join the pieces.1

Entities make the join

type Product @key(fields: "upc") {
  upc: String!
  name: String          # products subgraph
  reviews: [Review]     # reviews subgraph
}

# reviews subgraph resolves the shared entity:
Product: {
  __resolveReference(rep) { return byUpc(rep.upc); }
}

@key tells the router "this subgraph can resolve the entity if you give it the key". The router sends an entity representation — the key fields plus __typename — to the subgraph that owns the rest of the fields.2

The N+1 trap

A reference resolver can be called many times for one query. Untreated, that becomes an N+1 problem, so reference resolvers should batch lookups (typically with data loaders).2

Key idea Query planning is the daily-visible consequence of federation. Whether gateway or router, a bad @key or an N+1 reference resolver hurts every query that crosses subgraphs.2
