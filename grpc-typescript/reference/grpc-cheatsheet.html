gRPC TypeScript Cheat Sheet

The compressed essence of the course. Skim before a lesson, study it fully before an interview.

1. The contract (.proto)

syntax = "proto3";

package orders.v1;

import "google/protobuf/timestamp.proto";

enum OrderState {
  ORDER_STATE_UNSPECIFIED = 0;
  ORDER_STATE_CREATED     = 1;
  ORDER_STATE_FULFILLED   = 2;
  ORDER_STATE_CANCELLED   = 3;
}

message Order {
  string        id = 1;                       // field numbers are write-once
  string        customer_id = 2;
  OrderState    state = 3;
  repeated LineItem line_items = 4;           // array
  google.protobuf.Timestamp placed_at = 5;    // imported message
}

message LineItem { string sku = 1; int32 qty = 2; }
  • Fields are typed + numbered. Scalar types: int32/64, uint32/64, sint32/64, fixed32/64, float, double, bool, string, bytes.1
  • Never reuse or rename a field number — older readers will decode the new meaning as the old, corrupting data.
  • Adding a new field with a fresh number is backward-and-forward compatible.

2. Defining a service (4 call kinds)

service OrderService {
  // unary
  rpc GetOrder(GetOrderRequest) returns (Order);

  // server-streaming: one request, many responses
  rpc ListOrders(ListOrdersRequest) returns (stream Order);

  // client-streaming: many requests, one response
  rpc SubmitBatch(stream Order) returns (SubmitBatchResponse);

  // bidirectional: many requests and responses
  rpc Subscribe(stream OrderUpdateReq) returns (stream OrderUpdate);
}

The stream keyword on request and/or response picks the RPC kind.2

3. Codegen & project setup

# static (TypeScript-first): compile protos to .ts ahead of time
npm i -D @grpc/grpc-js @grpc/proto-loader grpc-tools google-protobuf
npx grpc_tools_node_protoc -I . ./orders.proto \
  --js_out=import_style=commonjs,binary:./gen \
  --grpc_out=grpc_js:./gen \
  --plugin=protoc-gen-grpc=./node_modules/.bin/grpc_tools_node_protoc_plugin
  • Static codegen (grpc-tools / buf) emits .js + .d.ts → the most type safety.3
  • Dynamic (@grpc/proto-loader + grpc.loadPackageDefinition) loads the proto at runtime — less setup, weaker types.
  • Add a protoc-gen-grpc-web plugin if browser clients are needed (see §8).

4. Server (Node / TypeScript)

import * as grpc from "@grpc/grpc-js";
import { loadPackageDefinition } from "@grpc/grpc-js";
import { loadSync } from "@grpc/proto-loader";
import { OrderServiceService } from "./gen/orders_grpc_pb";

const server = new grpc.Server();
server.addService(OrderServiceService, {
  getOrder: (call, callback) => {
    if (!call.request.id) {
      const err = Object.assign(new Error("missing id"), { code: grpc.status.INVALID_ARGUMENT });
      return callback(err);
    }
    const order = lookup(call.request.id);
    if (!order) return callback(Object.assign(new Error("not found"), { code: grpc.status.NOT_FOUND }));
    callback(null, order);
  },
});

server.bindAsync("0.0.0.0:50051", grpc.ServerCredentials.createInsecure(), (err, port) => {
  if (err) throw err;
  server.start();
});
  • For TLS use grpc.ServerCredentials.createSsl(ca, [key, cert]) and an h2/http2 protocol listener.
  • Always set a deadline and a code on errors — defaults are waiting forever and UNKNOWN.45

7. Deadlines, retries, idempotency

// deadline: fail the call if it can't finish by a time
client.getOrder(req, { deadline: new Date(Date.now() + 1500) }, cb);

// retry policy via service config (channel-level in grpc-js)
const channel = new grpc.Channel("orders:50051", creds, {
  "grpc.service_config": JSON.stringify({
    methodConfig: [{ name: [{ service: "orders.v1.OrderService" }],
      retryPolicy: {
        maxAttempts: 4,
        initialBackoff: "0.1s",
        maxBackoff: "1s",
        backoffMultiplier: 2,
        retryableStatusCodes: ["UNAVAILABLE"],
      } }],
  }),
});
  • No default deadline (wait forever) and no default retry policy.89
  • Transparent retries happen even without a policy; a configured policy adds controlled retries for chosen codes.
  • Retryable side-effect calls: make the handler idempotent (dedupe on a request/business key).

  • Interceptors: middleware on a channel or server for logging/metrics/auth; server-side auth is fine here.

9. The BFF boundary & AWS

  • Keep gRPC server-side. The GraphQL and REST BFFs are gRPC clients of the domain services; browsers don't call gRPC directly (gRPC-web exists but needs a proxy).11
  • A GraphQL resolver or REST handler maps a requested shape to one or more gRPC calls, fanning out and aggregating, then maps gRPC status codes to GraphQL errors / HTTP statuses.
  • AWS hosting:
    • Long-running Node gRPC service on ECS (or EKS) behind an Application Load Balancer using the gRPC target type with HTTP/2 (TLS, or h2c on a private network).12
    • Serverless alternative: API Gateway + Lambda transcoding maps a gRPC contract onto REST calls into a Lambda — loses streaming/HTTP/2 benefits.
    • Discover instances via ALB target group or AWS Cloud Map; add grpc.keepalive + health checks.13
  • Observability: propagate W3C trace context in metadata end-to-end; emit OpenTelemetry spans/metrics for each call and retry attempt.

10. Design checklist

  • Contract-first: the .proto is the source of truth; field numbers are write-once; never rename or reuse a number.
  • Prefer unary for domain reads/writes; add server-streaming for bulk query and client-streaming for bulk ingest; use bidi rarely (live sync).
  • Always pass a deadline from the BFF into every outbound call; propagate it to downstream services.
  • Map to real status codes: NOT_FOUND, INVALID_ARGUMENT, ALREADY_EXISTS, UNAVAILABLE, DEADLINE_EXCEEDED, UNAUTHENTICATED/PERMISSION_DENIED.
  • Configure retries only for idempotent-safe calls and choose retryable codes deliberately (UNAVAILABLE, sometimes DEADLINE_EXCEEDED/ABORTED).
  • Make handlers idempotent (dedupe on a request/business key) so retries can't double side effects.
  • Carry context: request-id, tenant, trace context, auth token in metadata; use call credentials for client auth, interceptors for logging/metrics.
  • Encrypt in transit (TLS via mTLS or service mesh) even inside the VPC; never send unauthenticated tokens.
  • BFFs aggregate, domain services stay small and single-purpose; map gRPC errors at the BFF, not leak raw codes to clients verbatim.
