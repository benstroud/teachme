Streaming for Domain APIs

The stream keyword and when a domain service should actually earn its complexity by using it.

The mental model in one sentence

Streaming means a single RPC carries many messages in one direction (or both), flowing over one HTTP/2 stream instead of many separate calls.1

The four call kinds, recap

KindRequestResponseDomain use
Unaryoneonedefault; most domain reads/writes
Server-streamingonemanybulk query / paging a big result
Client-streamingmanyonebulk ingest / batch writes
Bidirectionalmanymanylive sync / chat; use rarely

Server-streaming in the client

const call = client.listOrders({ customer_id: "c_1" });   // returns a stream
call.on("data", (order) => { /* accumulate or forward each Order */ });
call.on("end",  () => { /* stream finished cleanly */ });
call.on("error", (err) => { /* a status code is here */ });

Server-streaming shines when a result can be huge (all orders for a customer) — the server starts sending the first row while it still materializes the rest. The server calls write(order) repeatedly and end() when done. Watch backpressure: a slow BFF resolver should stop pulling from the domain stream when it can't keep up.

Client-streaming for bulk ingest

// client: write many requests, then finish with one response callback
const call = client.submitBatch((err, summary) => { /* one final summary */ });
for (const order of batch) call.write(order);
call.end();

Use it to push a large batch to a domain service and get a single result — e.g. importing a week of inventory.2

Bidirectional: rare by design

Bidi (rpc Sync(stream Req) returns (stream Res)) lets both ends write independently, like a WebSocket. It's powerful for live sync, but costs: harder load-balancing, harder retries/dedup, more state. In a domain layer, reach for it only when streaming both ways is genuinely needed.

Key idea Streaming is a tool, not a default. Prefer unary RPCs — they are simple and retryable. Add streaming when the volume or latency pattern (bulk query, bulk ingest) makes a stream of many messages over one connection materially better.
