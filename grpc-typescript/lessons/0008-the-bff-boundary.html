The BFF Boundary

How your GraphQL and REST BFFs are gRPC clients of the domain layer — and how errors and shapes cross that seam.

The mental model in one sentence

The BFF is the translator: it takes a GraphQL/REST shape from the browser, fans out into multiple gRPC calls to domain services, aggregates the typed results, and maps any gRPC status back into a client-safe error.1

A GraphQL resolver as a gRPC client

// resolver: order + the customer it belongs to
order: async (parent, _args, ctx) => {
  const [order, customer] = await Promise.all([
    ctx.orders.getOrder({ id: parent.orderId },
      { deadline: ctx.deadline }),
    ctx.orders.getCustomer({ id: parent.orderId },
      { deadline: ctx.deadline }),
  ]);
  return { ...order.toObject(), customer: customer.toObject() };
}
  • A single GraphQL field can fan out to several gRPC calls; Promise.all keeps them concurrent (mind your deadlines).
  • Domain services stay small and single-purpose; the BFF owns aggregation and shape — that is its job, not the domain's.2
  • The same pattern holds in a REST BFF: a route handler calls the gRPC client and maps to an HTTP response.

Mapping gRPC errors to the edge

gRPC codeGraphQLREST
NOT_FOUND (5)null / field error404
INVALID_ARGUMENT (3)validation error400
UNAUTHENTICATED (16)authn error401
PERMISSION_DENIED (7)authz error403
DEADLINE_EXCEEDED (4)server error504
UNAVAILABLE (14)server error503

Do the mapping at the BFF, and don't leak internal detail (server addresses, raw messages) verbatim to browsers.

Why browsers don't call gRPC directly

Browsers speak HTTP/1.1, not gRPC's HTTP/2 framing. gRPC-web exists and bridges that gap through a proxy, but it drops most of the transport benefits (binary framing, streaming semantics) and adds a deployment.3 For a service you control end-to-end, the cleaner call is:

Browser → GraphQL/REST BFF → gRPC → domain service.

The BFF is the only gRPC client that matters for your edge.
