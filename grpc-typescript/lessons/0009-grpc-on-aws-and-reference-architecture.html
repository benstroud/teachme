gRPC on AWS & Reference Architecture

Where the domain services run, how they're discovered and encrypted, and the whole picture assembled.

The mental model in one sentence

gRPC needs long-lived HTTP/2 listeners, so on AWS the classic fit is containerized Node domain services on ECS (or EKS) behind an Application Load Balancer that speaks gRPC — not Lambda.1

Hosting: the two realistic AWS options

  • ECS (or EKS) + ALB — recommended. Run each domain service as a container. Register it in a target group using the gRPC target type over HTTP/2; the ALB fronts all instances. Use TLS (HTTPS listener, HTTP/2) publicly, or h2c on a private network where TLS terminates elsewhere or mTLS is handled internally.1
  • API Gateway + Lambda — transcoding. API Gateway can transcode gRPC into REST-style calls that invoke a Lambda. It is serverless-friendly but trades away streaming and HTTP/2 benefits, and only suits unary-shaped domain calls.2

Encryption & service discovery

  • TLS end to end. Encrypt the BFF → domain hop even inside the VPC — mutual TLS (mTLS) or a lightweight mesh/ingress so a caller can't impersonate a BFF.
  • Discovery. BFFs resolve the domain service by name. Options: the ALB's DNS name (DNS resolver, dns:///…) for load-balanced access, or AWS Cloud Map for per-instance discovery with health checks.3
  • Keepalive + health checks. Configure grpc.keepalive so an idle connection doesn't die, and wire the gRPC health-checking protocol (or ALB health checks) so the load balancer drops dead instances.

Observability

Propagate W3C trace context in metadata from the inbound edge request through every BFF → domain hop. Emit OpenTelemetry spans/metrics per RPC (including retry attempts). Because request-id and trace travel in metadata, one user click produces one end-to-end trace across GraphQL BFF, REST BFF, and each domain service.

Putting it together: the reference architecture

             Browser / external clients
                        │  HTTP/1.1 · GraphQL / REST
              ┌─────────▼─────────┐
              │    Edge layer     │
              │  GraphQL BFF      │  REST BFF
              └─────────┬─────────┘
                        │  gRPC over HTTP/2 · TLS · deadlines
                    ┌───▼────┐  ┌──────┐  ┌─────────┐
                    │ orders │  │ cat. │  │ billing │   ← domain
                    │ svc    │  │ svc  │  │ svc     │     services
                    └───┬────┘  └──┬───┘  └────┬────┘
                        │ (ECS / EKS behind an ALB gRPC target)
                    ┌───▼─────────┴────────────▼────┐
                    │  Data stores (DynamoDB, Aurora) │
                    └────────────────────────────────┘
   Context in metadata: authorization · x-request-id ·
                        x-tenant · traceparent (→ OpenTelemetry)
  • Edge stays client-friendly (GraphQL/REST).
  • Domain layer is contract-first gRPC over HTTP/2, each service single-purpose, on ECS behind an ALB.
  • Resilience rides the call: deadlines from every BFF, retries on idempotent-safe codes, idempotent handlers.
  • Context (auth, tenant, trace) is carried in metadata and re-propagated every hop.
