Channels, Resilience, Retries

A client stub talks through a channel; make that hop survive transient faults without corrupting state.

The mental model in one sentence

A channel is a client's virtual connection to a server address — it owns connection pooling, name resolution, and load-balancing config, and a stub rides on it.1 Resilience comes from deadlines, retries, and idempotent handlers.

Channels and stubs

import * as grpc from "@grpc/grpc-js";
import { OrderServiceClient } from "./gen/orders_grpc_pb";

const client = new OrderServiceClient(
  "orders.internal.example:50051",     // name the channel resolves
  grpc.credentials.createInsecure(),   // or createSsl(rootCert)
  { "grpc.keepalive_time_ms": 30000 }  // channel options
);

// every call carries its own deadline
client.getOrder({ id: "ord_1" }, { deadline: new Date(Date.now() + 1500) },
  (err, res) => { /* ... */ });
  • Reuse one channel/stub for many calls; it pools connections rather than opening one per call.
  • The address can be dns:///… for a hostname, or a service-discovery name (AWS Cloud Map / ALB DNS resolves it).

Transparent retry: free but limited

Retries are enabled by default but there is no default retry policy. Without one, gRPC only performs transparent retries — safe because it is certain the work was not processed:2

  • Unlimited while the RPC has never left the client.
  • A single retry if it reached the server library but not your app logic.

That covers connection races but not "server really failed", so you additionally configure a policy for the codes you want retried.

A configured retry policy

const channel = new grpc.Channel("orders:50051", creds, {
  "grpc.service_config": JSON.stringify({
    methodConfig: [{
      name: [{ service: "orders.v1.OrderService" }],
      retryPolicy: {
        maxAttempts: 4,
        initialBackoff: "0.1s",
        maxBackoff: "1s",
        backoffMultiplier: 2,
        retryableStatusCodes: ["UNAVAILABLE"],
      },
    }],
  }),
});

  • Pick retryable codes deliberately — realistically UNAVAILABLE, and sometimes DEADLINE_EXCEEDED/ABORTED.3 Do not blindly retry INVALID_ARGUMENT.
  • Backoff jitter (±20%) is applied automatically so many clients don't hammer a recovering service.
  • Once the server sends a response header, the call is committed — no further retries.2

Retryable calls must be idempotent

A retried call can be executed twice. If the handler performs a side effect (create a charge, decrement stock) a naive retry duplicates it. Make the RPC idempotent: carry a client-supplied request/business key and dedupe on it server-side, so attempt #2 returns the same result instead of a second side effect.
