The proto Contract

Messages, field numbers, and the compatibility rules that let an old server talk to a new client.

The mental model in one sentence

A .proto file is a plain-text schema: message blocks of typed, numbered fields. One tool (protoc) compiles it into data classes for every language, so the same schema generates both your TypeScript client and your TypeScript server.1

Messages: typed, numbered fields

syntax = "proto3";

package orders.v1;

message Address {
  string line1 = 1;
  string city   = 2;
  string zip    = 3;
}

message Order {
  string        id          = 1;
  string        customer_id = 2;
  repeated LineItem items   = 3;   // a list of LineItem
  Address       ship_to     = 4;   // a nested message
  Status        status      = 5;   // an enum
}

enum Status {
  STATUS_UNSPECIFIED = 0;
  STATUS_PLACED      = 1;
  STATUS_FULFILLED   = 2;
}
  • Scalar types to remember: string, bool, bytes, int32/int64, uint32/64, float, double.2
  • repeated makes a field a list. Enums come from a named enum; its first value is 0 (the default).
  • Types can reference other messages in the same file, or imported ones (import "google/protobuf/timestamp.proto";).

Key idea The field number, not the name, is the identity of a field on the wire. Think of it as a write-once database schema key.

Why field numbers make compatibility possible

On the wire a field is identified by its number, encoded as part of a tag: (field << 3) | wire_type.3 Names are only for humans. Because receivers read fields by number and preserve fields they don't recognize, you can evolve a message safely:

  • Add a field with a fresh, unused number → old readers skip it, new readers use it. Backward and forward compatible.
  • Never reuse a number after deleting a field → an old server still thinks number 7 means the old thing and corrupts data. Reserve the number instead.
  • Never rename the meaning of an existing number. Renaming the field name is fine (numbers carry the wire); changing what it means is not.

This is the entire reason versioning is a non-event: the contract evolves by adding numbered fields, not by breaking calls.
