Why gRPC for Domain Services

The hand-rolled JSON hop between your BFFs and your domain services is the class of problem gRPC exists to solve.

The mental model in one sentence

gRPC is a way for one server to call a method on another server as if it were a local object — with a typed, versioned, machine-readable contract between them instead of a drifting pile of JSON.1

Where your architecture actually breaks

Client-facing traffic ends at the edge: a GraphQL BFF and a REST BFF. They request data from a layer of smaller domain services (orders, catalog, inventory, billing). The fracture point is that middle hop — BFF → domain service. Hand-written REST between every pair produces:

  • No contract. The "schema" is whatever a converter and a constructor happen to agree on this week. A field rename in one service silently breaks the caller.
  • Ad-hoc serialization. JSON-in-JSON-out, stringified by hand, parsed by guess, validated nowhere.
  • Per-call overhead. Each call opens another HTTP/1.1 request; fan-out multiplies it.
  • No shared type safety. TypeScript types on each side drift because nothing generates them from one source of truth.
Key idea The client-facing protocols (GraphQL, REST) serve browsers and external clients. The service-to-service protocol can be far more structured, because you control both ends.

What gRPC gives you

PropertyWhat it means for a domain layer
Contract-first IDLThe .proto file is the single source of truth. Services are defined, not discovered by reading code.
CodegenClient stubs and server handlers are generated in TypeScript (and other languages) from the same file — no drift.
Binary encodingProtocol Buffers are small and fast to serialize — less payload per fan-out call.
HTTP/2 transportMultiplexed streams, header compression, and true streaming (see Lesson 7).2
Status codesA typed outcome on every RPC (0–16) instead of "it 500'd".
Cross-languageThe same contract can serve a Go catalog service and a TypeScript orders service.

Where gRPC does NOT belong

  • In the browser. Browsers don't speak HTTP/2 gRPC natively; gRPC-web needs a proxy and loses benefits. Keep gRPC server-side and let the BFFs be its clients.3
  • For public, third-party APIs where clients are unruly and discoverability matters — HTTP/JSON and OpenAPI fit better.
  • Tiny two-service systems where the overhead of a contract layer outweighs the benefit. The payoff comes when several domain services sit under several BFFs.
