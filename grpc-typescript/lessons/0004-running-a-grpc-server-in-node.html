Run a gRPC Server in Node

Implement handlers, surface real status codes, and stop waiting forever.

The mental model in one sentence

A gRPC server mounts one handler per rpc method. Each handler receives the call and finishes by calling callback(err, response) for unary methods.1

A working server

import * as grpc from "@grpc/grpc-js";
import { OrderServiceService } from "./gen/orders_grpc_pb";
import { repository } from "./repository";

const server = new grpc.Server();
server.addService(OrderServiceService, {
  getOrder(call, callback) {
    const found = repository.findById(call.request.id);
    if (!found) {
      return callback(mkError(grpc.status.NOT_FOUND, "order not found"));
    }
    callback(null, found);
  },
});

server.bindAsync("0.0.0.0:50051", grpc.ServerCredentials.createInsecure(),
  (err, port) => {
    if (err) throw err;
    server.start();
    console.log(`listening on :${port}`);
  });

function mkError(code, message) {
  return Object.assign(new Error(message), { code });
}
  • addService(Svc.service, handlers) — the Service object comes from your generated code or @grpc/proto-loader.2
  • For TLS: grpc.ServerCredentials.createSsl(ca, [key, cert]). For h2c behind an internal ALB: insecure on a private network.
  • Handlers for streaming methods differ — Lesson 7.

Errors are status codes, not 500s

Every RPC ends with a status object: an integer code and a message. Reach for the codes your domain actually has:3

Domain situationCode
Input is unusable regardless of stateINVALID_ARGUMENT (3)
Entity missingNOT_FOUND (5)
Create collided with an existing rowALREADY_EXISTS (6)
Auth token missing/invalidUNAUTHENTICATED (16)
Allowed but not permittedPERMISSION_DENIED (7)
System not in required stateFAILED_PRECONDITION (9)
Transient outage, retry meUNAVAILABLE (14)
Ran out of timeDEADLINE_EXCEEDED (4)

Set the code on the error (as above); if you don't, the client sees UNKNOWN (2) — unhelpful for a caller deciding what to do.

Key idea Only codes a handful of codes are ever produced by the library; the rest come from your handlers. Choose them on purpose — a caller's retry logic depends on UNAVAILABLE vs INVALID_ARGUMENT being correct.

Deadlines: the caller owns the clock

A deadline is set by the client — there is no default, so a client can wait forever.4 When the deadline passes, the client fails the call (DEADLINE_EXCEEDED) and the server is told to cancel; your handler should check for cancellation and stop its own work. This is the discipline that keeps fan-out usable: every outbound BFF call carries a deadline.
