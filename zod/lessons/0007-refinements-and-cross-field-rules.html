Refinements and Cross-Field Rules

Some rules cannot be written on a single field: a minimum must not exceed a maximum, and two passwords must match. Refinements add those checks to an object, and point each error at the field that is wrong.

A refinement on an object

.refine(check, options) adds a check that runs after the object's fields have passed. The check returns true or false. The path option decides which field the error is reported against.1

const Range = z
  .object({ min: z.number(), max: z.number() })
  .refine((v) => v.min <= v.max, {
    error: "min must not exceed max",
    path: ["max"],
  });

The rule runs only when the fields themselves are valid. A min that is not a number never reaches the comparison.

superRefine for several issues

.superRefine receives a context and lets you add an issue directly with ctx.addIssue. Use it when one object may produce more than one error, or when you need a specific issue code.

const Password = z
  .object({ password: z.string(), confirm: z.string() })
  .superRefine((v, ctx) => {
    if (v.password !== v.confirm) {
      ctx.addIssue({
        code: "custom",
        message: "Passwords do not match",
        path: ["confirm"],
        input: v.confirm,
      });
    }
  });
Put the error where the user can fix it A password mismatch should point at confirm, not at the whole form. The path is what lets a form highlight the right input.

Check yourself

When does an object-level refinement run?

The refinement runs once the fields are valid, so its comparison sees values of the right type.1

What does the path option of a refinement control?

The path tells the caller which field the issue belongs to, so a form can show the error next to that input.1

Which tool fits a rule that may report more than one issue?

superRefine receives a context and can add several issues, each with its own path and code.1
