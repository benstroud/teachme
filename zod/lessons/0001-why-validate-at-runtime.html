Lesson 1 of 10Zod

Why Validate at Runtime

TypeScript checks your code at compile time. The data that arrives from a request, a file, or an API is only checked by a runtime library, and Zod is that library.

Types disappear when the program runs

TypeScript removes its types when it compiles to JavaScript. A function that says it takes a User has no way to know, at run time, whether the object it receives really has a name and an age. The compiler checked your code, not the data.1

This matters most at the edges of a program. A request body, a parsed config file, or a response from another service arrives as data of unknown shape. Calling response.json() returns whatever the server sent, and the type you write on the result is a promise that the compiler cannot keep.

What Zod does

Zod is a TypeScript-first validation library. You describe the shape once, as a schema that exists at run time. Zod checks incoming data against that schema, and it derives the static type from the same definition, so the check and the type cannot disagree.1

import { z } from "zod";

const User = z.object({ name: z.string(), age: z.number() });
type User = z.infer<typeof User>;   // derived from the schema, not written twice
Two jobs, one definition A schema checks data at run time and gives you a type at compile time. Writing the type by hand and the check separately means they can drift apart.

Check yourself

Why can a TypeScript type not protect a program from bad request data?

TypeScript types exist only at compile time. At run time the data is just a value, so nothing checks it against the type.

What does response.json() give you, as far as the compiler knows?

The JSON is parsed, but nothing checks its shape. Any type you assign to the result is an unverified promise.

What is the main idea behind Zod?

Zod defines the shape once as a runtime value, checks data against it, and infers the TypeScript type from the same definition.1
