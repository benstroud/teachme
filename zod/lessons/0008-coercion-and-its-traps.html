Coercion and Its Traps

Query strings and form fields arrive as text, so a number must be converted before it is checked. z.coerce does that conversion, and it is convenient precisely because it can turn bad input into good-looking values.

What coercion does

z.coerce.number() converts the input with Number(...) before it checks the result. The docs note that the input type of a coerced schema is unknown by default.1

const Quantity = z.coerce.number().int().positive();
Quantity.parse("3");   // 3

The trap: empty means zero

Number("") is 0. A field that the user left blank becomes a valid number, if the schema allows zero. The check passes, and the program now believes the user asked for nothing, which is not the same as "not provided".

const Count = z.coerce.number().int().nonnegative();
Count.parse("");   // 0, and it passes

The fix is to turn the empty string into undefined before the coercion, so the schema can reject it as missing. The lab uses z.preprocess for this.

const SafeQuantity = z.preprocess(
  (v) => (v === "" ? undefined : v),
  z.coerce.number().int().positive(),
);
Coerce only where the input is text Use coercion at a boundary where you know the input is a string, such as a query string. Coercing a JSON body with a value that could be a string or a number hides the mistake you want to catch.

Check yourself

What does z.coerce.number().nonnegative() return for the empty string?

Number("") is 0. Zero is nonnegative, so the value passes and the blank field is accepted as 0.1

Why does the SafeQuantity example use z.preprocess?

Preprocess maps the empty string to undefined first, so a missing value is rejected rather than read as zero.

Where is coercion most appropriate?

A query string is text, so converting it is the job coercion does. A typed JSON body should be checked, not converted, so a wrong type is caught.
