Boundaries and JSON Schema

Zod earns its place at the edges of a program: request handlers, config loaders, and integrations. At those edges, a failed check becomes a clear response, and the same schema can be exported as JSON Schema for other tools.

Validate at the edge, trust inside

Parse data once, where it enters the program, and pass the typed result inward. Inside the program, the type is the contract, so you do not re-check the same value at every step. A handler that parses its body and returns a 400 for failures keeps the rest of the code simple.1

export function handleCreateUser(body: unknown) {
  const result = UserSchema.safeParse(body);
  if (!result.success) {
    return { status: 400, issues: result.error.issues.map((i) => `${i.path.join(".")}: ${i.message}`) };
  }
  return { status: 201, user: result.data };
}

Export the schema as JSON Schema

z.toJSONSchema converts a schema to JSON Schema, so documentation and other tools can share the same definition. The default target is draft 2020-12. Some Zod types have no JSON Schema equivalent, and the default is to throw for them.2

const js = z.toJSONSchema(UserSchema);
// js.type === "object", with properties and a list of required keys
One definition, two consumers The schema checks data at run time, and the exported JSON Schema documents the same rules for a client or an API reference. Keeping one source avoids the documentation drifting from the check.

Check yourself

Where is parsing with Zod most useful?

Parse once where data enters, then pass the typed result inward. Re-checking at every step adds cost without adding safety.

What does z.toJSONSchema produce?

It converts the Zod schema to JSON Schema, so other tools can read the same definition.2

What does the failing branch of handleCreateUser return?

It returns a 400 status with issue strings built from each issue's path and message.
