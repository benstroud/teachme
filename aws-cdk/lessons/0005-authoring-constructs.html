Authoring Constructs

Package a bundle of resources behind a small, typed interface — constructs you write compose like any other.

The mental model in one sentence

A construct is a class that extends Construct, receives (scope, id, props), adds child constructs with this as their scope, and exposes what consumers need as readonly properties.1

A custom construct

import { Construct } from 'constructs';
import { Bucket, BucketProps } from 'aws-cdk-lib/aws-s3';
import { Topic } from 'aws-cdk-lib/aws-sns';
import { SnsDestination } from 'aws-cdk-lib/aws-s3-notifications';

export interface NotifyingBucketProps extends BucketProps {
  prefix?: string;
}

export class NotifyingBucket extends Construct {
  public readonly topic: Topic;               // expose for consumers
  public readonly bucket: Bucket;

  constructor(scope: Construct, id: string, props?: NotifyingBucketProps) {
    super(scope, id);
    this.bucket = new Bucket(this, 'bucket', props);          // child of this
    this.topic = new Topic(this, 'topic');
    if (props?.prefix) {
      this.bucket.addObjectCreatedNotification(new SnsDestination(this.topic), { prefix: props.prefix });
    }
  }
}

Every construct library class follows the same pattern: instantiated with (scope, id, props), where props conforms to a dedicated interface like BucketProps.

Compose, don't scatter

The power of custom constructs is reuse: define NotifyingBucket once, and any stack can instantiate it — a bucket, a topic, and the wiring all come as one unit. You can extend an existing interface (as above) to add your own props.2

Key idea Scope is this inside the construct, so its children land in the tree under it, giving them a stable path and (through synthesis) stable CloudFormation logical IDs.

Expose and consume

Consumers reach the inner resources through public readonly fields — e.g. images.topic.addSubscription(...) — so encapsulation stays tidy without hiding what integration code needs.1
