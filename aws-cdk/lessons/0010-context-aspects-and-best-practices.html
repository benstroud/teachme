Context, Aspects & Best Practices

Parameterize with context, apply cross-cutting policy with Aspects, and run a maintainable CDK app.

The mental model in one sentence

Use context for config, Aspects for cross-cutting changes across the tree, and treat infrastructure like production code — tested, reviewed, committed.1

Context: configuration at the edge

// cdk.json
{ "context": { "appName": "my-app", "dev": true } }

// read it in a construct
const name = this.node.tryGetContext('appName');
const isDev = this.node.tryGetContext('dev') === true;

Context is a key/value store you can set in cdk.json, via CLI flags, or programmatically. It keeps environment-specific values out of your code so one app can deploy to many environments.2

Key idea Don't hardcode accounts, regions, or feature flags deep in code. Route them through context (or props), so a new environment is a config change, not a code change.

Aspects: policy across the whole tree

An Aspect is a visitor CDK applies to every node in the construct tree — the natural home for cross-cutting concerns like mandatory tagging, security checks, or naming conventions.2

import { Aspects, Tag } from 'aws-cdk-lib';
Aspects.of(app).add(new Tag('team', 'core'));   // tag everything

Best practices for a maintainable app

  • Treat infrastructure as code: source control, reviews, and tests.1
  • Prefer L2 constructs; go L1/escape hatch only when you must.1
  • Split into stacks by environment and lifecycle; set env explicitly.2
  • Avoid hardcoding; pass props and use context and Tokens.
  • Run cdk diff before cdk deploy, and be deliberate about destructive changes.2
