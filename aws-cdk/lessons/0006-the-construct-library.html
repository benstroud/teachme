The Construct Library

aws-cdk-lib ships curated constructs for AWS services — import a module, build a resource, and reach down to L1 when you must.

The mental model in one sentence

In v2, all the curated constructs live in one package, aws-cdk-lib, organized into per-service namespaces (e.g. aws-s3, aws-lambda, aws-iam) you import and use like any TypeScript module.1

Import and build

import * as s3 from 'aws-cdk-lib/aws-s3';
import * as lambda from 'aws-cdk-lib/aws-lambda';
import * as iam from 'aws-cdk-lib/aws-iam';

const bucket = new s3.Bucket(this, 'Bucket', { versioned: true });
const role = new iam.Role(this, 'Role', {
  assumedBy: new iam.ServicePrincipal('lambda.amazonaws.com'),
});
const fn = new lambda.Function(this, 'Fn', {
  runtime: lambda.Runtime.NODEJS_20_X,
  handler: 'index.handler',
  code: lambda.Code.fromAsset('src'),
  role,
});

Each class embodies an L2 construct: defaults, best-practice security, and helper methods are baked in, so a few lines produce a safe, working resource.2

Key idea The library is the interface you compose against. If you can find the service module, you can build its resources; the props interfaces tell you (via editor completions) exactly what each construct accepts.

Reaching down to L1 / the escape hatch

When an L2 lacks a control, every construct exposes its underlying L1 (e.g. bucket.node.defaultChild as a CfnBucket) or you can add the L1 directly. This is how you get exact CloudFormation property fidelity without leaving CDK.2

Know your imports, keep them tidy

In TypeScript, import only the modules you use and lean on your IDE's completion for props. Because everything is typed, a wrong property fails at compile time rather than at deploy time — one of CDK's big advantages over hand-written templates.1
