Lesson 03 · Jest + TypeScript

Mocks Done Right

Type-safe mocks, the jest.Mocked<T> family, and the one decision that separates a senior's mocks from everyone else's.

★ Mission link: builds on Lesson 02 (the type-level trap: expect is loosely typed). Mocks are where that trap becomes the whole story — an untyped mock lets a refactor silently break a test, and you find out in production. The win today: write mocks that the compiler enforces, so a signature change either updates the mock or fails the build.

The two layers of mocking

Jest mocking has two layers, and seniors keep them straight:1

  • Function mocks — jest.fn() creates a spy you control. Use for: callbacks, injected dependencies, standalone functions.
  • Module mocks — jest.mock('path') replaces an entire module with an auto-mock or a factory. Use for: external services, fs, fetch, anything imported.

Both have TypeScript-specific patterns. The failure mode is the same in both: an untyped mock that doesn't match the real thing.

jest.fn: type it or regret it

jest.fn() with no arguments is loosely typed. The fix is a generic — either infer from an implementation, or state the signature explicitly:2

<code>function add(a: number, b: number): number { return a + b; }

// ❌ untyped — mockImplementation params are any
const bad = jest.fn();
bad.mockImplementation((a, b) => a + b);  // a, b are any

// ✅ infer from implementation
const ok1 = jest.fn((a: number, b: number) => a + b);

// ✅ explicit generic — matches the real function's type
const ok2 = jest.fn<typeof add>();
ok2.mockImplementation((a, b) => a + b);  // a, b inferred as number</code>

The jest.fn<typeof add>() pattern is the senior default: the mock's signature mirrors the real function. When add gains a third parameter, the mock fails to compile until you update it — which is exactly what you want.2

Async return shorthands are generic too: jest.fn<() => Promise<number>>().mockResolvedValue(43) or jest.fn<() => string>().mockReturnValue('x'). The generic is the whole signature, not just the return type — note the () => inside the angle brackets.2

The jest.Mocked<T> family

After jest.mock('module'), the import binding still has the original TypeScript type — .mock.calls isn't visible on it. You need to wrap it. Jest provides a family of utility types for this:2

Utility typeWrapsUse for
jest.Mocked<T>Any — deep-wraps nestedThe general case
jest.MockedFunction<T>A functionWhen T is a standalone fn
jest.MockedClass<T>A classClass constructors + methods
jest.MockedObject<T>An objectObjects with fn properties
<code>jest.mock('./db');
import { saveUser } from './db';

// saveUser's TS type is still the real one — .mock is not visible
// Option A: cast
(const m = saveUser as jest.MockedFunction<typeof saveUser>);

// Option B: the runtime helper (preferred — no cast)
const m = jest.mocked(saveUser);
m.mockImplementation(async () => true);
expect(m).toHaveBeenCalledWith('Ada');</code>

jest.mocked(source) is the runtime helper — it returns the source object wrapped with mock types. Prefer it over the cast: it deep-wraps nested members by default, and you can pass { shallow: true } to wrap only the top level.2

jest.mock factories: type the whole module

When you provide a factory, TypeScript checks its return against the real module shape. Use a generic on jest.mock to get that checking:3

<code>jest.mock<typeof import('./random')>('./random', () => ({
  __esModule: true,          // ← required for default exports
  getRandom: jest.fn(() => 10),
}));</code>

Two traps here, both documented:3

  1. Missing __esModule: true — for modules with a default export, the factory must include it. Babel/TS normally generate this; in a manual factory you set it yourself.
  2. Partial mock fails the type check — if you mock only one export, the factory return doesn't match the full module type. Fix: spread the actual module: return { __esModule: true, ...jest.requireActual('./m'), getRandom: jest.fn() }.

The senior decision: contract vs implementation

This is the one that separates seniors. You have two things you can mock:

  • The contract — the interface your code depends on. "A thing with a save() method that returns Promise<boolean>." Mock this when you own the boundary.
  • The implementation — the specific module your code imports. jest.mock('./db') replaces a concrete dependency. Mock this when you don't control the boundary.

The senior rule: mock the contract, not the implementation, whenever you can. If your code takes a Database interface and you inject a jest.fn() typed against it, you test that your code works with any Database — and a refactor of the real DB module can't break your test. If you jest.mock('./db') instead, your test is now coupled to a specific module's export shape; rename an export and the test breaks even if the contract is unchanged.4

Implementation mocks have a cost: they couple your test to a module's internal structure. Every jest.mock('path') is a dependency on that path existing and that export shape holding. Reach for dependency injection (mock the contract) for code you own; reach for jest.mock for boundaries you don't control (external packages, Node built-ins like fs).
