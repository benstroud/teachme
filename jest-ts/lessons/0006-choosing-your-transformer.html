Choosing Your Transformer

ts-jest vs @swc/jest vs babel-jest — a decision framework, not a ranking.

★ Mission link: closes the transformer thread opened in Lesson 01 and configured in Lesson 05. The mission says "choose between ts-jest, @swc/jest, and babel-jest and justify the trade-off" — this is that justification. The win today: when someone asks "why did you pick that transformer?" you have an answer that isn't "it was the first result."

The axis that matters

You learned in Lesson 01 that Jest's default transformer is babel-jest, which strips types without checking them. The three options differ on one axis: where does type-checking happen?12

TransformerType-checks in tests?SpeedType-check must happen…
ts-jestYes (runs tsc)Slowest— (it's in the test run)
babel-jestNo (strips types)FastSeparately: tsc --noEmit in CI
@swc/jestNo (strips via SWC)FastestSeparately: tsc --noEmit in CI

That's the whole decision. Everything else is secondary. The question is not "which is best" — it's "where do I want type errors caught, and how fast do my tests need to run?"

ts-jest: the safe default

Choose ts-jest when you want type errors to fail the test run itself.2 This is the behavior you saw in Lesson 01: pass a string where a number is expected, and Jest fails before running with a TS diagnostic — not a runtime assertion failure.

  • Pro: one source of truth — jest catches both type errors and test failures. No separate tsc step needed in CI.
  • Con: slowest. tsc runs per file. On large suites (thousands of tests) this is felt. ts-jest 29.4 supports Jest 30 via peer deps.3
  • Use when: small-to-medium codebase, you value the single-source-of-truth model, or CI doesn't already run tsc --noEmit.

babel-jest: the default you already have

Choose babel-jest when you're fine type-checking elsewhere and want Jest to just run code.1 This is Jest's out-of-the-box transformer — zero config if you add @babel/preset-typescript.

  • Pro: fast, zero-friction, ecosystem-standard. Babel also injects the mock-hoisting plugin Jest needs.1
  • Con: no type-checking in tests. A type-broken test runs and reports green. You must add tsc --noEmit to CI — or accept that type errors show up in review/CI, not in jest.
  • Use when: your CI already runs tsc, you have a fast suite that needs to stay fast, or you're in a Babel ecosystem already.

@swc/jest: the speed option

Choose @swc/jest when test speed is the bottleneck.4 SWC is a Rust-based compiler — the fastest option. Same trade-off as babel-jest: no type-checking, so run tsc --noEmit separately.

  • Pro: fastest. SWC's own docs call it a "drop-in Rust replacement" for ts-jest.4
  • Con: still pre-1.0 (0.2.39 as of 2025). No type-checking. Not mentioned in official Jest docs.1
  • Use when: large suite where seconds matter, you type-check in CI already, and you're comfortable with a pre-1.0 dependency.
The "where does type-checking happen" test: ask yourself — if I delete tsc --noEmit from CI, do type errors still get caught? With ts-jest: yes, in the test run. With babel-jest or @swc/jest: no — nothing checks types. That's the decision. If your CI already runs tsc, the speed options lose their downside.

The hybrid: ts-jest with isolatedModules

There's a fourth path that's easy to miss: keep ts-jest, but set isolatedModules: true.5 Now ts-jest transpiles per-file without a project-wide type check — you get ts-jest's ESM handling and config integration, but the speed of transpile-only. Type-checking moves to your editor and CI tsc --noEmit. This is the "I want ts-jest's ergonomics but babel-jest's speed" option.

The decision framework

<code># 1. Does your CI already run `tsc --noEmit`?
#    YES → babel-jest or @swc/jest (speed wins, no lost safety)
#    NO  → ts-jest (or add tsc --noEmit to CI, then reconsider)

# 2. Is test speed a felt pain?
#    YES & CI has tsc → @swc/jest
#    NO  → babel-jest (or ts-jest if no CI tsc)

# 3. Want ts-jest ergonomics but transpile-only speed?
#    → ts-jest with isolatedModules: true

# 4. Default when unsure?
#    → ts-jest. It's the only one that type-checks in tests.</code>
