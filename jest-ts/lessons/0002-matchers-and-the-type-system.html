Matchers & the Type System

The matcher vocabulary, what each one actually checks, and how to write tests a refactor can't silently break.

★ Mission link: builds on Lesson 01 (ts-jest type-checks tests). If the transformer is the bedrock, matchers are the vocabulary — the words you reach for without docs. The win today: know which matcher to grab for any assertion, and understand the one type-level trap that catches seniors and juniors alike.

The two matchers you must never confuse

toBe and toEqual look similar. They are not.

<code>const a = { x: 1 };
const b = { x: 1 };

expect(a).toBe(b);     // FAILS — different object references
expect(a).toEqual(b);  // passes — same structure & values</code>

toBe uses Object.is — reference identity for objects, value equality for primitives.1 toEqual does a deep recursive equality check, ignoring undefined properties and sparseness.2 The rule: use toBe for primitives and "is this the same object," toEqual for "do these two objects have the same shape and values." Getting this wrong produces tests that pass when they shouldn't, or fail mysteriously on day two.

Why Object.is not ===? Object.is(NaN, NaN) is true; NaN === NaN is false. So expect(NaN).toBe(NaN) passes — toBe catches NaN where === would miss it. This is a deliberate Jest improvement over raw JS equality.1

toEqual vs toStrictEqual — the senior trap

This is the one that catches people. toEqual ignores undefined properties and sparseness. toStrictEqual does not.2

<code>expect({ x: 1, y: undefined }).toEqual({ x: 1 });           // passes
expect({ x: 1, y: undefined }).toStrictEqual({ x: 1 });     // FAILS — extra key</code>

Use toStrictEqual when the exact shape matters — API responses where an extra undefined field would break a consumer, serialization, or a type guard. Use toEqual when you care about the meaningful values and don't want spurious failures from undefined drift.

The type-level trap: expect is not type-safe by default

Here's the thing that surprises seniors coming to Jest+TS: expect accepts any. You can write nonsense that compiles and passes:

<code>const getUser = (id: number): { name: string } => ({ name: 'Ada' });

// this compiles — and tests a property that doesn't exist on the type
expect(getUser(1)).toEqual({ nmae: 'Ada' });  // typo! FAILS at runtime</code>

The runtime catches the typo (good — that's toEqual doing its job). But TypeScript didn't catch it before runtime, because expect(actual: any) — the matcher chain is loosely typed. This is why you pair Jest with TS discipline: the code under test is type-checked (ts-jest from Lesson 01), so the function's return type is enforced. The assertion itself is where you stay vigilant.

Mitigation: type the actual explicitly when it matters — const result: ReturnType<typeof getUser> = getUser(1); expect(result).toEqual({ name: 'Ada' }). Now a typo in the expected object is a compile error against the real return type, not just a runtime failure. This is the senior pattern: use the type system to guard the expected side, since Jest doesn't guard it for you.

Custom matchers (when the built-ins aren't enough)

You can extend expect with custom matchers. The TS pattern uses expect.extend plus an interface merge:2

<code>declare global {
  namespace jest {
    interface Matchers<R> {
      toBeWithinRange(floor: number, ceiling: number): R;
    }
  }
}

expect.extend({
  toBeWithinRange(received, floor, ceiling) {
    const pass = received >= floor && received <= ceiling;
    return {
      pass,
      message: () => pass
        ? `expected ${received} not to be within range ${floor}–${ceiling}`
        : `expected ${received} to be within range ${floor}–${ceiling}`,
    };
  },
});

// now typed: toBeWithinRange(n: number, m: number)
expect(5).toBeWithinRange(1, 10);</code>

The declare global block is what makes the matcher type-safe — without it, TS doesn't know toBeWithinRange exists on the Matchers chain. Put this in a .d.ts or a setup file that's in your tsconfig.
