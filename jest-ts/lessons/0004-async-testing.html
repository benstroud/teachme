Async Testing

Four patterns for async code, the silent-pass trap, and why resolves/rejects are safer than they look.

★ Mission link: builds on Lesson 03 (typed mocks are the return values you control here). Async testing is where juniors write tests that silently pass — green check, no assertion ever ran. The win today: know all four async patterns, know which one is the trap, and never write a test that passes because it didn't wait.

The trap: a test that passes by not running

This is the most important thing in this lesson. This test passes, and it's wrong:

<code>// ❌ SILENT PASS — the assertion never runs
test('fetches a user', () => {
  const promise = fetchUser(1);
  promise.then(user => {
    expect(user.name).toBe('Ada');   // never reached before test ends
  });
});</code>

The test function returns undefined (not the promise). Jest sees the function complete, runs zero assertions, and reports pass. The .then callback runs after the test has already finished.1

The fix is one of four patterns — and the choice matters.

The four patterns

Jest supports four async patterns. All are legitimate; the last two are the senior defaults.1

1. Return the promise

<code>test('fetches a user', () => {
  return fetchUser(1).then(user => {   // ← return
    expect(user.name).toBe('Ada');
  });
});</code>

The return is the whole fix. Jest waits for the returned promise. If it rejects, the test fails. Simple, but easy to forget — which is why the next patterns exist.

2. .resolves / .rejects matchers

<code>test('fetches a user', async () => {
  await expect(fetchUser(1)).resolves.toMatchObject({ name: 'Ada' });
});

test('rejects for missing id', async () => {
  await expect(fetchUser(0)).rejects.toThrow('not found');
});</code>

You must await these. Without await, the matcher returns a promise Jest never waits on — and you're back to the silent-pass trap, but now with a deceptively modern-looking API.1 The await is not optional.

3. async/await (the senior default)

<code>test('fetches a user', async () => {
  const user = await fetchUser(1);
  expect(user.name).toBe('Ada');
});</code>

This is the cleanest pattern: the async function returns a promise implicitly, Jest waits for it, and the assertion runs before the test completes. If fetchUser rejects, the rejection fails the test — no .catch needed. Make this your default.

4. Callbacks with done (legacy)

<code>test('calls back with a user', done => {
  fetchUserCb(1, user => {
    expect(user.name).toBe('Ada');
    done();   // ← tells Jest to wait
  });
});</code>

The done callback is the old callback-era pattern. Jest waits until done() is called. If you forget it, silent pass. Prefer promises/async — done exists for APIs that don't return promises.1

Order matters: in the done pattern, expect before done(). If the assertion throws, done is never called and the test times out — which is at least a failure, but a confusing one. For this reason, prefer async/await wherever the API allows it.

Rejections: don't swallow them

A subtle trap with async/await: a rejected promise you don't await is an unhandled rejection, not a test failure. Use .rejects to assert rejection explicitly:

<code>// ❌ doesn't assert rejection — might not reject at all
test('rejects for bad id', async () => {
  await fetchUser(0).catch(e => expect(e).toBeDefined());
});  // if it DOESN'T throw, the catch never runs — silent pass

// ✅ asserts rejection explicitly
test('rejects for bad id', async () => {
  await expect(fetchUser(0)).rejects.toThrow('not found');
});  // if it resolves, the test fails — no silent pass</code>

Fake timers: control the clock

For code using setTimeout, setInterval, Date, or requestAnimationFrame, use fake timers:2

<code>import { setTimeout as setTimeoutReal } from 'timers/promises';

test('runs after delay', async () => {
  jest.useFakeTimers();
  const spy = jest.fn();
  setTimeout(spy, 1000);

  jest.advanceTimersByTime(1000);   // ← jump forward
  expect(spy).toHaveBeenCalled();

  jest.useRealTimers();             // ← always restore
});</code>

Pair fake timers with beforeEach(() => jest.useFakeTimers()) and afterEach(() => jest.useRealTimers()) so a timer leak in one test can't poison the next. For async functions that await a timer, use jest.advanceTimersByTimeAsync (Jest 29+) — the plain version doesn't flush microtasks.
