Testing Like a Senior

Structure, what not to test, and the judgment that turns the tools into a safety net instead of a tax.

★ Mission link: this is the capstone — the "testing like a senior" success criterion. Every prior lesson was a tool: matchers (02), mocks (03), async (04), config (05), transformer (06). The tools don't make you senior; the judgment does. The win today: know what to test, what to skip, and how to write tests that survive a refactor without being rewritten.

Arrange-Act-Assert: the structure that ages well

Every test has three phases. Seniors make them visible:1

<code>test('total includes discount', () => {
  // Arrange — set up the world
  const cart = [{ price: 30 }, { price: 20 }];
  const discount = 0.1;

  // Act — the one thing under test
  const total = computeTotal(cart, discount);

  // Assert — the behavior you care about
  expect(total).toBe(45);
});</code>

One Act line. One behavior per test. If you can't describe the test in one sentence ("total includes discount"), it's testing too much. The structure isn't dogma — it's a smell detector. When your Arrange section is longer than the rest, your code has too many dependencies. When your Act section has three calls, you're testing a flow, not a unit.

Test behavior, not implementation

This is the single most-cited senior testing principle, and the one that separates good test suites from ones everyone hates.2

<code>// ❌ tests implementation — breaks on refactor
test('sorts by calling quickSort', () => {
  const spy = jest.spyOn(utils, 'quickSort');
  sortItems(items);
  expect(spy).toHaveBeenCalled();   // breaks if you switch to merge sort
});

// ✅ tests behavior — survives refactor
test('sorts items ascending', () => {
  const result = sortItems([3, 1, 2]);
  expect(result).toEqual([1, 2, 3]);   // survives any algorithm change
});</code>

The first test breaks when you swap quickSort for mergeSort — even though the behavior is identical. That's a test that resists refactoring, which is the opposite of what you want. The second test passes regardless of internal algorithm, because it tests the contract: put in [3,1,2], get out [1,2,3].2

How to spot an implementation test: it asserts that something was called rather than what the result is. expect(spy).toHaveBeenCalled() is the smell. Spy on the boundary (a network call, a DB write) — not on your own code's internal functions.

What not to test

Seniors skip more tests than they write. Here's what doesn't earn its keep:2

  • Getters/setters that just assign. If a property has no logic, testing obj.x = 5; expect(obj.x).toBe(5) tests JavaScript, not your code.
  • Framework internals. Don't test that React.useState re-renders, or that Array.map iterates. Test your code's behavior.
  • Third-party libraries. If lodash.sortBy breaks, that's lodash's problem. Test that you called it correctly, not that it sorts.
  • Constants and config. Testing that MAX_RETRIES = 3 is 3 locks in a number that should be free to change.
  • Implementation of private methods. If it's not exported, it's not a contract. Test it through the public interface.

One assertion per behavior (not per test)

The old rule "one assertion per test" is too rigid. The real rule: one behavior per test. A behavior might need several assertions to verify:1

<code>test('rejects invalid email and logs the attempt', () => {
  const logger = jest.fn();
  const result = validateEmail('not-an-email', logger);

  expect(result.valid).toBe(false);          // behavior: rejects
  expect(result.error).toMatch(/email/i);    // behavior: right reason
  expect(logger).toHaveBeenCalledWith({ invalid: 'not-an-email' });  // behavior: logs
});</code>

These three assertions verify one behavior: "invalid input is rejected and logged." That's fine. What you avoid is testing two different behaviors in one test — "rejects invalid email AND accepts valid email" — because when it fails, you don't know which broke.

Refactor-resilience: the test-suite quality bar

The ultimate test of a test suite: can you refactor the code without rewriting the tests?2 If every internal rename breaks a test, the suite is a chain around the code's ankles. If tests focus on behavior and contracts (Lesson 03), they survive refactors. The metrics that matter:

  • Coupling: how many tests break when you change an internal detail that doesn't affect behavior? Target: zero.
  • Signal: when a test fails, does it tell you what broke and where? A test named "works" tells you nothing; one named "rejects expired tokens with 401" tells you everything.
  • Speed: slow suites get skipped. A suite that takes 30 seconds is one that nobody runs. This is where the transformer choice (Lesson 06) bites.

The senior's testing loop

<code># 1. What's the behavior? (one sentence)
# 2. What's the simplest arrange that exercises it?
# 3. One act — the single call under test
# 4. Assert the result, not the call (unless it's a boundary)
# 5. Name the test for what it verifies, not what it does
# 6. Ask: would this survive a refactor? If not, rewrite it.</code>
