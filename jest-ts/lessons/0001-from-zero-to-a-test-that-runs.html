Lesson 01 · Jest + TypeScript

From Zero to a Test That Runs

Install, configure, and write your first typed test — and understand the one decision that quietly shapes everything else.

★ Mission link: this is the bedrock of the testing track — the equivalent of Types as Sets for your type-level arc. Every later lesson (matchers, mocks, async, config) assumes you can set up a Jest+TS project and explain why it's configured that way. The win today: one test that compiles, runs, and passes — plus the vocabulary to choose between the three transformers.

The thing nobody tells you first

Jest does not understand TypeScript out of the box. Its default transformer is babel-jest, which strips type annotations and runs the code — it never type-checks anything.1 So this passes under a default setup:

<code>// this has a type error AND a logic error — but passes under babel-jest
test('adds numbers', () => {
  const x: number = "five" as any;  // string in number's clothes
  expect(x + 1).toBe("five1");        // not what you meant — green check
});</code>

The fix is to choose a transformer. This is the first senior decision, and it has three answers:12

TransformerType-checks?SpeedWhen to reach for it
ts-jest Yes (runs tsc) Slowest You want compile-time safety in tests. Default for typed codebases.
babel-jest No (strips types) Fast Jest's default. Fine if your editor/CI type-checks separately.
@swc/jest No (strips via SWC) Fastest Large suites where test speed is the bottleneck; type-check elsewhere.
Senior tell: the choice is not "which is best" — it's "where does type-checking happen?" If ts-jest checks inside the test run, you catch type errors in jest itself. If you use babel-jest or @swc/jest, you need a separate tsc --noEmit step in CI — because the test runner will happily run type-broken code and report green.2

Set it up (ts-jest, the safe default)

You need four things: Jest, TypeScript, a type provider for Jest's globals, and the transformer. Versions verified 2026-08-06: Jest 30.4, ts-jest 29.4 (peers jest ^29 || ^30 — compatible).3

<code># install
npm install --save-dev jest ts-jest typescript @types/jest

# generate a Jest config with ts-jest preset
npx ts-jest config:init</code>

That init writes a jest.config.js with one load-bearing line:

<code>export default {
  preset: 'ts-jest',   // ← the transformer. swap for '@swc/jest' or remove for babel-jest
  testEnvironment: 'node',
};</code>

Under the hood, preset: 'ts-jest' expands to a transform entry that maps \\.[jt]sx?$ files through ts-jest's transformer.4 That's the whole mechanism: a regex picks files, a transformer compiles them. Everything else is configuration around that one hook.

Senior nuance (2026): the preset: 'ts-jest' string is the legacy form. The current ts-jest docs recommend preset-creator functions — createDefaultPreset(), createDefaultEsmPreset(), etc. — which return the transform object directly so you can extend it.5 The string preset still works (and config:init generates it), but if you need custom transform config, ts-jest's own docs say to remove preset and use the function form instead.5 For now, the string form is fine — we'll switch to the function form when we need ESM or custom options in Lesson 05.

Your first typed test

Two files. Put them next to each other so imports are short:

<code>// sum.ts — the code under test
export function sum(a: number, b: number): number {
  return a + b;
}</code>
<code>// sum.test.ts
import { sum } from './sum';

test('sum adds two numbers', () => {
  expect(sum(2, 3)).toBe(5);
});</code>

Run it:

<code>npx jest</code>

You should see 1 passed. Now — and this is the point of using ts-jest — break the types on purpose:

<code>// change the test to pass a string where a number is expected:
expect(sum("2", 3)).toBe(5);  // ← type error</code>

Under ts-jest, Jest now fails before running with a TypeScript diagnostic — not a runtime assertion failure, a compile error. That's the difference: you found the bug at the type layer, not the test layer. This is why ts-jest is the safe default for a typed codebase.2

Two ways to get the globals typed

test, expect, jest are global functions. There are two ways TypeScript can know about them:1

  • Globals (default): install @types/jest and the globals are typed everywhere. No import needed. This is what the test above relies on.
  • Explicit imports: use @jest/globals and import { test, expect } from '@jest/globals'. More verbose, but the types are versioned with Jest itself and there's no global ambient pollution. Some teams prefer this for monorepos.

Both work. The choice is style + tooling, not correctness. Pick one per project and be consistent.
