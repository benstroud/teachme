tsconfig vs Jest config, path aliases, ESM mode, and the preset-creator functions we deferred from Lesson 01.

Two configs, one goal

You have two config files. They look related; they serve different masters:12

FileWho reads itWhat it controls
tsconfig.jsontsc, your editor, ts-jestHow TS is compiled: module, target, paths, strict, esModuleInterop
jest.config.tsJestHow tests run: transform, preset, moduleNameMapper, testEnvironment

The overlap is the transformer — ts-jest reads your tsconfig to know how to compile. Everything else is separate. A common senior mistake: change tsconfig paths and forget that Jest has its own resolution layer.

The preset-creator functions (the modern form)

In Lesson 01 we used preset: 'ts-jest' — the legacy string. The current ts-jest docs recommend preset-creator functions instead:2

<code>// jest.config.ts — the modern form
import type { Config } from 'jest';
import { createDefaultPreset } from 'ts-jest';

const config: Config = {
  ...createDefaultPreset(),   // ← { transform: { '^.+\\.tsx?$': ['ts-jest', {}] } }
  testEnvironment: 'node',
};

export default config;</code>

The function returns the transform object directly, so you can spread it and override. For ESM, swap to createDefaultEsmPreset(). The docs are explicit: if you use custom transform config, remove preset from your Jest config — mixing both causes "Jest doesn't transform files correctly."2 Options (tsconfig, diagnostics, isolatedModules, useESM) live in the transform tuple's second element:

<code>const config: Config = {
  ...createDefaultPreset({
    tsconfig: 'tsconfig.test.json',
    diagnostics: false,          // skip type-checking (transpile-only)
    isolatedModules: true,        // ← per-file transpile, no project-wide check
  }),
  testEnvironment: 'node',
};</code>

isolatedModules: true disables type-checking — it's the ts-jest equivalent of switching to babel-jest or @swc/jest, but without changing transformers. Use it when you want ts-jest's ESM handling but type-check elsewhere.3

Path aliases: pathsToModuleNameMapper

The classic pain: tsconfig has paths like @/* -> ./src/*, your code imports @/db, and Jest can't resolve it. The fix is moduleNameMapper — but don't write it by hand. ts-jest ships a converter:4

<code>// jest.config.ts
import { pathsToModuleNameMapper } from 'ts-jest';
import { compilerOptions } from './tsconfig.json';

const config: Config = {
  ...createDefaultPreset(),
  roots: ['<rootDir>'],
  modulePaths: [compilerOptions.baseUrl],   // ← usually './'
  moduleNameMapper: pathsToModuleNameMapper(
    compilerOptions.paths,
    { prefix: '<rootDir>/' }    // ← resolve relative to project root
  ),
};</code>

Why this matters: moduleNameMapper is a regex-to-path map. Writing it by hand means maintaining the same aliases in two files — drift is inevitable. The converter keeps them in sync: change tsconfig paths, Jest follows.4

One gotcha: globalSetup and globalTeardown files bypass moduleNameMapper. If those files need path aliases, use import 'tsconfig-paths/register' at the top of the setup file.4

ESM mode: experimental, but usable

Jest's ESM support is still labeled experimental in 30.4 (May 2026).5 If your project uses "type": "module" in package.json, you'll need it. Three things change:56

  1. Run with the flag: node --experimental-vm-modules node_modules/.bin/jest (or NODE_OPTIONS). Jest relies on Node's experimental VM modules API — doubly experimental.
  2. Tell the transformer to emit ESM: use createDefaultEsmPreset(), or set useESM: true in the transform options and extensionsToTreatAsEsm: ['.ts', '.tsx'] in Jest config. Your tsconfig module must be ES2022/ ESNext or Node16/NodeNext.
  3. Mocking changes: jest.mock (CJS, hoisted) does NOT work in ESM. Use jest.unstable_mockModule — the factory is required and can be async, and you load the mocked module with await import(...). Also: the jest global is not injected in ESM — import it from @jest/globals.
<code>// ESM mocking — the unstable API
import { jest, test, expect } from '@jest/globals';  // ← no global jest

jest.unstable_mockModule('./db', () => ({
  saveUser: async () => true,    // factory is required, can be async
}));

test('saves', async () => {
  const { saveUser } = await import('./db');   // ← dynamic import after mock
  expect(await saveUser('Ada')).toBe(true);
});</code>

The unstable_ prefix is honest: this API may change. For hybrid Node16/NodeNext mode, ts-jest requires isolatedModules: true.6

esModuleInterop: what it actually does

You've seen "esModuleInterop": true in every tsconfig. It affects how import x from 'cjs-module' works — without it, default-importing a CommonJS module is an error under strict mode. ts-jest inherits your tsconfig setting, so if your app needs it, tests need it.6 It's not a Jest config — it's a TS compiler option that ts-jest respects.
