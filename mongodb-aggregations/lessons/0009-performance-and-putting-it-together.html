Lesson 9 of 9MongoDB Aggregations

Performance, Limits & Wrap-up

Know the guardrails, spend the pipeline well, and assemble a real analytics query.

The mental model in one sentence

Aggregations have hard guardrails — per-document size, per-stage memory, stage count — and a performance story driven by index use and stage order. Respect both and pipelines stay fast and predictable.

The three guardrails (learn these)

LimitWhat breaksMitigation
16 MiB per result document (BSON)A group's big $push/$$ROOT array, or a fat $lookup result, exceeds it → error.Keep stored arrays small; slice/project; write big results to a collection.
100 MB per-stage RAMBlocking stages ($group, $sort) exhaust memory.Allow allowDiskUse: true to spill those stages to disk.1
1000 stagesOver-long pipelines error.Consolidate; you rarely need that many.

Stages that can spill to disk when allowed: $group, $sort, $bucket, $bucketAuto, $setWindowFields, $sortByCount.1 The usedDisk profiler flag tells you when it happened.

Performance: spend the pipeline well

  • Filter first, filter cheap. $match and $limit early shrink everything after; $match is the stage an index best serves.2
  • Keep $project narrow. Less data per stage is less memory and I/O.
  • Sort then limit for top-N; avoid sorting huge unindexed inputs.
  • Index the join key for $lookup; prefer embedding where the data belongs together.3
  • Mind blocking stages — $group and $sort hold the whole input. Order them late, not early.

Putting it together: a monthly seller dashboard

db.orders.aggregate([
  { $match: { status: "fulfilled", placed: { $gte: startOfYear } } },
  { $unwind: "$items" },
  { $addFields: {
      month:  { $dateToString: { format: "%Y-%m", date: "$placed" } },
      lineRevenue: { $multiply: [ "$items.qty", "$items.price" ] }
  } },
  { $group: {
      _id: { month: "$month", seller: "$items.sellerId" },
      revenue:   { $sum: "$lineRevenue" },
      unitsSold: { $sum: "$items.qty" },
      orders:    { $addToSet: "$_id" }
  } },
  { $setWindowFields: {
      partitionBy: "$_id.month",
      sortBy: { revenue: -1 },
      output: { rank: { $rank: {} } }
  } },
  { $match: { rank: { $lte: 5 } } },
  { $sort: { "_id.month": 1, revenue: -1 } }
])

Read it stage by stage: filter early → flatten line items → derive month and line revenue → group per seller-month → rank sellers within each month → keep the top five → present ordered.

Key idea Senior fluency is the reflex of asking "what shape does each stage hand to the next, and where do the guardrails and indexes bite?" Before running any pipeline, answer both.
