Router Authentication & Security

Prove who the caller is at the router, then decide whether the subgraphs should learn who that was on the upstream hop.

The mental model in one sentence

The Router can verify client tokens (JWT) before planning a request, and it can attach credentials when calling subgraphs — so authentication happens once at the edge and authorization is enforced where the gateway sits.1

Authenticating clients at the router

Configure a router JWT block so that the Router validates the caller's token against a trusted issuer and JWKS before the query is planned and executed:1

authentication:
  router:
    jwt:
      issuer: https://auth.example.com
      audiences: [ "my-app" ]
      jwks:
        - url: https://auth.example.com/.well-known/jwks.json
  • issuer and audiences pin the token's claims; jwks supplies the public keys used to verify the signature.
  • This is authentication — identity. What the caller may do is a separate concern you enforce with your own checks (commonly via Rhai or coprocessors).

Secure the upstream hop

Subgraphs are usually not world-exposed; the Router should present credentials to them. Under authentication.subgraph you can attach headers per service (for example a fixed service token) so one trusted identity flows Router → subgraph:1

authentication:
  subgraph:
    all:
      http:
        headers:
          Authorization: "Bearer a-fixed-token-placeholder"
Key idea Keep the two hops distinct. The client-to-router hop proves the end user; the router-to-subgraph hop proves the gateway. Writing the same credential into both places is a common security mistake.

Also in the security toolkit

  • CORS — restrict which browser origins the Router serves (critical because the Router is the client-facing edge).1
  • CSRF prevention, TLS, and request limits — harden the listener and cap abuse.
  • Demand control — protect the graph from high-cost operations.

Because the Router fronts every subgraph, locking it down once protects the whole graph behind it.2
