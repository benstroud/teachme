Caching & Performance

The Router is built for throughput — but caching and shaping are where you stop hitting subgraphs for every identical request.

The mental model in one sentence

The Router can serve responses from a cache (often Redis), shrink requests with automatic persisted queries (APQ), batch operations, and shape upstream traffic — turning repeated work into cache hits.1

Response caching

Response caching stores a full operation response (keyed by operation + variables, and typically honoring cache-control) so an identical request is answered without a subgraph fan-out. It works best with Redis so many Router instances share one cache across instances.1

  • When it pays: hot, read-heavy operations with stable shapes.
  • The cost: stale data — so pair it with invalidation or short TTLs for anything that changes.
  • It is not the plan: the query still has to be valid; caching skips recomputing it.

Automatic persisted queries (APQ)

APQ is a wire optimization: the client sends a hash of the query instead of the whole text, and only transmits the full query when the Router reports a miss. That shrinks payloads for large, repeated queries and is a natural fit for a Router that is already caching.1

Traffic shaping and batching

Traffic shaping applies per-operation policies — like timeouts and retries — that tune reliability against slow or flaky subgraphs. Query batching lets the Router receive batched requests and process them together, which is useful when clients or gateways in front of the Router batch.1

Key idea Caching changes latency and backpressure, not correctness. Get the plan right first; then cache the hot, read-only operations, and shape upstream calls so one slow subgraph can't stall everything.
