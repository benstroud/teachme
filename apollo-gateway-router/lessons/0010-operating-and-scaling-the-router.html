Operating & Scaling the Router

In production the Router earns its trade-offs through telemetry, health checks, and a deployment model that scales alongside your graph.

The mental model in one sentence

Treat the Router as an edge service you operate like any other: ship it as a container (or the Kubernetes Operator), give it health checks, and watch its OpenTelemetry traces and metrics.1

Observe it with telemetry

The Router emits OpenTelemetry traces and metrics covering the request lifecycle, including per-subgraph calls and query planning. You wire exporters to your observability stack — OTLP, Datadog, Prometheus, and others — so one client request is visible as it fans out across subgraphs.2

  • Metrics answer "how many, how long, how many errors?" per operation and subgraph.
  • Traces answer "what did this one request do?" across planning and subgraph hops.
  • Telemetry exporters are configured in YAML (e.g. under telemetry.exporters) and require a target endpoint.

Health checks & resource management

Like any service, the Router exposes a health check you can point load balancers and orchestrators at, and is designed to run with bounded resources. Read the monitoring docs for the exact check path for your version.2

Deploy and scale

Apollo ships deployment guidance for Docker, Kubernetes (via the Apollo Operator, which manages the Router pods and schema-aware updates), and the major clouds (AWS, Azure, GCP). Scale by running multiple stateless Router instances behind a load balancer, sharing caches (Redis) and a schema source.3

Key idea The Router is stateless toward subgraphs: any instance can serve any request, so the fleet scales horizontally and one instance's restart is invisible to clients — as long as caches and schema delivery are shared.
