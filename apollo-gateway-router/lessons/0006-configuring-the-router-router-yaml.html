Configuring the Router (router.yaml)

router.yaml declares the Router's runtime features; the supergraph schema is wired separately. Know both sides.

The mental model in one sentence

Running the Router means (1) giving it the supergraph schema and (2) declaring its runtime features in a YAML config — named router.yaml by default.1

The two halves of setup

HalfWhat it providesHow
The supergraph schemaThe graph the Router serves and routes againstLocal file, Uplink, graph artifact, or Operator
router.yamlListeners, CORS, headers, auth, caching, telemetryYAML passed as --config or discovered by name
1

A representative router.yaml

supergraph:
  path: ./supergraph.graphql

listeners:
  - port: 4000

cors:
  origins:
    - https://app.example.com

headers:
  all:
    request:
      - propagate:
          named: x-request-id

authentication:
  router:
    jwt:
      issuer: https://auth.example.com
      audiences: [ "my-app" ]
      jwks:
        - url: https://auth.example.com/.well-known/jwks.json
  subgraph:
    all:
      http:
        headers:
          Authorization: "Bearer a-fixed-token-placeholder"

telemetry:
  exporters:
    metrics:
      otlp:
        endpoint: http://collector:4317
  • supergraph.path points at the supergraph file (an alternate to the --supergraph flag).1
  • listeners open the port(s) the Router serves on.
  • cors and headers govern origins and header propagation; authentication adds JWT at the router and attaches credentials to subgraph calls.
  • telemetry.exporters wires observability output (expanded in a later lesson).

Environment variables that matter

  • APOLLO_ROUTER_SUPERGRAPH_PATH — set the supergraph via a local file path.
  • APOLLO_GRAPH_REF — fetch the supergraph from Apollo Uplink.
  • APOLLO_GRAPH_ARTIFACT_REFERENCE — reference a versioned graph artifact.1
Key idea For local files the Router can hot reload: when the supergraph file changes it reloads the schema at runtime, giving zero-downtime schema updates in local/CI workflows.1
