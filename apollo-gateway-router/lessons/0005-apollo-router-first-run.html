Apollo Router: First Run

A binary, a supergraph schema, and a way to serve it — then it plans and routes client queries to your subgraphs.

The mental model in one sentence

The Router is a standalone binary that needs (a) the supergraph schema it serves and (b) a router.yaml for its features; you give it the schema through a file path, an environment variable, or Apollo's schema services, then it listens and routes.1

Give it the supergraph

The Router needs to know the graph it is running. For a local setup the simplest source is a supergraph file, supplied either by flag or by environment variable:1

# by command-line flag
./router --supergraph ./supergraph.graphql

# or by environment variable
APOLLO_ROUTER_SUPERGRAPH_PATH=./supergraph.graphql ./router

Other schema sources exist — Apollo Uplink (APOLLO_GRAPH_REF), graph artifacts (APOLLO_GRAPH_ARTIFACT_REFERENCE), and the Kubernetes Operator — each suited to a different deployment.1

Run it (binary or container)

With a local supergraph file and a minimal router.yaml, launch it and it begins serving the composed API:

# supergraph.graphql   (from rover supergraph compose)
# router.yaml
supergraph:
  path: ./supergraph.graphql

listeners:
  - port: 4000

# run
./router --config router.yaml

Running via container follows the same idea — mount the supergraph and config, set the schema path, and expose the listener port. The exact image tag and volume layout depend on the Router version and its deployment guide; confirm those from the docs before relying on a specific command.2

Send a first query

Once the Router is up, an HTTP POST to the listener with a GraphQL query behaves like any GraphQL endpoint. It validates against the supergraph, plans, fans out to the subgraphs that can answer, and merges the result:

curl -X POST http://localhost:4000/ \
  -H 'content-type: application/json' \
  -d '{"query":"{ product(id: 1) { name reviews { body } } }"}'
Key idea Launching the Router is not building a GraphQL API — the API is the supergraph. Your job is to give the Router that schema and let its query planner do the fan-out.
