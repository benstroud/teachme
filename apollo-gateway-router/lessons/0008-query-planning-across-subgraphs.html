Query Planning Across Subgraphs

One client query becomes a plan: which subgraphs to call, with what, in what order — then a merged answer.

The mental model in one sentence

Given a client query, the gateway builds a query plan — which subgraph returns which pieces, how to sequence entity lookups across them — executes it, and merges the parts into one response.1

Reading a simple plan

# client query
query { product(id: 1) { name reviews { body } } }

# conceptual plan
1. products:  product(id: 1) -> Product { name }         (returns entity + key)
2. reviews:   __resolveReference(ref: { id: 1 })
              -> Product { reviews { body } }             (fills the rest)
3. merge:     Product { name, reviews: [...] }

The gateway asks the products subgraph for the fields it owns (name), then asks the reviews subgraph to resolve the same entity by its key and fill reviews. It merges on the shared id.2

Entities are the joints

Crossing a subgraph boundary requires an entity. The owning subgraph resolves it from its key fields; the other subgraph contributes additional fields. The plan chains these references so a single client query composes the whole object across services.2

  • Fields owned by the same subgraph stay together in one call — the plan avoids splitting them needlessly.
  • Entity references are batched where possible, so a list of products becomes a batch reference resolver, not one call per product.
  • The query planner decides shape and order; you don't hand-write the plan, but you must be able to read it.
Key idea Planning is why the supergraph must carry routing metadata: the gateway cannot know which subgraph owns name unless the composed schema tells it. Read the plan, and you understand how a query maps onto your services.

The native query planner

The Apollo Router uses a native query planner tuned for throughput: it parses the operation, validates against the supergraph, chooses subgraph calls, and emits the execution schedule — work that happens on every request, so its cost is amortized across high request loads.1
