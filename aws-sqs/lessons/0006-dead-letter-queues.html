Dead-Letter Queues

Stopping the loop when a message is genuinely unprocessable.

The problem: a message that never succeeds

Imagine your handler has a subtle bug: it crashes on any order whose total is exactly 0. Visibility timeout expires, message becomes visible again, Lambda retries, handler crashes again, forever. The queue grows. Your DLQ stays empty. The bad message is invisible.

A dead-letter queue is the trip wire. After N failed receives, SQS moves the message to a separate queue where humans can look at it. The original queue keeps serving healthy traffic; the bad message is isolated for diagnosis.1

Key idea A DLQ is not a retry mechanism — SQS's natural visibility-timeout loop is the retry mechanism. A DLQ is a parking lot for messages that have proven they can't be processed by the current consumer.

How the redrive policy works

You attach a redrive policy to the source queue. It says: "after this message has been received N times without being deleted, move it to this other queue." The two settings you care about:

SettingWhat it does
deadLetterTargetArnThe ARN of the DLQ
maxReceiveCountHow many receives before the message is moved to the DLQ (default 10)

The DLQ must be in the same AWS account and region as the source queue. A FIFO source can use a FIFO DLQ (and should, unless breaking the order is OK).2

Picking maxReceiveCount

  • Low (1–3): very strict; one failure sends to DLQ. Use for handlers that should be fast-failing — bad input shouldn't get four chances.
  • Medium (5–10, the default 10): good for most transient failure shapes — network blips, occasional timeouts.
  • High (30+): for handlers with genuinely long retry curves (e.g. dependency that comes back online slowly).

One subtle behavior for standard queues with maxReceiveCount > 3: after a message has been received 3 or more times without being deleted, SQS moves it to the back of the queue so a younger message has a chance to be processed. The ApproximateAgeOfOldestMessage metric then reflects the age of the next message that hasn't hit the threshold.3

What lands in the DLQ

The original message body, attributes, and a few extras:

  • DeadLetterQueueSourceArn — the source queue's ARN
  • The original messageId and body (unchanged)
  • ApproximateReceiveCount continues to be useful

You will see your normal CloudWatch metrics on the DLQ too — NumberOfMessagesSent, ApproximateNumberOfMessagesVisible. These are your alarms.

The DLQ is itself a queue

The DLQ is just an SQS queue. Nothing inspects it for you. You have three reasonable choices:

  1. Alarm and inspect by hand — CloudWatch alarm on ApproximateNumberOfMessagesVisible > 0; on-call engineer reads messages.
  2. Another Lambda watches it — event source mapping on the DLQ; a triage handler tries to figure out what went wrong and pages a human.
  3. Redrive back to source — once you fix the bug, use DLQ redrive to move messages from the DLQ back to the source queue for another attempt.4
Engineer's rule If your DLQ has zero messages forever, it means you have no failures — or no observability. Alarm on it.

Don't use a DLQ with FIFO when order matters

The official guidance: don't use a DLQ with a FIFO queue if exact order is critical. A message that fails N times is moved to the DLQ, but messages after it continue being delivered. When you redrive, the dead-lettered message arrives out of order with respect to its successors.5

The minimal setup

  1. Create a second SQS queue (the DLQ). Same account, same region. FIFO if the source is FIFO.
  2. On the source queue, set the redrive policy: target = the DLQ ARN, maxReceiveCount = your choice.
  3. Add a CloudWatch alarm on ApproximateNumberOfMessagesVisible on the DLQ.
  4. Document who looks at the DLQ and how messages get redriven or deleted.

What a DLQ does NOT do

  • It does not retry for you — visibility timeout already retries for you.
  • It does not auto-fix the bad message.
  • It does not page on its own — you need the alarm.
  • It does not preserve messages past the DLQ's own retention. The DLQ has its own 4-day default; set it long enough to be looked at.
