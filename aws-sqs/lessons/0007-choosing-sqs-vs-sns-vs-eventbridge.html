Choosing SQS vs SNS vs EventBridge

Pick the right AWS messaging primitive — and the right combination.

Three primitives, three shapes

AWS gives you three managed messaging primitives, and they are not interchangeable. Each is shaped for a different delivery relationship between producer and consumer.

PrimitiveShapeReach for it when…
SQSQueue — one consumer group pullsDurable buffer between a producer and one or many workers; backpressure; order or dedup per entity
SNSTopic — push fan-out to N subscribersEvery subscriber must get a copy; subscribers are heterogeneous (Lambda, HTTP, email, SQS)
EventBridgeEvent bus — route by content to N targetsMany consumers care about different kinds of events; rules select which consumer sees which event

Sources: AWS Decision Guide — SQS, SNS, or EventBridge?, AWS — What is SNS?.

SQS: the durable inbox

Producers SendMessage; a single consumer group pulls and processes. The message lives in the queue until deleted. The queue absorbs spikes; the consumer processes at its own pace.1

Pick SQS when:

  • The producer can finish before the consumer can.
  • You need durability — the work must survive a consumer crash, a deploy, a region-wide issue.
  • One consumer group (one team, one workflow) owns the work.
  • You need per-entity order (FIFO) or per-entity dedup.

Avoid SQS when:

  • Many unrelated consumers need their own copy of each event — the bus/topic shapes are better fits.

SNS: the push fan-out

Producers publish to a topic. Every subscriber gets a copy via their chosen protocol — Lambda, SQS, HTTP/S, email, SMS, mobile push. There is no buffering on the topic itself; if no subscriber is ready, the message is lost (unless the subscriber is an SQS queue).2

Pick SNS when:

  • Every subscriber must get a copy, and they don't coordinate.
  • Subscribers are heterogeneous and managed by different teams.
  • Latency matters more than durability.

Avoid SNS when:

  • A subscriber needs durability or backpressure — subscribe an SQS queue to the topic; that gives you both fan-out and durability.

EventBridge: the content router

Producers publish events with a structure (source, detail-type, detail). Rules on the bus match on that structure and route to many targets. A single event can fan out to many consumers, and each consumer sees only what it cares about.

Pick EventBridge when:

  • You have many independent consumers, each reacting to a different kind of event.
  • The audience for an event can grow or shrink without redeploying producers.
  • You need integration with AWS service events (S3, CodePipeline, etc.) or SaaS partner events.

The combinations that matter

The interesting answers are usually combinations.

SNS → SQS: fan-out with durability

Every subscriber gets its own SQS queue subscribed to the same topic. The topic delivers a copy to each queue; each consumer drains its own queue at its own pace. This is the canonical "tell everyone reliably" pattern.3

EventBridge → SQS: ordering + content filtering

The bus routes events to one or more SQS queues. SQS FIFO gives per-entity order on top of the bus's content filtering. Useful when you want EventBridge's "many consumers by content" but you need order for a specific downstream.

SQS → Lambda (with EventBridge watching for DLQ events)

SQS as the durable work queue, Lambda as the worker, EventBridge piping DLQ events to a separate triage handler. The three primitives each play their natural role.

The decision in five questions

  1. How many consumer groups? One → SQS. Many independent → SNS or EventBridge.
  2. Do they all want the same events? Yes → SNS. Only some of them, depending on content → EventBridge.
  3. Does order matter per entity? SQS FIFO (or EventBridge → SQS FIFO).
  4. Can the consumer fail and lose work? SQS (or SNS → SQS). Topics alone are not durable.
  5. Is the producer an AWS service or a SaaS? EventBridge has built-in integrations; use it.

A worked example

You launch a SaaS where:

  • Customers hit POST /orders on API Gateway → Lambda.
  • The Lambda validates and writes one OrderPlaced message to SQS.
  • A worker Lambda drains the queue and charges the card, reserves inventory, etc.
  • On DLQ, an alarm pages on-call.
  • If you later want a notifications team to also receive every order, you subscribe an SQS queue (or SNS topic → SQS) to EventBridge — without changing the orders Lambda.

SQS is the workhorse. EventBridge is the optional router for new consumers. SNS would be a reasonable alternative if every downstream wanted push and the same message.

Engineer's check The decision isn't SQS or EventBridge. It is which shape fits the producer–consumer contract for THIS integration. Most systems use all three.

Check yourself

1. A single Lambda worker must reliably process each "image uploaded" event. Multiple workers may run in parallel. What is the right primitive?
