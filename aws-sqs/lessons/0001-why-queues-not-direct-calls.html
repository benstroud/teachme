Why Queues, Not Direct Calls

The coordination problem that SQS exists to solve.

The trap: work that has to wait on other work

Here is a typical API handler in a serverless app: a customer hits POST /orders, the Lambda validates the order, charges the card, reserves inventory, sends the email, and finally returns 200 OK.

// inside the orders Lambda handler
const charge   = await paymentClient.charge(order);
const reserve  = await inventoryClient.reserve(order);
const email    = await emailClient.sendWelcome(order);
return { statusCode: 200, body: "ok" };

This works on the demo, and it collapses in production. Three downstream services now sit on the user's hot path. The handler's timeout (default 30s in API Gateway) is shared with three other systems you don't control.1

Key idea The failure isn't slow code — it's coupling. The order function is a conductor for three other services, and every slow service slows the customer.

Four failure modes of direct calls

Failure modeWhat happens
Cascade timeoutsA 25-second payment call eats most of the API Gateway timeout; one slow hop takes the whole request down.
Hot-path backpressureIf a thousand orders arrive in a spike, every one tries to call payment at once — your payment provider rate-limits you, every order fails.
Tight couplingThe handler holds names/ARNs of three services and has to be redeployed when one is renamed or replaced.
Lost work on failureCharge succeeded, inventory reservation failed, email never sent. The customer is charged with no inventory. Who fixes it? The handler returned 500 and lost the context.2

What a queue changes

With an SQS queue, the orders function stops being a conductor. It becomes a poster:

  1. It validates the order.
  2. It writes one short message to the orders queue (SendMessage).
  3. It returns 200 OK immediately.
  4. Separate worker Lambdas consume the queue at their own pace.

The order is committed the moment the message is in the queue. The queue holds the work durably (replicated across Availability Zones) until a worker can pick it up. If payment is slow, the queue grows; if payment is down, the queue keeps the work safe for up to 14 days.3

Engineer's check Ask: does the customer need this work done before I can answer them? If yes, do it inline. If no — and a lot of work is "no" — push it onto a queue.

The decoupling trade

You've traded a synchronous result (knowing every step completed) for three things:

  • Durable buffer. A failed downstream service doesn't drop the work; the queue keeps it.
  • Independent pace. Workers scale to whatever throughput they need; the producer doesn't care.
  • Failure isolation. A bug in the email service doesn't take down order placement.

The cost: you no longer get an immediate answer to "did every step succeed?" You get it eventually, through monitoring and through a separate workflow you design.

What SQS is — and isn't

SQS is a queue: producers write, a single consumer group pulls, the message lives until deleted. It is not a router (use EventBridge for that) and not a fan-out (use SNS for that). It is the durable inbox you put work into when the producer can finish before the consumer can.4

Two things are required for this to work, and they are the heart of this whole course:

  • A way to write a message that survives whatever happens next (the producer side).
  • A way to consume that message without losing it on a crash, and without processing it twice (the consumer side).

Lesson 2 covers both.
