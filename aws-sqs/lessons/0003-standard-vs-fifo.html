Standard vs FIFO

Pick the queue type by the contract you need, not by "it feels safer."

Two queue types, one decision

When you create an SQS queue, you choose standard or FIFO. That single choice pins three things for the life of the queue:

  • how many times a message can be delivered
  • what order messages arrive in
  • how much throughput the queue can carry

You cannot convert between them later without a cutover — pick carefully up front.

Why standard can reorder

SQS standard queues are built for raw throughput. To deliver very high TPS, SQS uses many servers; a high-volume send can hit different servers and arrive in a slightly different order than sent. Most apps don't care, but order-sensitive ones (e.g. "process order creation before order payment") cannot rely on it.1

How FIFO achieves strict order

A FIFO queue is partitioned by MessageGroupId. Two messages with the same group id are delivered strictly in the order they were sent. Messages with different group ids can be processed in parallel by different consumers.

// FIFO send
await sqs.send(new SendMessageCommand({
  QueueUrl:              "https://sqs.us-east-1.amazonaws.com/123/orders.fifo",
  MessageBody:           JSON.stringify({ orderId: "ord_1", action: "create" }),
  MessageGroupId:        "ord_1",
  MessageDeduplicationId: "ord_1-create",
}));

Use one MessageGroupId per logical entity you want to keep ordered — per customer, per order, per session — not one for the whole queue. If you use the same group id for everything, you serialize the entire queue and lose FIFO's parallelism.2

Engineer's rule One MessageGroupId per entity that has an order. Many entities → many groups → parallelism.

Why FIFO deduplicates

Within a 5-minute window, SQS refuses to accept a second message that carries the same MessageDeduplicationId as a recently accepted one. Two ways to use it:

  • Content-based deduplication: turn it on at queue level; SQS hashes the body for you. Good when the body is identical on retries.
  • Explicit deduplication ID: you pass a stable id (often your business key) on every send. Good when you want control over what counts as "the same."

This protects you from double-charging a customer when your own producer retries — not from a duplicate on the consumer side (that's what idempotency handles; covered in lesson 5).3

When FIFO isn't enough throughput

If your workload exceeds the default 300 msg/s per FIFO queue, turn on high-throughput mode (via the FifoThroughputLimit attribute) and use MessageDeduplicationId (or content-based dedup). That gives you up to 3,000 msg/s with batching. For higher, you parallelize across multiple FIFO queues.4

The decision in three questions

  1. Does order matter within an entity? If no → standard. If yes → FIFO.
  2. Can a duplicate cause a duplicate side effect? If yes → idempotent handler (lesson 5). FIFO's dedup window covers producer-side duplicates within 5 minutes; consumer-side idempotency is on you regardless.
  3. What's your peak throughput? If > 3,000 msg/s on a single FIFO queue → parallelize across many FIFO queues (one per shard key).

The default answer

Most production queues are standard. FIFO's strict order and exactly-once processing are valuable, but they come at the cost of throughput and operational complexity. Reach for FIFO when you can name a concrete business reason: an order that must be created before it is paid, a seat reservation that must register before it is sold, an account that must exist before it is granted access.5
