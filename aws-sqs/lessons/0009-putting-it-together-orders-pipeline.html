Putting It Together

A small but realistic orders pipeline — and why every choice was made.

The system we're building

A customer-facing SaaS where:

  • Users hit POST /orders on API Gateway.
  • A Lambda validates, then enqueues a single message per order.
  • A worker Lambda drains the queue and runs the slow work (charge, inventory, email).
  • A second queue carries the result of the slow work for a fan-out step.
  • DLQs catch anything that fails repeatedly; alarms page on-call.

Why each piece is shaped this way

Orders queue: standard, not FIFO

Two different orders can be processed in any order. There's no business rule that order #100 must finish before order #99. Standard gives unlimited throughput at the cost of best-effort order, which we don't need.

Orders DLQ: redrive on maxReceiveCount=5

Five retries is enough to ride out transient failures (payment provider blip, downstream timeout) without letting a bad message loop forever. The DLQ alarm is on ApproximateNumberOfMessagesVisible > 0 for 5 minutes.

Worker Lambda: idempotent, partial batch response

Charging a card is not idempotent by default — we use a conditional DynamoDB write on orderId so a duplicate delivery never produces a duplicate charge. The handler returns { batchItemFailures: [...] } with only the failing records; SQS retries only those.1

// orders-worker, sketched
export const handler: SQSHandler = async (event: SQSEvent): Promise<SQSBatchResponse> => {
  const failures: { itemIdentifier: string }[] = [];
  for (const record of event.Records) {
    try {
      await processOrderOnce(JSON.parse(record.body), record.messageId);
    } catch (err) {
      console.error("failed", record.messageId, err);
      failures.push({ itemIdentifier: record.messageId });
    }
  }
  return { batchItemFailures: failures };
};

Order-processed queue: a result stream

Once the order is durably processed, the worker writes a short "OrderProcessed" message to a second queue. Why a queue and not just calling the next Lambda synchronously? Same reason as lesson 1: the next stage (analytics, notifications, third-party webhook) shouldn't sit on the worker's hot path or take the worker down with it.

Fan-out Lambda: pull the queue, do the side effects

The fan-out Lambda drains order-processed-queue. Each record triggers analytics, a notification, and a webhook. Side effects are individually idempotent (notification deduped on orderId, webhook retried by the receiver).

Visibility timeouts

  • Orders queue: 60 seconds. The worker is fast — payment < 5s, inventory < 2s, email < 3s — but we give headroom.
  • Order-processed queue: 30 seconds. The fan-out is fast too.

Why two queues, not one with a "stage" attribute

Two concerns: lifecycle and throughput. The orders queue carries one message per order; the processed queue carries the same volume plus downstream retries. Mixing them on a single queue would force a single consumer to handle both stages. Separate queues let each stage scale on its own and fail in isolation.

The trade-offs you can defend in an interview

Pick any one of these and explain it as if to a senior engineer:

  1. Standard queue over FIFO — because no per-entity order rule applies across orders.
  2. Two queues over one — because each stage has its own throughput and its own failure domain.
  3. Idempotent worker — because the worker charges a card, which is the irreversible side effect.
  4. DLQ with low maxReceiveCount — because we want poison messages parked fast, not after 50 retries.
  5. Partial batch response — because without it, one bad order retries the whole batch and forces idempotency on every record.
Engineer's check If you can defend each of the five, you can defend an SQS architecture in a senior conversation. The exact configuration is less important than the reasoning.

What you would add in production

This course deliberately stopped short of:

  • Observability: CloudWatch metrics for all four queues; X-Ray for trace continuity from API Gateway through both queues.
  • Cost: batched sends where possible; long polling already on by default for ESM.
  • Schema control: a JSON Schema for the message body, versioned, with a CI check that producers and consumers match.
  • Cross-cutting alarms: DLQ depth, ApproximateAgeOfOldestMessage (queue is backing up), consumer error rate.
  • Cross-region / multi-account: out of scope for this course; the same shape scales by replicating the queues per region.

Where to go next

Two natural follow-ons, in this order:

  1. EventBridge — for the kind of routing this pipeline would need when more teams want to react to orders (notifications team, finance team, analytics).
  2. Step Functions — for workflows that need explicit orchestration (e.g. "wait for human approval before charging").
