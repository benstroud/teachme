Lesson 8 of 9 — waitAWS SQS

Lambda as a Consumer

The event source mapping — let Lambda poll the queue for you.

Why you almost never poll SQS yourself

The pattern from lesson 2 — ReceiveMessage in a loop, DeleteMessage when done — works, but you now own a long-running process, scaling, retries, and visibility-timeout renewal. For Lambda-to-Lambda architectures there is a better shape: an event source mapping (ESM) that AWS runs on your behalf.

An ESM is a piece of Lambda-side configuration. It tells Lambda: poll this SQS queue, batch what you find, invoke my function with each batch, and delete the messages after a successful invocation.1

Key idea The ESM owns the polling loop and the successful-message cleanup. Your Lambda owns only the per-message work.

The shape of an event

Lambda invokes your handler with a single argument shaped like this:

{
  "Records": [
    {
      "messageId":     "9b...",
      "receiptHandle": "AQEBaZ...==",
      "body":          "{\"orderId\":\"ord_1001\",\"total\":129.99}",
      "attributes": {
        "ApproximateReceiveCount":        "1",
        "SentTimestamp":                  "1757145600000",
        "ApproximateFirstReceiveTimestamp": "1757145610000"
      },
      "messageAttributes": {
        "eventType": { "stringValue": "Order Placed" }
      },
      "eventSource": "aws:sqs",
      "eventSourceARN": "arn:aws:sqs:us-east-1:123:orders",
      "awsRegion": "us-east-1"
    }
  ]
}

The shape is the standard SQSEvent TypeScript type. The interesting fields are:

  • Records[].messageId — use this as your idempotency key.
  • Records[].body — your payload, a string; parse it.
  • Records[].attributes.ApproximateReceiveCount — how many times SQS has delivered this message; useful for fail-fast logic.
  • Records[].messageAttributes — your structured metadata.

A minimal handler

import type { SQSEvent, SQSHandler } from "aws-lambda";

export const handler: SQSHandler = async (event: SQSEvent) => {
  for (const record of event.Records) {
    const order = JSON.parse(record.body);
    await processOrder(order, record.messageId);
  }
  // Returning nothing = "treat the whole batch as successful".
  // SQS deletes every message in the batch.
};

This works — but it has a sharp edge. If one record throws, the whole batch throws. SQS treats the whole batch as failed, leaves every message in the queue, and they all become visible again after the visibility timeout. You will process some messages twice.2

Partial batch response — the right shape

Tell SQS exactly which messages failed by returning a partial batch response:

import type { SQSEvent, SQSHandler, SQSBatchResponse } from "aws-lambda";

export const handler: SQSHandler = async (event: SQSEvent): Promise<SQSBatchResponse> => {
  const failures: { itemIdentifier: string }[] = [];

  for (const record of event.Records) {
    try {
      const order = JSON.parse(record.body);
      await processOrder(order, record.messageId);
    } catch (err) {
      console.error("failed", record.messageId, err);
      failures.push({ itemIdentifier: record.messageId });
    }
  }

  // SQS deletes the successful messages and leaves the failed ones
  // to become visible again after their visibility timeout.
  return { batchItemFailures: failures };
};

Two things to know about this:

  • The function signature uses ReportBatchItemFailures semantics; you opt in by returning the right shape.
  • If batchItemFailures is empty (or absent), SQS deletes every message in the batch.

Configuring the mapping

The ESM has a handful of settings that matter. Set them in the console or in IaC:

SettingWhat it controlsDefault
batchSizeMax messages per invocation (1–10,000)10
maximumBatchingWindowInSecondsWait this long to fill a batch before invoking0 (invoke as soon as batch is full)
functionResponseType (was ReportBatchItemFailures)Enable partial batch responseoff
filterCriteriaSkip records by attribute (e.g. only process Order Placed)none
scalingConfigMin / max concurrent invocationsmin 5, max 1000

Source: AWS Lambda — Using Lambda with SQS.

Engineer's rule Always turn on partial batch response. Without it, one bad message will retry the whole batch — and your idempotency story has to cover records you already processed.

How concurrency plays with the queue

Lambda's reserved concurrency caps how many ESM invocations run at once. If your queue has 10,000 messages and concurrency is 10, Lambda runs 10 in parallel until the queue drains. If a downstream is slow, that throttles cleanly — the queue absorbs the spike instead of your function timing out.

For FIFO queues, the ESM respects MessageGroupId: a single group runs serially through the function (in send order), but different groups run in parallel up to your concurrency cap.3

Long polling is on by default

As of 2022, ESM uses long polling automatically — WaitTimeSeconds: 20. You don't have to configure it.4

When to write your own consumer instead

An ESM is right when:

  • Work is per-message and fits in a Lambda invocation.
  • You want zero ops on the consumer.
  • You want auto-scaling and backpressure for free.

Write your own consumer (long-poll loop, manual scaling) when:

  • You need to preserve message order across the whole queue (rare; usually a FIFO group is enough).
  • You need to ChangeMessageVisibility mid-processing to extend the window past 12h.
  • You need a non-Lambda runtime for some reason.
