Lesson 8 of 9 — waitAWS SQS

Visibility, Retries, Idempotency

The retry mechanism SQS gives you — and the discipline it requires.

What "at-least-once" really means

SQS standard queue gives you at-least-once delivery: each message will arrive, but it may arrive more than once. Your handler, then, must produce the same observable result whether it runs once or twice. That is the entire shape of this lesson.1

Visibility timeout — SQS's retry lever

When you ReceiveMessage a message, SQS does not remove it. It marks it invisible for a window called the visibility timeout. During that window, no other consumer will see it. You process it, then call DeleteMessage to remove it permanently.2

Three failure shapes if you don't delete in time:

  1. The visibility timeout expires.
  2. SQS makes the message visible again.
  3. Another consumer (or the same one) receives it — and processes it again.

Default is 30 seconds. Range is 0 seconds to 12 hours. Set it on the queue, or override per receive with the VisibilityTimeout field on ReceiveMessage, or extend mid-flight with ChangeMessageVisibility.

Key idea Visibility timeout is not a delay. It is a claim window. While it runs, the message is only yours. When it expires, the message is everyone's again.

Picking a visibility timeout

The rule of thumb:

  • Set it higher than your P99 handler duration. If most calls finish in 500ms but the slow path is 8 seconds, give yourself 15 seconds headroom — a 200ms cron in production will surprise you otherwise.
  • Short timeouts for fast-failing jobs. If the handler either succeeds or throws in < 2 seconds, a 10-second timeout means a poison message retries quickly and ends up in the DLQ fast.
  • Long timeouts for slow jobs. Image processing or PDF generation might need minutes; use ChangeMessageVisibility in a heartbeat to extend.

Heartbeating a long task

If your handler runs longer than the visibility timeout, extend it periodically:

import {
  SQSClient, ChangeMessageVisibilityCommand, ReceiveMessageCommand, DeleteMessageCommand,
} from "@aws-sdk/client-sqs";

async function runWithHeartbeat(sqs: SQSClient, queueUrl: string, receiptHandle: string, body: string) {
  const TIMEOUT = 60;          // current visibility window
  const HEARTBEAT_EVERY = 20;  // extend before it expires

  const extend = async () => {
    await sqs.send(new ChangeMessageVisibilityCommand({
      QueueUrl: queueUrl,
      ReceiptHandle: receiptHandle,
      VisibilityTimeout: TIMEOUT,
    }));
  };

  const timer = setInterval(extend, HEARTBEAT_EVERY * 1000);

  try {
    await doLongWork(body);   // up to TIMEOUT seconds per leg
    await sqs.send(new DeleteMessageCommand({ QueueUrl: queueUrl, ReceiptHandle: receiptHandle }));
  } finally {
    clearInterval(timer);
  }
}

Lambda's ESM does this for you up to the function's own 15-minute timeout, but if you write a long-running consumer you need the heartbeat pattern yourself.

Retries: the natural shape

With visibility timeout, SQS retries "for free" on any consumer crash or timeout: the message becomes visible again, gets re-delivered, gets another chance. There is no retry count built into SQS itself beyond ApproximateReceiveCount — which is metadata you can read and decide on. The redrive policy (covered in lesson 6) is what stops the loop after N receives.3

Idempotency — the discipline

An idempotent handler produces the same observable effect whether the message arrives once or five times. Two common patterns:

1. Dedupe on messageId

The SQS-assigned messageId is unique to each message and stable across retries of the same message. Store the ids you've processed in a fast key-value store; on receipt, check and skip if seen.

2. Dedupe on a business key from the body

Often the messageId is wrong: a business event "Charge Customer X $5" is the same work whether the producer retries once or twice. Use a stable id from the body (e.g. orderId) as the dedup key.

import { DynamoDBClient, UpdateItemCommand } from "@aws-sdk/client-dynamodb";

const ddb = new DynamoDBClient({});

async function chargeOnce(orderId: string, amount: number) {
  // Conditional write: succeed only if no row exists for this orderId yet.
  try {
    await ddb.send(new UpdateItemCommand({
      TableName: "orders_processed",
      Key:  { orderId: { S: orderId } },
      UpdateExpression: "SET #s = :done, amount = :a",
      ConditionExpression: "attribute_not_exists(orderId)",
      ExpressionAttributeNames:  { "#s": "status" },
      ExpressionAttributeValues: { ":done": { S: "charged" }, ":a": { N: String(amount) } },
    }));
    await paymentClient.charge(orderId, amount);
  } catch (err: any) {
    if (err.name === "ConditionalCheckFailedException") {
      // Already processed — idempotent no-op.
      return;
    }
    throw err;
  }
}

The conditional write is the heart of it: only one of the duplicate deliveries wins; the others see a ConditionalCheckFailedException and exit cleanly. AWS Lambda Powertools — Idempotency packages this pattern in TypeScript.4

Engineer's rule If your handler charges a card, sends an email, decrements inventory, or posts to another system that has its own side effect, it must be idempotent. There is no exception.

The mental model in one diagram

producer --SendMessage--> [SQS queue]
                            |
                            | ReceiveMessage (becomes invisible for VT seconds)
                            v
                       consumer
                       /        \
                  success     failure
                     |           |
              DeleteMessage     (do nothing — VT expires)
                     |           |
                  removed        becomes visible again
                                  |
                                  +--> another consumer (or this one) receives
                                        |
                                       ...until deleted or DLQ trips

The discipline checklist

  • Pick VisibilityTimeout > P99 handler time, with headroom.
  • If work can exceed the timeout, heartbeat via ChangeMessageVisibility.
  • Make the side effect idempotent — dedupe on messageId or a business key.
  • Turn on partial batch response for Lambda so one bad record doesn't retry the whole batch.
