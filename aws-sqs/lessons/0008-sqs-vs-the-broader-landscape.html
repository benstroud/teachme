SQS vs the Broader Landscape

How SQS compares to Redis/Valkey, MQTT, NATS, RabbitMQ, Kafka, and gRPC — and a decision tree you can defend.

What this chapter is for

Lesson 7 answered a narrow question: within the AWS messaging family, which one do I reach for? This one answers the wider one: when is SQS the right shape at all? In a senior conversation you will get asked "why SQS and not Kafka" or "why not just use Redis" — and you need the axes, not just the names.1

Key idea These are not seven versions of the same thing. Each is shaped for a different relationship between producer and consumer — durable buffer, log, pub/sub, RPC, ephemeral cache. The right answer depends on which shape fits the problem.

The eight comparison axes

Before any comparison table, fix the axes in your head. Every messaging tool can be characterized on the same eight dimensions. Memorize these; everything else is a row in a table.

AxisWhat it asks

With these axes, every "why not X instead" reduces to "where does X sit on the axes, and where is the workload."

The seven alternatives, one paragraph each

Redis / Valkey (as a queue, not just a cache)

Redis is an in-memory data store with primitives (LPUSH/BRPOP, Streams since 5.0) that can be used as a queue. It's blazingly fast — single-digit millisecond latency — but durability is opt-in. Plain LPUSH loses messages on a crash. RDB snapshots and AOF give you durability, but you operate the cluster yourself: you patch, scale, monitor, replicate, and replace nodes.2

Two important 2024–2026 footnotes for AWS readers:

  • Valkey is the fork. Valkey is a Linux Foundation–stewarded, BSD-licensed fork of Redis 7.2.4 created in March 2024 after Redis moved to the SSPLv1 license. The wire protocol and command set are compatible; existing Redis client libraries work against either engine. Most of what you read about Redis applies to Valkey.
  • On AWS, the realistic Redis-shaped managed service is ElastiCache for Valkey. ElastiCache for Valkey went GA in October 2024 and is now the default engine for new ElastiCache clusters (node-based and Serverless). Pricing for Valkey nodes is roughly 20% below the equivalent Redis OSS option, with ElastiCache Serverless for Valkey about 33% cheaper. The legacy ElastiCache for Redis OSS option still exists for existing clusters but is no longer the recommended path for new ones.8

For the rest of this chapter, "Redis" and "Valkey" are treated as one shape — the engine choice doesn't change the queue primitives, the durability story, or the operational model.

Where Redis/Valkey beats SQS: sub-millisecond latency, in-process pub/sub, ability to read/write the same data structure your app already uses, and the option of a fully managed path via ElastiCache for Valkey with 99.99% availability.

Where SQS beats Redis/Valkey: zero ops without a managed-service premium (no node sizing, no shard rebalancing), native Lambda ESM, 14-day retention, pay per request rather than per node-hour, and the same SQS guarantees for every region without an extra service to provision.

MQTT

MQTT is a lightweight pub/sub protocol designed for unreliable networks — IoT sensors, mobile devices, low-bandwidth links. Brokers (AWS IoT Core, Mosquitto, HiveMQ) keep persistent sessions; clients reconnect and resume. Topics are hierarchical (sensors/floor-3/temp) with wildcards (+, #).3

Where MQTT beats SQS: tiny clients on flaky networks, last-will-and-testament, millions of small devices, hierarchical topics.

Where SQS beats MQTT: server-side integrations, no broker to run, native Lambda ESM, FIFO per group with dedup, real durability guarantees.

NATS

NATS is a subject-based pub/sub system, famously small (single binary), fast, and cloud-native. Subjects are dotted strings (orders.eu.placed); subscribers use * (one token) or > (rest) wildcards. NATS Core is at-most-once and fire-and-forget; JetStream adds persistence, at-least-once / exactly-once, streams, and replay. NATS is the canonical choice for service-to-service messaging inside Kubernetes clusters.4

Where NATS beats SQS: subject-based routing built in, request/reply as a first-class pattern, very low footprint, no AWS lock-in, JetStream replay.

Where SQS beats NATS: zero ops, native AWS integration, simpler mental model for queue-shaped work, no cluster to run, no subject taxonomy to design.

RabbitMQ

RabbitMQ is an AMQP 0-9-1 broker. Producers publish to exchanges; exchanges route to queues via bindings (the routing rules). Four exchange types — direct, fanout, topic, headers — give you precise routing. RabbitMQ supports classic queues (with or without quorum), priority queues, dead-letter exchanges, and per-message TTL. Acknowledgements are explicit; you ack a message after you process it. You usually operate it yourself, on EC2 / EKS / a managed offering (CloudAMQP, Amazon MQ).5

Where RabbitMQ beats SQS: rich exchange/binding routing topology, priority queues, per-message TTL, complex queue patterns, on-prem deployability, full control over broker behavior.

Where SQS beats RabbitMQ: zero ops, native Lambda ESM, replicates across AZs by default, no broker patching, no cluster state to manage.

Kafka (and Kinesis)

Kafka is a distributed, partitioned, append-only log. Producers write to a topic; the topic is split into partitions; each partition is an ordered, durable sequence of records. Consumers read by tracking an offset and can rewind, replay, or read in parallel across partitions. The unit of ordering is the partition. Kafka is built for very high throughput (millions of events/sec), event sourcing, stream processing, and replay-heavy workloads. AWS's managed version is MSK; for Lambda integration you usually see Kinesis Data Streams used similarly.6

Where Kafka beats SQS: ordered replay, partition-level parallelism, event sourcing, stream processing, very high throughput, sub-second end-to-end with consumer groups.

Where SQS beats Kafka: zero ops, no cluster, no partition design, no offset management, no consumer group balancing, cheaper for low-to-moderate volume, simpler operational story. SQS is a queue; Kafka is a database you happen to write to in append-only fashion.

gRPC

gRPC is not a messaging system — it's a high-performance RPC framework (HTTP/2 + Protocol Buffers). You call a function on a remote service as if it were local. Streaming variants exist (server-streaming, client-streaming, bidi) but the contract is request/response, not fire-and-forget. If you need an answer from the consumer before the producer can continue, gRPC is the right shape; if you don't, it isn't.7

Where gRPC beats SQS: synchronous result, strongly-typed contracts (protobuf), low-latency service-to-service, bidi streaming, code generation for many languages.

Where SQS beats gRPC: async work, durable buffer, fan-out to many consumers, no consumer to be online, retries / DLQ / visibility timeout built in.

EventBridge (a reminder)

Already covered in lesson 7. EventBridge is the AWS-native router: producers publish events with structure; rules match and route to many targets. It is to SQS what a router is to an inbox — different job, often combined.

The decision tree

Walk this top-down. The first question that resolves the choice stops the walk.

Q1. Does the producer need an answer from the consumer to continue?
    YES  → gRPC (or a synchronous HTTP call / direct Lambda invoke).
    NO   → continue.

Q2. Is the work fan-out to many independent consumers?
    YES  → SNS, EventBridge, or Kafka (with consumer groups).
    NO   → continue.

Q3. Do consumers care about different *kinds* of events
    (rules select who sees what)?
    YES  → EventBridge, NATS subjects, or Kafka (filtered consumers).
    NO   → continue.

Q4. Does order matter per entity AND you need replay?
    YES  → Kafka (partition by entity), or NATS JetStream.
    NO   → continue.

Q5. Is the client a low-power device on a flaky network?
    YES  → MQTT.
    NO   → continue.

Q6. Are you on AWS, want zero ops, and the work is
    one-consumer-group-pulls-at-its-own-pace?
    YES  → SQS. (Standard, unless you can name a per-entity
           order rule, in which case SQS FIFO.)
    NO   → continue.

Q7. Do you need rich routing, priority, per-message TTL,
    or on-prem?
    YES  → RabbitMQ.
    NO   → continue.

Q8. Do you need sub-millisecond latency or in-process pub/sub?
    YES  → Redis / Valkey (typically ElastiCache for Valkey on AWS).
    NO   → SQS (almost certainly).
How to use the tree In an interview or design review, walk it out loud. The value isn't reaching "SQS" — it's being able to defend why you didn't pick the others.

The Lambda lens — how the answer tilts on AWS

If your system is Lambda-centric, three of these tools get demoted in your mind by default: RabbitMQ (operate a broker), NATS (operate a cluster), Kafka (operate a cluster unless you pay for MSK and tune it). The Lambda-ESM-compatible, zero-ops shortlist is:

  • SQS — durable queue, the workhorse.
  • SNS — push fan-out.
  • EventBridge — content routing.
  • Kinesis Data Streams — when you genuinely need Kafka-like ordered replay on AWS.
  • Amazon MQ — when a partner or legacy system requires AMQP and you don't want to run RabbitMQ.
  • ElastiCache for Valkey — when you need sub-millisecond in-memory pub/sub or queues behind Lambda and you want it managed on AWS (now the default engine for new ElastiCache clusters).

You can absolutely run Kafka behind Lambda (MSK + event source mapping), NATS behind Lambda (with a poller), or Redis/Valkey behind Lambda (ElastiCache + custom client). Each works. The question is whether the operational cost of the broker is worth the features it gives you over SQS/SNS/EventBridge.

Three honest "SQS isn't the right answer" cases

  1. Replay-heavy event sourcing. If your service's source of truth is the event log and you routinely need to rewind and reprocess days of history, Kafka is the better fit. SQS deletes on success; you can't replay.
  2. Sub-millisecond in-process pub/sub. If you have a hot path that needs to fan out inside a process or a small cluster in single-digit ms, Redis/Valkey pub/sub (or NATS Core) beat SQS on latency. On AWS, ElastiCache for Valkey is the managed way to get this.
  3. Edge devices on flaky networks. Sensors, vehicles, retail terminals, anything that reconnects across spotty cellular: MQTT is purpose-built for that, and SQS would force you to write the persistence and resumption logic yourself.

Three honest "SQS is the right answer" cases

  1. Async work between Lambda functions on AWS. The ESM is the right tool, full stop.
  2. Spike absorption. A bursty workload that must not overwhelm a downstream — the queue is the shock absorber.
  3. Loose coupling without a broker. When you want durable, fire-and-forget work but don't want to operate (or pay for) a broker cluster.

What the interview answer sounds like

I'd start with SQS because the work is async, one consumer group, and the system is Lambda-centric. SQS gives me durable buffering, native Lambda integration, and zero ops. I considered Kafka because of the volume, but we don't need replay or per-entity ordering — and operating MSK for this is overkill. I considered Redis for latency, but the work is in the 100s-of-ms range, not sub-ms — and if it ever did need sub-ms, I'd reach for ElastiCache for Valkey (the managed path), not SQS. If we needed to fan out to multiple teams, I'd put an SNS topic in front or have each team subscribe via their own SQS queue off EventBridge.

That answer shows the axes, not just a name.
