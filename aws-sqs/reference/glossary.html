SQS Glossary

Every term in this course, in one place. Return here when a lesson uses a word you do not fully own.

The queue and its messages

Queue
A durable, hosted buffer between a producer (sender) and a consumer (receiver). Producers call SendMessage to add work; consumers call ReceiveMessage to pull work; consumers call DeleteMessage when done. SQS stores messages redundantly across multiple Availability Zones.1
Message
A unit of work on a queue. Has a MessageBody (the payload, up to 256 KiB), a SQS-assigned MessageId, and on receive a ReceiptHandle that authorizes you to delete it.2
MessageBody
The free-form payload. SQS treats it as opaque text; the consumer parses it. Most apps send JSON here.
MessageId
SQS-generated unique id for a message. Use it as a deduplication key when you build idempotent handlers.
ReceiptHandle
An opaque token returned with every received message. You must present it to DeleteMessage to remove the message, or to ChangeMessageVisibility to extend the visibility window. ReceiptHandles expire — they are not durable references.
Message attributes
Up to 10 small structured fields (String / Number / Binary, with optional custom labels like Number.byte) sent alongside the body. Useful for routing hints or business metadata that consumers need without parsing the body. Total message size (body + attributes) capped at 256 KiB.3
Message system attributes
Reserved attributes consumed by AWS services (currently AWSTraceHeader for X-Ray). Don't invent your own here — the AWS. prefix is reserved.

Producers and consumers

Producer
Anything that calls SendMessage (or SendMessageBatch). In a Lambda-centric system, often the Lambda that handles an inbound API request, an S3 event, or a stream record.
Consumer
Anything that calls ReceiveMessage. In a serverless app, usually a Lambda wired to the queue via an event source mapping. SQS also lets you run a long-polling worker on EC2, ECS, or your laptop.
Event source mapping (ESM)
Lambda-side configuration that polls the queue on your behalf, batches messages, invokes your function synchronously, and deletes successfully-processed messages. The ESM is the standard way to attach a Lambda to an SQS queue.4

Delivery semantics

At-least-once delivery
SQS standard queue guarantee: a message will be delivered at least once, but it may arrive more than once. Your handler must tolerate duplicates (see idempotency).5
Best-effort ordering
Standard queue guarantee about order: messages are generally delivered in send order, but high volume can reorder them. Don't rely on order from a standard queue.
Exactly-once processing
FIFO queue guarantee: each message is delivered exactly once and processed in order. Achieved via deduplication IDs and a per-message visibility window.6
MessageGroupId
A FIFO-only identifier that partitions a queue into ordered streams. Two messages with the same MessageGroupId are delivered strictly in order; messages with different group ids can be processed in parallel. Use one group per logical entity (e.g. per customer or per order).7
MessageDeduplicationId
A FIFO-only token (or content-based hash) that prevents SQS from accepting the same message twice within a 5-minute window. Use it whenever your producer might re-send (retries, at-least-once producer side).8

Polling and timing

Short polling (default)
ReceiveMessage samples a subset of SQS servers and returns immediately, even with zero messages. Cheap on the producer side; can result in more empty receives at low load.9
Long polling
Setting WaitTimeSeconds to 1–20 makes SQS hold the receive call open until a message is available or the wait expires. Reduces empty responses and cost; recommended for almost every consumer.9
Visibility timeout
The window after a message is received during which no other consumer can see it. Default 30s; range 0–43,200s (12h); can be changed per-message via ChangeMessageVisibility. If you don't DeleteMessage before it expires, the message becomes visible again.10
Message retention
How long a message lives in the queue if never deleted. Default 4 days; configurable 60 seconds to 14 days (1,209,600 seconds).1
In-flight message
A message that has been received but not yet deleted. For standard queues, the in-flight limit is ~120,000 — once you hit it, receives fail until you delete or let visibility expire.

Failure handling

Poison message
A message that consistently causes your handler to fail (bad payload, missing dependency). Without a DLQ, it loops forever.
Dead-letter queue (DLQ)
A second queue that SQS moves a message to after it has been received maxReceiveCount times without being deleted. The DLQ must be in the same account and region as the source queue; a FIFO source can use a FIFO DLQ.11
maxReceiveCount
The threshold on the source queue's redrive policy. Default 10; tune based on how transient you expect failures to be.
Idempotent handler
A consumer that produces the same observable effect regardless of whether it processes a given message once or twice. Usually implemented by deduplicating side effects on a key (often the SQS MessageId or a business id from the body).12

The decision: queue vs bus vs topic

Event bus (EventBridge)
A router. Producers send events to the bus; rules match on event structure and deliver to many targets. Good for fan-out and decoupling consumers.
Queue (SQS)
A buffer with a single consumer group. Producer writes once, one or many workers pull at their own pace. Good for work that must be done reliably and where pace matters.
Topic (SNS)
A push fan-out. One producer, many subscribers (HTTP, email, SQS, Lambda). Good when every subscriber must get a copy and consumers can keep up.
