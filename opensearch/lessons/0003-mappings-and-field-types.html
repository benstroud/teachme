Mappings & Field Types

How you tell the engine what each field is, and why text differs so sharply from keyword.

The mental model in one sentence

A mapping tells OpenSearch how to store and index each field: text fields are tokenized for full-text search, keyword fields are kept as one exact value, and numeric/date/boolean fields are typed for range queries and aggregations.1

Dynamic vs explicit mapping

By default OpenSearch infers field types from your first document (dynamic mapping). That is convenient but easy to get wrong — a human-readable id might be inferred as long, or a short description as text when you actually need exact matching. Production mappings are usually written by hand.

The field types you will reach for

TypeUse it for
textFull-text on natural prose: analyzed, matched by words.1
keywordOne exact token: ids, slugs, enums, statuses; sortable, aggregatable.1
integer / longWhole numbers for range filters and metrics.
doubleFloating-point prices, ratings, coordinates.
booleanTrue/false flags.
dateTimestamps, for date ranges and histogram buckets.
object / nestedJSON sub-objects; nested keeps arrays independent.

A small explicit mapping

PUT /products
{ "mappings": {
    "properties": {
      "name":   { "type": "text", "fields": { "raw": { "type": "keyword" } } },
      "sku":    { "type": "keyword" },
      "price":  { "type": "double" },
      "tags":   { "type": "keyword" },
      "status": { "type": "keyword" },
      "added":  { "type": "date" }
    } } }
Key idea The name field is both text (for "copper mug" searches) and, via the raw sub-field, keyword (for exact sort/aggregation). One source field, two stored views.1
