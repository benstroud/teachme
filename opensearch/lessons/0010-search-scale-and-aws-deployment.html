Search at Scale on AWS OpenSearch

Pagination, shard-replica scaling, and picking between a domain and Serverless.

The mental model in one sentence

As search grows, you stop paging with from/size and switch to search_after + a point-in-time (PIT), and you choose an AWS deployment — a provisioned domain or OpenSearch Serverless — that matches your workload's predictability.1

Deep pagination

from/(size) is fine for the first pages but grows expensive past ~10,000 results — the coordinator must fetch and sort every preceding bucket. For deep, stable paging use a PIT (a fixed snapshot of the index) with search_after, which resumes from the last sort value seen.1

Provisioned domain vs OpenSearch Serverless

DeploymentWho manages capacityBest when
Provisioned domainYou choose instance types/countsPredictable, steady load you want to tune.2
OpenSearch ServerlessAWS auto-scales collections (OCUs)Intermittent or unpredictable load.2

A reference shape

ingest (bulk / a stream)  →  index  →  search API
   products_v2 (mapping + analyzer)        match / term / aggs
   PIT + search_after for deep pages
Key idea The engine scales by shards and replicas; Serverless hides shard and capacity management for you. Pick pagination and deployment by workload — not by habit.2
