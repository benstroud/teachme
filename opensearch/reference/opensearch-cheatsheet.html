OpenSearch Cheat Sheet

The compressed essence of the course. Skim before a lesson, study it fully before an interview.

1. The stack

OpenSearch = open-source search engine (Elasticsearch 7.10 fork)
Amazon OpenSearch Service = managed service; domain === cluster
  domain -> nodes (EC2 instances) -> indices -> shards(+replicas) -> documents
  • Search the index: OpenSearch distributes each index across shards.1

2. Documents & the REST API

# index (create-or-replace), read, update, delete
PUT    /products/_doc/1      { "name": "Copper Mug", "price": 12.5 }
GET    /products/_doc/1
POST   /products/_doc/1/_update  { "doc": { "price": 11.0 } }
DELETE /products/_doc/1
  • PUT with an explicit _id is idempotent; a bare POST lets the engine pick an id.2

3. Mappings & field types

PUT /products
{ "mappings": { "properties": {
    "name":  { "type": "text", "fields": { "raw": { "type": "keyword" } } },
    "sku":   { "type": "keyword" },
    "price": { "type": "double" },
    "added": { "type": "date" } } } }
  • text = analyzed for full-text; keyword = one exact, aggregatable value.3
  • Add a .raw keyword sub-field when one source field needs both uses.3

4. Indexing & bulk

POST /products/_bulk
{ "index": { "_id": "1" } }
{ "name": "Copper Mug", "price": 12.5 }
{ "index": { "_id": "2" } }
{ "name": "Steel Flask", "price": 9.9 }
  • Bulk is NDJSON: an action line, then a document line.4
  • Batching slashes round trips; id-based indexing is retry-safe.

5. Queries: match, term, bool

# full-text (analyzed, OR default)
{ "query": { "match": { "name": "copper mug" } } }
# exact value (unanalyzed, keyword)
{ "query": { "term": { "status": "PENDING" } } }
# combine
{ "query": { "bool": {
    "must": [{ "match": { "category": "kitchen" } }],
    "should": [{ "match": { "name": "copper" } }],
    "filter": [{ "term": { "inStock": true } }] } } }
  • match analyzes the input; term takes it verbatim. Use them on text vs keyword.5
  • must scored + required, should bonus, filter required, unscored.6

6. Relevance & BM25

# every hit has _score; _explain shows how
POST /products/_search { "query": {...}, "explain": true }
  • BM25 scores from term frequency, inverse document frequency, and field length (k1, b).7
  • Use filter for constraints so they never distort ranking.

7. Analyzers

# see the tokens
GET /_analyze { "analyzer": "standard", "text": "Let's contribute!" }
# custom analyzer = character filters + tokenizer + token filters
  • Analyze the same way at index and query time, or terms never align.8

8. Aggregations

# metric
{ "size": 0, "aggs": { "avg_price": { "avg": { "field": "price" } } } }
# bucket
{ "size": 0, "aggs": { "by_status": { "terms": { "field": "status" } } } }
  • Metrics (avg/sum/cardinality) compute; buckets (terms/date_histogram) group by value.9
  • Aggregate the keyword sub-field; text fields are not aggregatable by default.9

9. Scale on AWS

# deep pages
open PIT -> search_after on last sort value  (not a huge from/size)
# deploy
Provisioned domain  -> you size instances    (predictable load)
OpenSearch Serverless -> AWS auto-scales      (intermittent load)
  • PIT + search_after resume stably; deep from/size is expensive.10
  • Provisioned = you manage capacity; Serverless = AWS does.11

10. Checklist

  • Model documents and write an explicit mapping (text vs keyword, .raw).
  • Ingest with bulk and a stable _id.
  • Pick match for prose, term/terms for exact values, bool to combine.
  • Verify tokenization with _analyze before trusting a field.
  • Aggregate on keyword sub-fields for facets and reports.
  • Choose pagination by depth and deployment by workload predictability.
