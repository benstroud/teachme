When to Use & Measure

DataLoader is not always the answer — learn when to skip it, and always verify the query count with a real log.

The mental model in one sentence

Use DataLoader when many per-item or repeated loads hit the same data source in one request; skip it for single root lookups and already-loaded data, and confirm the effect by counting queries.1

When DataLoader is the wrong tool

  • Single root lookups. A top-level user(id) loads one entity once — batching adds nothing. Just query directly.1
  • Data you already have. If the parent already holds the children (a join fetched them), loaders that re-query are pure waste — use the default value.
  • Cross-request caching. The memoization cache is per request; for shared, TTL-managed caching use a real cache layer with invalidations, not a loader.1
  • Mutations of fresh data. Caching a just-written value can hand back stale data unless you clear() after the write.

Verify with a query log

Never trust the schema reading or guess. Instrument the data layer to log every query (e.g. a logger on the driver, or a request-scoped counter), run one representative nested operation, and read the count:

// count per request — pseudo
let queryCount = 0;
logger.on('query', () => queryCount++);
// ... run the operation ...
console.log('queries:', queryCount);   // N+1 shows loud and clear
Key idea Measure before and after: a naive query vs a loader-driven query on the same operation. If the numbers don't move, the loader is doing nothing — and you should either remove it or fix the resolver that bypasses it.

Keep the data layer tidy

Apollo recommends containing fetch logic in data source classes with methods resolvers call; loaders can live inside that boundary so batching, deduplication and caching stay a data-layer concern, not resolver noise.2
