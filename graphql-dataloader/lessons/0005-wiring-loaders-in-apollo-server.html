Wiring Loaders in Apollo Server

Put per-request loaders on contextValue, and field resolvers call them — that is the whole integration.

The mental model in one sentence

Apollo builds a per-request contextValue (via its context function); you construct loaders there and hand them to field resolvers through the third resolver argument.1

Build loaders in the context function

import { ApolloServer } from '@apollo/server';
import { startStandaloneServer } from '@apollo/server/standalone';
import DataLoader from 'dataloader';

type ContextValue = {
  loaders: { users: DataLoader<string, User> };
};

const server = new ApolloServer<ContextValue>({ typeDefs, resolvers });

const { url } = await startStandaloneServer(server, {
  context: async ({ req }) => ({
    // fresh loader per request, ready for every resolver
    loaders: { users: new DataLoader<string, User>(batchUsers) },
  }),
});

The context function runs once per request and its result becomes contextValue, available to every resolver — exactly the right scope for your loaders.1

Call loaders from field resolvers

const resolvers = {
  Query: { users: (_p, _a, ctx) => ctx.loaders.users.loadMany(userIds) },
  // ... or load one entity per parent:
  Post: {
    author: (post, _a, ctx) => ctx.loaders.users.load(post.authorId),
  },
};

Because every Post.author resolver runs in near-parallel during resolution, all their load(post.authorId) calls land in one event-loop tick and batch into a single user query.2

Key idea The resolver does not change its shape much — it just reads the loader from context instead of querying directly. That one swap (per-item query → ctx.loaders.x.load(...)) is what turns N+1 into one batch.

Keep loaders reachable and typed

Model ContextValue.loaders with the concrete DataLoader<K, V> types so resolvers get end-to-end type safety, and keep the loader construction in a small function (e.g. makeLoaders()) so the context function stays readable.3
