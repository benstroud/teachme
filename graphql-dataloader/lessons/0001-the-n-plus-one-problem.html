The N+1 Problem

One request fans out into one query for a list plus one query per item — the most common GraphQL performance bug.

The mental model in one sentence

When a list field's resolver loads data per item, an operation that looks like one query actually triggers N+1 queries: one for the list, then one for each of its N items.2

Seeing it happen

// "Users and their pets"
// Query: { users { name pets { name } } }

const resolvers = {
  Query: { users: () => db.users.find() },        // 1 query
  User: {
    pets: (user) => db.pets.find({ ownerId: user.id }),  // N queries!
  },
};

For 50 users this issues 1 + 50 = 51 queries to the database. The query text a client sent looks like one request — the round-trips happen invisibly during resolution.2

Why resolution causes it

GraphQL resolves a nested selection depth-first: the parent resolver returns an array of objects, then each child field is resolved once per parent object. A naive field resolver that queries inside itself runs per item, and each run is a round-trip.2

Key idea The N+1 pattern is a direct consequence of per-item resolver execution. The fix is not to stop resolving children — it is to make all those per-item calls a single batch (which DataLoader does).

The real cost

  • Latency: each round-trip adds network + query overhead, so a 50-item list multiplies time to the database.
  • Load: the database and connection pool are hit far harder than the schema suggests.
  • Hidden at the edge: it does not show in a small demo, only under real nesting and data volume.2
