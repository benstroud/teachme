Errors & Missing Values

Not every key resolves: return null for missing rows, and choose between rejecting or returning an Error for a failed lookup.

The mental model in one sentence

DataLoader surfaces errors per load(): return null/undefined for a missing value, return an Error instance at that index for a per-key failure, and only throw when the whole batch genuinely fails.1

Missing values → null

async function batchUsers(keys) {
  const rows = await db.users.whereIn('id', keys);
  const byId = new Map(rows.map(r => [r.id, r]));
  return keys.map(id => byId.get(id) ?? null);   // null for missing
}

A key with no row is not an error — return null at that index so alignment holds and the caller sees "no data."1

Per-key Errors stop the whole batch

If one key's lookup fails, rejecting the batch rejects every key in it. To fail just one key without poisoning the others, return an Error instance at that index — DataLoader then rejects only that key's load() while the rest resolve.1

// helper from the README: map object results to ordered values, Error for misses
function objResults(batchLoader) {
  return keys =>
    batchLoader(keys).then(objValues =>
      keys.map(key => objValues[key] || new Error(`No value for ${key}`)),
    );
}

Throwing from the batch function

Throwing inside the batch function causes the entire batch to reject — every load() in that batch gets the rejection. Reserve that for real batch-level failures (e.g. the data source is down), not for a single missing row.1

Key idea Align error handling with the semantics: null = absent but fine; per-key Error = that one lookup failed, others proceed; thrown batch = everything failed. Your resolvers then decide how each of those surfaces in GraphQL.
