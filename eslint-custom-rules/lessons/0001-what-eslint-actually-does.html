What ESLint Actually Does

A linter is a reader, not a runner: parse, traverse, report.

The pipeline, in one picture

source text
   |  parser (espree by default)
   v
ESTree AST + tokens + comments
   |  config resolution: which rules, at what severity
   v
rule visitors  ->  context.report(...)
   |
   v
formatter  ->  terminal, CI, editor

ESLint is a static analyser. It reads your source, builds a syntax tree, and walks that tree. It never executes your program, so it can flag a console.log inside a branch that never runs.1

Everything else in ESLint is plumbing around one idea: a rule is a function from the tree to a list of messages.2

What it does not do

QuestionThe linter's answer
Will this line throw at runtime?Unknown — it never runs the code.1
Is this value a string?Unknown — the default parser sees syntax, not types.
Is this variable used anywhere?Knowable — it can resolve bindings and references.2
Does this match our team convention?Knowable — that is exactly what rules encode.

Type-aware rules exist, but they need a parser wired to a TypeScript program (the typescript-eslint stack). That is a different machine bolted onto the same pipeline, not a feature of the default one.3

Anatomy of a problem

/Users/me/app/src/index.js
  3:7  error  Unexpected console statement  no-console

✗ 1 problem (1 error, 0 warnings)

A problem carries a ruleId, a severity, a message, a line and column, and sometimes a fix. Note what the severity does: it decides whether the problem is reported as a warning or an error, and therefore whether the process exits non-zero. It does not change what the rule inspects.4

npx eslint .                     # report everything
npx eslint src/index.js --fix    # apply safe fixes for this file
npx eslint . --max-warnings 0    # warnings now fail the build

Check yourself

1. ESLint finds problems by…

2. A rule can report code that never runs because…

3. Raising a rule from warn to error changes…

Key idea When a rule surprises you, ask which node it looked at, not which line you were thinking of. The line number is an output; the node is the input.2

What to hold onto

  • Linting is reading, not running.
  • The input to every rule is an AST node plus the surrounding source.
  • Severity controls reporting and exit codes, never detection.
