Options, Schema, and Defaults

Give a rule a dial, and validate the dial before it turns.

A dial on the rule

// eslint.config.js
rules: {
  "example/no-banned-calls": ["error", { "forbidden": ["eval", "Function"] }],
}

Validation runs in a fixed order: a non-array config is wrapped; element 0 is checked as a severity; if the rule is off, validation stops; every remaining element is copied into context.options; then meta.schema is validated against exactly those elements.1

Consequence worth remembering: a schema can never validate the severity, because severity is stripped before the rule or its schema sees anything.12

Declaring the schema

meta: {
  schema: [
    {
      type: "object",
      properties: {
        forbidden: { type: "array", items: { type: "string" }, minItems: 1 },
        allowInTests: { type: "boolean" },
      },
      additionalProperties: false,      // reject typos instead of ignoring them
    },
  ],
  defaultOptions: [{ forbidden: ["eval"], allowInTests: true }],
}

An array schema is positional: element i validates context.options[i]. If the user passes more options than there are schemas, validation fails; fewer is fine and the unmatched schemas are ignored.1

defaultOptions is merged recursively under whatever the user supplied, so a partial object still gets every default filled in.1

The rule that consumes it

create(context) {
  const [{ forbidden }] = context.options;   // defaults already merged
  const sourceCode = context.sourceCode;

  return {
    CallExpression(node) {
      if (node.callee.type !== "Identifier") { return; }
      const name = node.callee.name;
      if (!forbidden.includes(name)) { return; }

      context.report({
        node,
        messageId: "banned",
        data: { name },
      });
    },
  };
}

Declare messages: { banned: "Do not call {{name}}()." } and the interpolated value comes from data. One wording, one place, parameterised by the matched node.1

Why bother with a schema

  • A bad config fails before linting, with a message pointing at the offending option — not a TypeError deep inside your rule.1
  • Omitting schema (or writing []) means "no options accepted"; passing options then throws.1
  • schema: false opts out of validation entirely. It is allowed, and discouraged.1
Key idea Options are part of the rule's public contract. If two teams need different behaviour, that is a second option — not a second fork of the rule.1
Ask the agent Add an allowInTests option to your rule and honour it by checking context.filename. Then write the config that turns the rule off for test files without changing the rule at all.
