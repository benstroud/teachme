Packaging a Plugin

Rules travel in plugins. Configs are opt-in, always.

A plugin is a plain object

// eslint-plugin-acme.js  (CommonJS)
const noTodo = require("./rules/no-todo");
const noBannedCalls = require("./rules/no-banned-calls");

const plugin = {
  meta: { name: "eslint-plugin-acme", version: "1.0.0" },
  rules: {
    "no-todo": noTodo,
    "no-banned-calls": noBannedCalls,
  },
  configs: {},
};

// A config is just another array of config objects.
plugin.configs.recommended = [
  {
    plugins: { acme: plugin },        // self-reference is expected
    rules: {
      "acme/no-todo": "error",
      "acme/no-banned-calls": ["warn", { "forbidden": ["eval"] }],
    },
  },
];

module.exports = plugin;

meta identifies the plugin, rules is the rule registry, and configs holds ready-made arrays. Nothing else is required, and the tutorial walks this exact file into existence.12

Registering it locally, before publishing

// eslint.config.js
const acme = require("./eslint-plugin-acme");

module.exports = [
  {
    files: ["**/*.js"],
    plugins: { acme },                    // name it here, use it below
    rules: { "acme/no-todo": "error" },
  },
  // or consume the plugin's own config, explicitly:
  ...acme.configs.recommended,
];

The key in plugins becomes the namespace: acme plus no-todo yields the rule ID acme/no-todo. Rename the key and every rule reference changes with it.1

Note what is not happening: ESLint does not discover or auto-apply configs.recommended. The user has to put it in the array. Shipping configuration as its own package is a separate, documented pattern.13

Publishing

// package.json
{
  "name": "eslint-plugin-acme",
  "peerDependencies": { "eslint": ">=9.0.0" },
  "keywords": ["eslint", "eslintplugin", "eslint-plugin"]
}
  • Name the package eslint-plugin-<name> so it is discoverable and the namespace is obvious.1
  • List eslint as a peer dependency — the plugin is a guest in the user's linter, not a second copy of it.1
  • Keep meta.name and meta.version in sync with the package; tooling uses them to identify and cache the plugin.1

Supporting the old config system too? Export flat configs under their plain names and keep the legacy objects prefixed, or keep recommended for legacy and add flat/recommended. Both are documented compatibility paths.1

Check yourself

1. With plugins: { acme }, the rule no-todo is configured as…

2. A plugin's configs are…

3. A published plugin should declare eslint as…

Ask the agent Wrap your two rules in a plugin object, register it locally, and confirm the namespaced ID appears in eslint --print-config output for one file.
